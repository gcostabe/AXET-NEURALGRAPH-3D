# Análise Estruturada — Arquitetura de Flows, Managers Java e Orquestração por iFrame

## 1. Síntese executiva

A sessão teve caráter técnico e de treinamento. O foco principal foi explicar como funcionam os front-ends configuráveis baseados em *flows*, especialmente a execução das ações de tela por meio de serviços Java denominados **managers**.

O modelo apresentado combina parametrização em banco de dados, componentes técnicos de front-end, serviços REST e código Java. As definições de fluxo, passos, elementos visuais, ações, estados e regras de habilitação são mantidas em tabelas. A camada Java executa a lógica de backend adequada para cada ação, podendo acessar APIs, serviços legados do backend de Neutron ou, em determinados casos, um conector para TronWeb.

Também foi detalhado o papel de **Fuyi/Fuji** — a transcrição alterna entre essas grafias — como orquestrador das aplicações. Ele exibe aplicações de diferentes famílias em `iframe`, mantém Neutron carregado e realiza a comunicação entre aplicações usando mensagens de janela (`window.postMessage` e listeners de eventos).

A mensagem central da reunião é que o comportamento funcional de uma tela não depende exclusivamente do código: uma parte significativa é dirigida por configuração. O desenvolvimento Java entra sobretudo na implementação das ações de backend e na composição dos dados devolvidos aos componentes da interface.

> **Nota de nomenclatura:** a transcrição parece registrar variantes como “Fuyi”, “Fuji”, “Neutron”, “TronWeb”, “Actium”, “FlowPad”, “DTO Tron” e “NoCherector/Nocherector”. Este documento preserva os nomes conforme o contexto, mas não confirma a grafia oficial de todos eles.

## 3. Problemas e necessidades abordados

### 3.1 Necessidade de construir telas com comportamento configurável

A arquitetura apresentada busca permitir que fluxos e telas sejam definidos por dados configuráveis, sem concentrar toda a estrutura visual e comportamental exclusivamente no código.

A parametrização inclui, entre outros elementos:

- fluxo;
- passos do fluxo;
- tela inicial e final;
- componentes da tela;
- ações de navegação;
- ações por componente;
- ações por registro de uma lista;
- etiquetas;
- ícones;
- condições de habilitação;
- estados de visibilidade e validade;
- configuração funcional;
- configuração técnica de componentes.

### 3.2 Evitar duplicação de lógica de backend

O expositor destacou que funções semelhantes não devem ser repetidas em vários managers. O motivo explicitado é evitar um problema associado ao legado de Neutron: quando a lógica está copiada em vários pontos, uma alteração exige localizar todos eles, modificar cada ocorrência e testá-las individualmente.

A direção proposta é:

```text
Funcionalidade repetida
↓
Criação de serviço ou classe comum
↓
Reutilização por múltiplos managers
↓
Menos duplicação e menor esforço de manutenção
```

### 3.3 Aproveitar funcionalidades já existentes

Em determinados domínios, especialmente emissão e sinistros, há funcionalidade relevante já implementada em Neutron. Nesses casos, foi relatado que os novos managers podem injetar serviços de backend de Neutron e reutilizá-los.

Quando a funcionalidade não existe previamente em Neutron, a orientação apresentada é não criar necessariamente novas peças em Neutron. Em vez disso, a implementação pode ser feita diretamente em APIs e consumida pelo manager por meio de um proxy.

### 3.4 Integrar aplicações de diferentes famílias

A organização possui aplicações diferentes por família ou domínio, e não necessariamente uma aplicação por flow. O orquestrador resolve a navegação e o encaixe dessas aplicações em `iframe`, incluindo a troca de dados e os retornos entre chamador e aplicação chamada.

## 4. Solução apresentada

A solução combina um modelo configurável de front-end com execução centralizada de ações no backend Java.

De forma consolidada, o funcionamento pode ser entendido assim:

```text
Usuário interage com um componente
↓
Componente técnico chama um serviço de ação
↓
Camada REST recebe o DTO da tela
↓
Dispatcher consulta a parametrização
↓
Manager ou managers correspondentes são identificados
↓
Método Java apropriado é executado
↓
Manager consulta serviços, APIs, banco ou legado reutilizado
↓
Manager monta DTOs de saída e altera estados dos componentes
↓
Front-end recebe a resposta e atualiza a tela
```

A apresentação distingue dois conjuntos de responsabilidades:

| Camada | Responsabilidade apresentada |
|---|---|
| Parametrização | Definir fluxos, passos, componentes, ações, estados, etiquetas, regras e mapeamento de managers |
| Componentes técnicos | Renderizar a configuração e disparar chamadas técnicas |
| Serviço REST de ação | Receber a solicitação e iniciar o processamento |
| Dispatcher | Resolver quais managers devem ser executados |
| Manager Java | Executar a lógica de backend associada à ação |
| APIs / BE Neutron / conector | Executar acesso a dados ou funcionalidade de negócio |
| Orquestrador Fuyi/Fuji | Montar aplicações, navegar entre elas e trocar mensagens |

Foram citados principalmente três serviços ligados ao fluxo.

| Serviço citado | Finalidade descrita |

| `FlowPad` | Recupera informações de todos os passos do fluxo |

### 5.1 Serviço `Flow`

O serviço `Flow` é acionado ao entrar em uma operação. Na demonstração, foram enviados elementos como:

- companhia;
- idioma, com exemplo em espanhol;
- identificador da operação.

A resposta traz, segundo a explicação:

- o primeiro passo do fluxo;
- o identificador do passo;
- ações de navegação;
- componentes da tela;
- etiquetas;
- ícones;
- configuração associada a cada elemento.

A tela inicial demonstrada possuía um passo identificado como `searchV`, enquanto o passo final foi citado como `editV`.

### 5.2 Serviço `FlowPad`

O `FlowPad` foi apresentado como a fonte de informações de todos os passos do fluxo. Na demonstração, devolvia pelo menos:

- primeiro passo;
- segundo passo;
- indicação de passo inicial;
- indicação de passo final;
- etiqueta a ser mostrada no cabeçalho;
- indicadores relacionados a navegação e *stepper*.

O expositor informou que alguns campos retornados por esse serviço existem para conhecimento técnico, mas não devem ser alterados pelos desenvolvedores que configuram as telas.

### 5.3 Serviço `Action`

O serviço `Action` é o ponto central para executar ações. Ele é chamado pelos componentes técnicos, sempre com uma estrutura de entrada comum, referida como um DTO de Tron — a nomenclatura exata não ficou totalmente clara na transcrição.

Esse DTO contém os elementos de tela e seus dados. O mesmo modelo estrutural é usado para entrada e saída: o manager lê os dados recebidos e devolve a estrutura atualizada com:

- resultados de consultas;
- alteração de visibilidade;
- alteração de validade;
- mensagens;
- alertas;
- marcas de navegação;
- dados compartilhados para etapas subsequentes.

## 6. Modelo de fluxo e parametrização

### 6.1 Fluxos e passos

O fluxo demonstrado possui, aparentemente, dois passos:

| Passo citado | Papel apresentado |
|---|---|
| `searchV` | Passo inicial de busca |
| `editV` | Passo final de edição, consulta ou modificação |

A parametrização indica quais passos são iniciais ou finais. Também define as transições entre eles, como a navegação do primeiro passo para o segundo.

### 6.2 Ações por nível

As ações podem existir em níveis diferentes:

| Nível | Comportamento descrito |
|---|---|
| Componente | Ação ligada a um componente específico da tela |
| Passo/tela | Ação ligada ao passo como um todo; a transcrição menciona o uso de hífen para indicar esse nível |
| Lista | Ação apresentada no nível geral de uma tabela ou lista |
| Registro | Ação exibida para cada registro da lista |

Na lista demonstrada:

- a ação de criar aparecia no nível da tabela;
- ações como consultar, modificar e selecionar apareciam no nível de registro;
- uma marca denominada `registry` parecia controlar essa diferença.

A transcrição registra que `registry = false` faz a ação aparecer como ação geral da tabela, enquanto `registry = true` faz a ação aparecer associada a cada linha.

### 6.3 Estados dos elementos

Os elementos de tela possuem estados. O estado `0` foi descrito como “visível e não válido”; o estado `2` foi demonstrado como oculto.

A reconstrução funcional apresentada é:

```text
Componente inicialmente oculto
↓
Usuário executa uma ação, por exemplo, busca
↓
Manager carrega os dados
↓
Manager altera o estado do componente
↓
Componente passa a ser exibido como válido
```

> A transcrição não fornece um catálogo completo dos estados possíveis, nem confirma formalmente todos os significados numéricos além dos exemplos demonstrados.

### 6.4 Condições de habilitação

A configuração dos botões pode incluir uma expressão lógica. No exemplo, o botão de busca só era habilitado quando o campo de número de apólice recebia valor.

A explicação indica que a condição era avaliada com base nos dados do formulário. Enquanto o campo estivesse vazio, a condição resultava em falso e o botão permanecia desabilitado.

## 8. Processo de execução de uma ação

### 8.1 Entrada no fluxo

Ao entrar em um fluxo:

1. o cliente chama `Flow`;
2. o serviço consulta a parametrização;
3. a primeira tela e seus componentes são retornados;
4. os componentes técnicos renderizam o conteúdo;
5. pode haver execução de uma ação inicial, referida como `initialize`.

Foi explicado que, se `initialize` estiver definido em Java, o código é executado quando a tela é carregada. Caso não esteja definido, a solicitação pode ocorrer sem produzir alteração de dados.

### 8.2 Disparo de uma ação pelo usuário

No exemplo de busca:

1. o usuário preenche o número da apólice;
2. o botão Buscar fica habilitado;
3. o componente técnico chama o serviço `Action`;
4. o DTO enviado contém os dados da tela;
5. o dispatcher identifica o manager associado à ação;
6. o manager executa a busca;
7. os resultados são colocados no componente de lista;
8. a lista, inicialmente oculta, passa para estado válido e visível;
9. o front-end apresenta os dados.

### 8.3 Retorno booleano dos managers

Os métodos de ação nos managers retornam `true` ou `false`, e não diretamente uma coleção ou objeto de domínio como retorno do método Java.

O significado apresentado foi:

| Retorno | Significado descrito |
|---|---|
| `true` | Execução concluída sem erro |
| `false` | Ocorreu erro |

Os dados não são retornados pelo valor do método. Eles são gravados no mecanismo de intercâmbio de dados, chamado de `Data Exchange` ou simplesmente `Data` na explicação.

## 9. `Action Resource`, Dispatcher e Data Exchange

### 9.1 `Action Resource`

Foi apresentada uma classe denominada aproximadamente `Action Resource`, possivelmente exposta como recurso REST. Sua função é receber a solicitação de ação e coordenar a execução.

O processamento descrito é:

1. validar ou obter companhia;
2. receber o DTO enviado pela tela;
3. guardar os dados de entrada no `Data Exchange`;
4. consultar o dispatcher;
5. obter os managers que devem ser executados;
6. percorrê-los na ordem configurada;
7. executar cada manager;
8. verificar se houve erro;
9. decidir, conforme uma marca da parametrização, se continua ou interrompe o processamento;
10. devolver a estrutura de saída.

### 9.2 Dispatcher

O dispatcher consulta uma tabela de configuração que relaciona elementos como:

- fluxo;
- passo;
- componente;
- ação;
- manager;
- indicador relacionado ao tratamento de erro;
- possível método específico.

A transcrição registra que, em uma mesma ação, pode haver mais de um manager associado. Isso permite que, por exemplo, vários componentes realizem inicialização durante a entrada da tela.

### 9.3 Data Exchange

O `Data Exchange` foi apresentado como um objeto disponível ao longo da requisição e injetado no manager como componente de Spring, sendo único por solicitação.

Ele armazena:

- dados de entrada da tela;
- dados de saída por componente;
- dados compartilhados do fluxo;
- mensagens;
- alertas;
- marcas de navegação;
- dados adicionais personalizados.

A explicação diferencia dois usos:

| Área | Finalidade |
|---|---|
| `data` de componente | Dados que o componente deve mostrar ou consumir |
| `custom` de componente | Informações adicionais ligadas ao componente |
| `flow data` | Dados que precisam ser compartilhados entre componentes, managers ou passos do fluxo |

## 10. Resolução de métodos nos managers

Todos os managers estendem uma classe-base, referida como `BaseManager`, diretamente ou por meio de uma classe-base específica do domínio, por exemplo uma base ligada a emissão.

A classe-base é responsável por decidir qual método concreto deve ser chamado.

A ordem descrita foi:

```text
1. Verificar se existe método específico definido na parametrização
↓
2. Se não existir, procurar método:
   execute<Componente><Ação>
↓
3. Se não encontrar, procurar:
   execute<Ação>
↓
4. Executar o método localizado
```

O exemplo apresentado envolvia uma ação de busca e uma convenção semelhante a:

```java
execute<IdentificadorDoComponente><Acao>
```

A transcrição cita um método equivalente a `execute...Search`, relacionado ao formulário de busca.

> A convenção exata de maiúsculas, prefixos e nomes foi explicada por exemplos, mas não há especificação formal completa no conteúdo fornecido.

## 11. Implementação dos managers Java

### 11.1 Papel do manager

O manager é a peça de código que implementa a lógica de backend associada à ação de tela. Ele:

- recebe indiretamente os dados enviados pelo front-end;
- recupera o contexto do fluxo;
- mapeia os dados genéricos para DTOs específicos;
- chama a capacidade de backend necessária;
- monta os DTOs de saída;
- altera estados de tela;
- registra dados de fluxo;
- define mensagens, alertas e navegação quando necessário.

### 11.2 Recuperação dos dados de entrada

O fluxo descrito para recuperar dados é:

1. obter o `Data Exchange`;
2. buscar o objeto associado ao identificador do componente;
3. recuperar o DTO genérico;
4. usar um `ObjectMapper`;
5. converter o conteúdo para a classe de DTO esperada;
6. trabalhar com propriedades tipadas.

Para listas, foi citado o uso de algo semelhante a `TypeReference`; para objetos simples, seria utilizado o mapeamento para uma classe específica.

### 11.3 Formação da resposta

Após executar a lógica:

1. cria-se um DTO de saída para o componente destino;
2. adicionam-se os dados retornados;
3. altera-se o estado do componente, quando necessário;
4. incluem-se dados `custom`, se aplicável;
5. registra-se o objeto no `Data Exchange`;
6. o front-end recebe a resposta e atualiza a interface.

No exemplo de busca, o formulário permaneceu como estava, enquanto o DTO de saída foi montado para a lista de resultados.

## 12. Formas de acesso ao backend e aos dados

A reunião apresentou diferentes alternativas, dependendo do domínio e das capacidades existentes.

### 12.1 APIs

Quando não há funcionalidade legada já criada, a orientação apresentada é criar a funcionalidade em APIs. O manager consome essas APIs por meio de um proxy.

O proxy:

- recupera a URL a partir das propriedades de ambiente;
- monta parâmetros;
- executa uma requisição REST;
- recebe a resposta;
- devolve os dados ao manager.

Na demonstração, foi mostrado um endpoint configurado em ambiente, incluindo um endereço IP interno. Este documento não reproduz o endereço completo por não ser necessário para o entendimento arquitetural.

### 12.2 Serviços de backend Neutron

Nos domínios que já possuem grande volume de lógica em Neutron, como emissão e sinistros, o manager pode injetar serviços de backend de Neutron por dependência e chamá-los diretamente.

A finalidade é aproveitar capacidades existentes, em vez de recriar toda a lógica.

### 12.3 OSM Connector e TronWeb

Para tesouraria, foi dito que não havia “paquetería” de Neutron. Nesse cenário, a aplicação funciona por meio de TronWeb, usando um projeto chamado **OSM Connector**.

O expositor o descreveu como algo semelhante a um backend Neutron, mas voltado à conexão com TronWeb. Também foi mencionada a possibilidade de acesso direto via JDBC.

> A reunião não detalha a arquitetura interna do OSM Connector, a origem do nome, os controles de segurança nem o modelo de acesso ao banco.

## 13. Navegação, encerramento e retorno entre flows

### 13.1 Navegação para o próximo passo

Para navegar dentro de um flow, o manager pode armazenar dados no `flow data` e marcar a navegação como próxima, em algo citado como `setNext(true)`.

No caso demonstrado:

- o usuário selecionava um registro;
- o registro selecionado era salvo no `flow data`;
- uma marca de somente leitura podia ser armazenada;
- a arquitetura reconhecia a indicação de `next`;
- o usuário era levado ao passo seguinte.

Para a ação de consulta, a marca de somente leitura era verdadeira. Para atualização, era falsa.

### 13.2 Navegação entre flows ou aplicações

Foi explicado que uma ação pode indicar a navegação para outro flow, inclusive em outra aplicação. A configuração pode incluir:

- aplicação;
- URL;
- dados a transferir;
- ação de retorno ou *callback*.

O exemplo conceitual apresentado foi: abrir um flow externo e, ao fechá-lo, refazer uma busca no flow de origem.

### 13.3 Retorno a um chamador

Quando uma tela foi aberta por outro programa ou outro flow, ela pode encerrar devolvendo dados ao chamador. A ação `finish` foi citada como palavra reservada associada ao comportamento de encerramento.

No exemplo:

- o usuário seleciona um registro;
- a tela é fechada;
- o registro selecionado é devolvido ao chamador.

### 13.4 Salto para passo específico

Foi mencionada a possibilidade de saltar para um passo específico, em vez de seguir necessariamente para o próximo passo sequencial.

### 13.5 Interrupção de saída em ações reservadas

Ações como `leave` e `finish` possuem comportamento predefinido. A arquitetura prevê uma maneira de impedir o fechamento caso a lógica de negócio determine que a saída não deve ocorrer.

## 18. Orquestração pelo Fuyi/Fuji

### 18.1 Papel do orquestrador

A pergunta levantada por um participante foi se cada flow seria uma aplicação exibida em `iframe`.

A resposta foi que não: a separação ocorre por **família de aplicação**, e não por flow individual. Foram citados, como exemplos:

- Neutron;
- aplicação para front-ends de tesouraria;
- aplicação para sinistros;
- aplicação para fornecedores;
- aplicação de emissão.

O menu do orquestrador aponta para a URL da aplicação correspondente. Ao selecionar uma opção, o `iframe` passa a conter a aplicação daquela família.

### 18.2 Neutron como aplicação carregada

Neutron foi descrito como uma aplicação pesada. Por esse motivo, permanece carregada e, quando o usuário navega para uma opção, a aplicação muda internamente para o flow ou tela correspondente, em vez de ser recarregada integralmente a cada interação.

### 18.3 Ocultação de cabeçalhos

Foi citado um parâmetro semelhante a `ShowHider`, usado para indicar que a aplicação está sendo executada dentro de Fuyi/Fuji. Nessa condição, a aplicação oculta elementos próprios de navegação e cabeçalho, exibindo apenas o conteúdo necessário no `iframe`.

Ao remover esse parâmetro em demonstração, a mesma aplicação passou a mostrar sua própria interface, incluindo cabeçalho e menu.

## 19. Comunicação entre Fuyi/Fuji e aplicações

A comunicação entre o orquestrador e as aplicações é feita por mensagens de janela. Foram citados mecanismos equivalentes a:

- `window.addEventListener`;
- `postMessage`;
- escuta de mensagens;
- envio de dados ao `iframe`.

### 19.1 Comunicação do orquestrador para a aplicação

A aplicação, como Neutron, mantém um listener para receber mensagens. Conforme o tipo da mensagem, executa comportamentos diferentes.

Foram citados tipos ou conceitos equivalentes a:

| Tipo citado | Comportamento explicado |
|---|---|
| `OK` | Não fazer nada específico |
| `Init` | Executar inicialização |
| `Navigate` | Navegar para outra tela ou flow |
| Dados associados | Receber parâmetros enviados por outra aplicação |

### 19.2 Comunicação da aplicação para o orquestrador

Quando uma aplicação deseja solicitar algo ao orquestrador — por exemplo, abrir outra aplicação em `iframe`, encerrar uma tela ou devolver dados — ela envia mensagem a Fuyi/Fuji.

Os exemplos explicados incluem:

- Neutron solicitando a abertura de tesouraria;
- tesouraria chamando uma rotina de Neutron para buscar um terceiro;
- aplicação fechando após a seleção de um registro;
- devolução dos dados selecionados ao chamador;
- comunicação de estado de prontidão.

Também foram mencionados dados de sessão para gestão de cabeçalhos, mas os detalhes não foram aprofundados.

## 20. Glossário, objetos e geração de esqueletos

### 20.1 Observer

Um participante perguntou se havia glossário para a nomenclatura. Foi indicada uma ferramenta chamada **Observer**.

Segundo a explicação:

- ela pode ser instalada;
- permite consultar tabelas e glossário;
- possui menos informação que outra ferramenta chamada “Nocherector” ou similar;
- parece estar disponível também a partir de um ambiente ou página de acesso aos entornos.

A transcrição não deixa claro se Observer tem apenas função de consulta ou outras capacidades adicionais.

### 20.2 Nocherector / ferramenta de modelo de dados

Foi explicado que uma ferramenta — registrada na transcrição como “nocherector” — contém maior quantidade de informação sobre:

- objetos;
- tabelas;
- termos;
- etiquetas;
- propriedades;
- famílias.

Ela pode gerar o esqueleto de componentes novos a partir de um conceito lógico, como terceiro ou informação geral.

O processo descrito é:

```text
Selecionar conceito lógico
↓
Gerar estrutura básica de componente
↓
Obter campos e tipos conhecidos
↓
Completar manualmente regras de visibilidade, edição, ajuda e listas de valores
```

A ferramenta conhece a estrutura básica e o tipo dos campos, como numérico, data ou texto, mas não consegue inferir regras de negócio específicas, tais como:

- visibilidade em determinada tela;
- possibilidade de edição;
- obrigatoriedade;
- existência de ajuda;
- necessidade de lista de valores.

Também foi dito que o uso pode exigir permissões e templates, obtidos por meio de uma área referida como “modelos de dados”.

### 20.3 Convenções de termos

A apresentação sugeriu que certos códigos de três letras correspondem a termos em inglês e podem derivar das primeiras consoantes ou de abreviações relacionadas ao nome em inglês.

Exemplos foram mencionados de maneira pouco nítida na transcrição. Assim, não é possível estabelecer uma regra formal e universal de formação dos códigos apenas com este material.

## 21. Caso concreto demonstrado: busca de declarações/apólices

### Contexto

Foi demonstrado um flow de busca e edição, com uma tela inicial que contém:

- formulário de busca;
- botão Buscar;
- lista de resultados inicialmente oculta;
- formulário de criação ou edição, também inicialmente não exibido.

### Funcionamento

1. o usuário informa um número de apólice;
2. a condição lógica habilita o botão Buscar;
3. a ação de busca é enviada ao serviço `Action`;
4. o dispatcher identifica o manager correspondente;
5. o manager recupera o DTO do formulário;
6. o DTO é mapeado para uma classe conhecida;
7. o manager chama um proxy;
8. o proxy faz uma chamada REST à API configurada no ambiente;
9. a API devolve registros associados à apólice;
10. o manager cria o DTO da lista;
11. o estado da lista é atualizado para válido;
12. a lista passa a ser exibida.

### Ações citadas na lista

| Ação | Papel descrito |
|---|---|
| Criar | Ação geral da lista |
| Consultar / query | Abrir visualização do registro |
| Modificar / update | Abrir edição do registro |
| Selecionar / finish | Selecionar registro e encerrar o flow, especialmente quando chamado por outro programa |

## 22. Perguntas e respostas relevantes

### Pergunta 1 — Cada flow é uma aplicação em `iframe`?

**Resposta:** não. O agrupamento é por família ou aplicação, como Neutron, tesouraria, sinistros, fornecedores e emissão. Cada aplicação pode conter diversos flows.

**O que isso esclarece:** o modelo não é uma arquitetura de microfrontends por flow individual. A separação apresentada está no nível de aplicações ou domínios maiores, coordenados pelo orquestrador.

---

### Pergunta 2 — Ainda há grande dependência de Neutron?

**Resposta:** sim. Foi afirmado que existe muito mais desenvolvimento em Neutron e que os novos front-ends ainda não cobrem tudo, pois levam tempo para serem construídos.

**O que isso esclarece:** a transformação para os novos front-ends está em andamento, e a convivência entre legado e novas aplicações é parte relevante do cenário atual.

---

### Pergunta 3 — Existe glossário para a nomenclatura utilizada?

**Resposta:** foi indicada a ferramenta Observer e também o acesso por ambientes, onde podem ser consultadas áreas de objetos, termos e famílias.

**O que isso esclarece:** há mecanismos de consulta para reduzir ambiguidade de códigos e termos, embora a cobertura e a qualidade da informação possam variar entre ferramentas.

---

### Pergunta 4 — Observer serve somente para consulta ou também gera componentes?

**Resposta:** a geração de esqueletos foi atribuída à ferramenta referida como Nocherector, não a Observer. Observer foi caracterizado principalmente como consulta de glossário e tabelas.

**O que isso esclarece:** consulta de metadados e geração de estrutura parecem ser capacidades separadas.

---

### Pergunta 5 — O que a ferramenta de geração produz?

**Resposta:** ela gera uma estrutura básica a partir do conceito lógico, com campos e tipos conhecidos. Depois, a equipe deve complementar regras de tela, visibilidade, edição, ajudas e listas de valores.

**O que isso esclarece:** a automação reduz o esforço inicial, mas não substitui a modelagem funcional específica de cada tela.

## 24. Riscos e desafios

### 24.1 Riscos explicitamente mencionados

- Duplicação de lógica em múltiplos managers ou pontos do legado pode elevar o custo e o risco de manutenção.
- A necessidade de aproveitar funcionalidades existentes em Neutron pode manter dependências técnicas durante a transição.
- A coexistência de formas diferentes de integração pode aumentar a heterogeneidade da solução.
- Permissões, templates e acesso a ferramentas de modelagem podem ser pré-requisitos operacionais para desenvolvimento.

### 24.2 Desafios derivados do contexto

> Os itens desta subseção são leituras analíticas, não afirmações literais dos participantes.

- **Governar a parametrização:** como fluxos, ações, componentes e transições dependem de dados em tabelas, alterações de configuração podem ter impacto funcional relevante e exigem controle de qualidade.
- **Manter consistência entre aplicações:** a comunicação por `postMessage` e o uso de `iframe` exigem contratos estáveis para mensagens, dados enviados, fechamento e retorno.
- **Reduzir dependência do legado:** a estratégia de reutilizar serviços de Neutron reduz retrabalho no curto prazo, mas pode prolongar o acoplamento entre o novo modelo e capacidades antigas.
- **Garantir rastreabilidade:** a divisão entre parametrização, dispatcher, manager, APIs e aplicações embarcadas pode dificultar diagnóstico se não houver observabilidade adequada.
- **Padronizar convenções:** a arquitetura depende de nomes, identificadores, ações reservadas e mapeamentos. Inconsistências nesses artefatos podem impedir a resolução correta dos métodos.

## 25. Transformações estruturais identificadas

> Esta seção apresenta interpretação sustentada pelo conjunto da reunião.

### 25.1 De telas codificadas para telas orientadas por metadados

A solução apresentada desloca parte importante da definição de interface para tabelas de parametrização. Isso permite alterar componentes, ações, colunas, etiquetas, visibilidade, estados e regras sem necessariamente modificar toda a estrutura do front-end.

### 25.2 De implementação isolada para execução padronizada de ações

O uso de `Action Resource`, dispatcher, `BaseManager` e convenções de nomes sugere uma tentativa de padronizar a execução da lógica de backend. O objetivo aparente é permitir que várias operações sejam tratadas dentro de um mesmo ciclo técnico.

### 25.3 De duplicação de lógica para serviços reutilizáveis

A recomendação de extrair funcionalidade comum para serviços evidencia uma preocupação explícita com manutenibilidade e com a redução de repetição observada no legado.

### 25.4 De aplicação única para ecossistema de aplicações orquestradas

O modelo de Fuyi/Fuji indica uma arquitetura em que aplicações diferentes coexistem, sendo incorporadas conforme a família funcional. O orquestrador atua como ponto de navegação e comunicação entre elas.

### 25.5 De migração integral para convivência progressiva

A estratégia não parece ser uma substituição imediata de Neutron. A organização mantém Neutron, reaproveita serviços existentes e cria novos front-ends gradualmente. Isso sugere uma modernização incremental.

## 27. Conclusões principais

A reunião apresentou uma arquitetura baseada em configuração de flows e componentes, com execução de ações delegada a managers Java resolvidos dinamicamente por um dispatcher.

A camada Java não devolve diretamente objetos de negócio pelo retorno dos métodos; ela utiliza um `Data Exchange` para transportar dados de entrada, resultados de saída, mensagens, estados de componentes e informações de navegação.

A solução suporta diferentes formas de integração: APIs para novas capacidades, injeção de serviços de backend Neutron para reaproveitamento do legado e conectores específicos para cenários como TronWeb.

Fuyi/Fuji exerce papel relevante de orquestrador entre aplicações, exibindo-as em `iframe` e permitindo comunicação bidirecional por mensagens de janela. O ambiente atual é híbrido: Neutron permanece central em várias áreas, enquanto novas aplicações são desenvolvidas gradualmente.

A principal diretriz técnica transmitida foi evitar repetição de lógica, aproveitar componentes e serviços comuns quando possível e usar a parametrização como mecanismo de definição e evolução dos fluxos funcionais.
