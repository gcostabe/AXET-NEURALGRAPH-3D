# Análise estruturada — Arquitetura de front-ends declarativos baseada em parametrização

> **Escopo e rastreabilidade:** esta análise foi produzida exclusivamente a partir da transcrição fornecida. Não há timestamps ou numeração de linhas disponíveis; por isso, a rastreabilidade é feita por tema e por trechos conceituais apresentados durante o treinamento.

## 1. Síntese executiva

A reunião foi um treinamento técnico sobre uma arquitetura de front-end declarativa, concebida para substituir ou reduzir a necessidade de construir telas e fluxos específicos manualmente para cada operação. O modelo anterior, referido como **Neutron**, parece ter exigido a montagem mais direta de telas, diretivas, views e fluxos, levando a soluções muito específicas e com menor potencial de reutilização.

A arquitetura apresentada desloca parte substancial da definição das interfaces e jornadas para a **parametrização persistida em tabelas de banco de dados**. Com isso, um fluxo é composto dinamicamente por passos, transições, elementos visuais, componentes funcionais, ações, regras de habilitação, dependências e classes Java responsáveis pelo processamento no servidor.

No cliente, a aplicação Angular concentra-se principalmente em componentes funcionais reutilizáveis — por exemplo, formulários associados a conceitos lógicos de negócio. No servidor, classes Java chamadas de **managers** são selecionadas dinamicamente conforme a parametrização para atender ações disparadas pela interface, como buscar, validar, carregar, cancelar ou modificar.

A apresentação também detalhou práticas de desenvolvimento: scripts SQL reentrantes por fluxo, geração inicial de componentes por uma ferramenta denominada **Gerator**, uso de bibliotecas comuns para formulários reativos e estilos centralizados, listas de valores com filtros reativos e publicação isolada de componentes em **Storybook**.

A mensagem central é uma transição de telas e fluxos montados pontualmente para uma plataforma de UI orientada por configuração, com componentes técnicos comuns, componentes funcionais reutilizáveis e comportamento governado por dados e regras de banco.

## 2. Contexto e antecedentes

### 2.1. Modelo anterior

O ponto de partida apresentado foi um modelo anterior associado ao nome **Neutron**. Nesse modelo:

- as telas eram desenvolvidas por meio de diretivas e views;
- os fluxos eram montados em um ambiente ou estágio citado como “stage”;
- cada operação tendia a receber uma implementação específica;
- havia menor reutilização entre operações.

A explicação sugere que esse padrão levava a uma construção mais individualizada: cada fluxo exigia desenvolvimento próprio de interface e comportamento, mesmo quando havia semelhanças funcionais com outras operações.

### 2.2. Motivação para a nova arquitetura

A nova arquitetura foi apresentada como resposta à necessidade de criar fluxos de forma mais padronizada e configurável.

A lógica descrita é:

```text
Fluxos e telas específicos por operação
↓
Baixa reutilização e maior esforço repetitivo
↓
Necessidade de componentes técnicos comuns
↓
Definição declarativa de telas, passos e ações
↓
Montagem dinâmica da interface a partir da parametrização
```

Essa relação de causa e efeito é uma reconstrução contextual da exposição. A transcrição afirma diretamente que, antes, “praticamente” cada operação era feita de forma específica e que não havia muito reaproveitamento; a conclusão de que a arquitetura busca reduzir repetição decorre do desenho apresentado.

### 2.3. Material de referência

Foi mencionada a existência de uma guia ampla, em inglês, que documentaria:

- os componentes disponíveis;
- a parametrização;
- a geração de componentes;
- o desenvolvimento associado à arquitetura.

A reunião, porém, foi assumidamente um resumo prático dessa documentação, não uma substituição integral dela.

## 3. Problemas identificados

## 3.1. Desenvolvimento excessivamente específico por operação

No modelo anterior, telas e fluxos eram construídos de maneira particular para cada operação. A consequência provável era a repetição de esforço para elementos conceitualmente parecidos.

A solução apresentada é organizar a interface em componentes técnicos e funcionais reutilizáveis, deixando a diferença entre fluxos concentrada, sempre que possível, na parametrização.

## 3.2. Risco de alterações manuais não serem promovidas entre ambientes

Foi enfatizado que o desenvolvedor deve trabalhar sobre o **script SQL**, e não realizar mudanças diretamente na base de dados.

A justificativa apresentada foi objetiva:

- alterações diretas no banco podem não existir quando a solução for promovida para outros ambientes;
- o script é o artefato que preserva e transporta a configuração;
- portanto, toda a configuração deve estar representada em SQL.

## 3.3. Repetição de valores técnicos na configuração

Foi apresentado um padrão inicial de scripts com muitos `INSERTs` individuais, repetindo informações como instalação, fluxo, companhia e dados comuns.

Posteriormente, foi citado o uso de um pacote ou abordagem chamada **DPL** — termo preservado conforme a transcrição — para declarar valores genéricos e encapsular inserções em procedimentos. A motivação é reduzir duplicidade de informações recorrentes nos scripts.

## 3.4. Necessidade de atualização coordenada de listas de valores

Há campos cujas listas de valores dependem de outros dados do fluxo, como ramo, tomador, grupo de apólice, acordo ou subacordo.

Sem um mecanismo coordenado, uma alteração em um campo poderia deixar outras listas com filtros desatualizados. A arquitetura apresentada usa serviços e assinaturas reativas para propagar as mudanças.

## 4. Solução apresentada

A solução é uma arquitetura de front-end composta por três camadas conceituais:

```text
Parametrização em banco de dados
↓
Componentes técnicos de interface
↓
Componentes funcionais Angular
↓
Ações processadas por managers Java
```

### 4.1. Parametrização

A parametrização define, entre outros aspectos:

- nome e identificador de fluxo;
- passos do fluxo;
- ordem e transições entre passos;
- regras de transição;
- elementos de cada tela;
- ordem visual dos elementos;
- componentes técnicos que exibem os elementos;
- componentes funcionais associados;
- botões e outras ações;
- dependências entre ações;
- classes Java responsáveis pelas ações;
- configuração funcional de campos;
- configuração técnica de listagens e outros componentes;
- comportamento de modais, agrupadores, menus laterais e abas.

### 4.2. Componentes técnicos

São componentes já desenvolvidos e reutilizáveis. Eles montam estruturas visuais e operacionais, como:

- fluxo;
- tela;
- barra de navegação;
- botões;
- acordeões;
- listagens;
- menus laterais;
- abas;
- agrupadores;
- modais ou pop-ups.

A parametrização determina quais desses componentes devem ser usados em cada contexto.

### 4.3. Componentes funcionais

São componentes Angular associados a conceitos lógicos de negócio, como:

- informação geral;
- agente;
- interveniente;
- outros objetos ou formulários referidos durante a demonstração.

A premissa apresentada é que um componente funcional não deve ser criado exclusivamente para um fluxo quando puder representar o conceito de negócio de forma mais abrangente. A parametrização define quais campos desse componente serão exibidos, editáveis, obrigatórios ou ocultos em cada tela.

### 4.4. Managers Java

Os managers são classes Java que respondem a ações geradas na interface.

A sequência descrita é:

```text
Usuário dispara uma ação na tela
↓
Ação é enviada a um serviço REST comum
↓
Serviço recebe dados do fluxo e a ação solicitada
↓
Parametrização identifica fluxo, passo, elemento e ação
↓
Tabela de dispatcher/manager aponta a classe Java aplicável
↓
Manager executa a lógica correspondente
```

A transcrição indica que as chamadas não são modeladas como um serviço REST específico para cada botão. Há um serviço comum de ação, e a parametrização determina qual manager será executado.

## 7. Scripts SQL e gestão da configuração

## 7.1. Script único, reentrante e por fluxo

Foi apresentada uma regra operacional clara:

- deve existir um único script por fluxo;
- o script deve ser reentrante;
- ao iniciar, ele limpa a configuração existente daquele fluxo;
- em seguida, reinsere toda a configuração;
- o script deve considerar as companhias aplicáveis.

O efeito observado na demonstração foi que a execução do script restaurou uma definição conhecida do fluxo após alguém ter alterado a configuração em uma base de desenvolvimento.

## 7.2. Trabalho orientado a script, não a alteração manual no banco

A orientação é que o desenvolvedor modifique o SQL versionado e execute esse script, evitando intervenções manuais persistentes na base.

A implicação prática é garantir que a mesma configuração possa ser promovida entre ambientes.

## 7.3. Estrutura do script

A estrutura mencionada inclui:

1. declaração de variáveis e dados genéricos;
2. limpeza dos registros relacionados ao fluxo;
3. inserção da parametrização;
4. repetição da inserção por companhia;
5. inserções nas tabelas de passos, transições, elementos, ações, dispatcher e demais estruturas relacionadas.

## 7.4. Evolução do padrão de scripts

Foram descritos dois estilos.

### Inserções explícitas por registro

O padrão inicial realizava um `INSERT` por registro e replicava registros da companhia inicial para as demais companhias encontradas em uma tabela de companhias.

### Procedimentos e variáveis genéricas

A abordagem posterior, associada a um pacote ou recurso chamado “DPL”, declara valores repetitivos uma única vez e usa procedimentos para inserir nas tabelas.

O benefício apresentado é evitar repetição contínua de dados genéricos, como:

- instalação;
- nome;
- fluxo;
- datas;
- companhia;
- valores recorrentes de auditoria.

## 9. Componentes funcionais

## 9.1. Princípio de reutilização

Um componente funcional representa um conceito lógico de negócio, e não necessariamente uma única tela ou fluxo.

Exemplo conceitual apresentado:

- um componente de informação geral pode conter todos os campos desse objeto;
- a parametrização decide quais campos devem aparecer em cada fluxo;
- um fluxo pode reutilizar o componente existente com uma configuração distinta;
- a criação de um novo componente deve ocorrer apenas quando não houver um componente adequado.

## 9.2. Geração inicial por Gerator

A ferramenta denominada **Gerator** é usada para gerar uma estrutura inicial de componente com base em objetos de negócio ou modelo de dados.

O resultado mencionado inclui, ao menos:

- HTML inicial;
- classe TypeScript;
- arquivo de configuração padrão;
- possivelmente arquivo de testes unitários.

A transcrição registra incerteza do próprio apresentador sobre todos os artefatos gerados. Portanto, não é possível afirmar com segurança que todos os arquivos listados sempre sejam produzidos pela ferramenta.

## 9.3. Ajustes manuais necessários

O código gerado não é a implementação final. O desenvolvedor precisa:

- reorganizar os campos no HTML;
- agrupá-los conforme a experiência desejada;
- trocar controles genéricos por componentes apropriados;
- criar listas de valores quando necessário;
- adicionar eventos;
- ajustar comportamento visual e funcional.

Um exemplo foi a substituição de um `input` de texto por um componente de lista de valores ou de ajuda.

## 10. Configuração de campos

Cada componente funcional possui uma configuração padrão para seus campos. Essa configuração pode determinar:

- visibilidade;
- obrigatoriedade;
- capacidade de edição;
- tamanho máximo;
- validadores;
- padrões de validação;
- outras propriedades citadas de forma parcial.

A precedência apresentada é:

```text
Configuração retornada pelo servidor
↓
Possível alteração no Java
↓
Configuração padrão local do componente
```

Ou seja:

1. o componente pode receber configuração a partir do banco de dados e do servidor;
2. a camada Java pode alterar a configuração segundo condições de negócio;
3. se determinada informação não vier do servidor, o componente utiliza sua configuração padrão local.

Essa configuração padrão deve ser explicitamente atribuída pelo desenvolvedor no construtor do componente.

## 10.1. Configurações múltiplas

Foi citado o caso em que o mesmo componente tem mais de uma configuração padrão. Por exemplo, um componente de interveniente pode exibir campos distintos conforme o tipo de interveniente, como tomador ou outro papel.

Nesse cenário, o componente identifica o tipo aplicável e troca a configuração que deve usar.

## 10.2. Validações

Foram mencionados:

- validadores predefinidos do Angular, como e-mail;
- validadores personalizados;
- `pattern`, entendido como expressão regular;
- regras de tamanho máximo.

A transcrição não detalha o conjunto completo de validações suportadas nem a forma de distribuição de validadores personalizados.

Na tabela de dispatcher, há uma marca que indica se o processamento deve continuar para outros elementos quando ocorrer erro em uma ação ou inicialização.

2. serviços específicos por conceito lógico;

4. mecanismos reativos para atualização após mudanças de dados dependentes.

## 14.2. Configuração de uma lista

A configuração pode incluir:

- identificador da lista;
- versão;
- coluna de código;
- coluna de descrição;
- filtros dinâmicos.

A lista pode exibir código e descrição, conforme a configuração atribuída ao componente.

## 14.3. Filtros

Os filtros podem depender de dados do fluxo, como:

- ramo;
- grupo de apólice;
- acordo;
- subacordo;
- tomador.

A apresentação destacou que alguns desses dados não pertencem ao componente que consome a lista. Por isso, eles são armazenados em um serviço comum ao módulo.

## 14.4. Uso de `BehaviourSubject`

Foi mencionado o uso de um objeto semelhante a `BehaviourSubject` para:

- armazenar dados usados nos filtros;
- emitir eventos quando esses dados mudam;
- permitir que listas dependentes se atualizem automaticamente.

O fluxo descrito é:

```text
Mudança de dado relevante, como ramo
↓
Serviço comum atualiza o objeto de dados
↓
Serviço emite evento
↓
Serviços específicos recebem a notificação
↓
Filtros das listas dependentes são atualizados
↓
Listas elegíveis são recarregadas
```

## 14.5. Limitação reconhecida

Nem todos os componentes de lista participam desse modelo dinâmico.

Foi indicado que o mecanismo detalhado funciona com um componente de typeahead dinâmico. Há outro typeahead, sem essa característica, que carrega suas listas no início e não as atualiza quando filtros mudam.

Essa é uma limitação funcional relevante explicitamente reconhecida.

## 15. Dados compartilhados entre elementos do fluxo

A tela trabalha com:

- objetos de dados para cada elemento;
- uma estrutura compartilhada chamada `flow data`.

O `flow data` permite que um componente grave informações para consumo por outro componente ou pela camada de servidor.

O padrão descrito é:

```text
Componente A obtém ou produz um valor
↓
Valor é salvo no flow data
↓
Componente B ou servidor recupera o valor posteriormente
```

O objetivo é compartilhar dados dentro do mesmo fluxo sem depender exclusivamente do DTO de um único elemento.

## 16. Registro de componentes

Para utilizar um componente funcional novo, não basta criá-lo.

O treinamento indicou ao menos dois registros necessários:

1. registro no módulo funcional;
2. registro no componente principal da aplicação.

No módulo funcional, o componente é incluído em estruturas como declarações e exports, para que fique disponível.

No componente principal, ele é associado a um alias por meio de um serviço ou mecanismo citado como `Component Factory Service`.

Esse alias é importante porque a parametrização de elementos de tela deve referenciar o alias registrado, e não necessariamente o nome técnico da classe Angular.

## 18. Demonstração prática de fluxo

Foi demonstrado um fluxo relacionado a “intervenimento” ou “interveniente” de “pólizas declarativas”. A terminologia exata pode ter sido afetada pelo reconhecimento de voz, mas o fluxo foi usado para ilustrar a parametrização.

## 18.1. Pesquisa e listagem

A tela inicial apresentava um filtro de busca em que apenas parte dos campos disponíveis no componente era exibida.

Após o preenchimento de condição necessária — no exemplo, o número de apólice — uma ação de busca era habilitada.

Depois da busca:

- o servidor era chamado;
- uma lista de resultados era carregada;
- ações de tabela e ações por registro eram disponibilizadas;
- estados de componentes podiam ser alterados.

## 18.2. Configuração restaurada por script

A base de desenvolvimento havia sido alterada por testes de outra pessoa. Ao executar novamente o script do fluxo:

- a configuração anterior foi apagada;
- a configuração definida no arquivo foi reinserida;
- a apresentação do resultado mudou.

Esse exemplo reforçou concretamente o papel reentrante do script SQL.

## 18.3. Reutilização do mesmo formulário com configurações diferentes

O mesmo componente funcional foi exibido em mais de um momento do fluxo, mas com comportamentos distintos.

Em uma tela, o formulário mostrava poucos campos com configuração padrão. Em outra, a parametrização do banco tornava campos adicionais visíveis e desabilitava determinado campo.

Isso exemplifica o modelo:

```text
Mesmo componente funcional
+
Configuração de tela distinta
=
Experiência visual e comportamental distinta
```

## 18.4. Listagens e ações

Foram demonstradas:

- ações de nível de tabela, como adicionar;
- ações de nível de linha, como consultar e modificar;
- ações condicionais que podem permanecer desabilitadas;
- mudança de passo dentro do mesmo fluxo após uma ação.

## 18.5. Labels dinâmicos

Foi demonstrado o recurso chamado `Dynamic Label`.

Ele é usado, por exemplo, para exibir um resumo de informações no cabeçalho de um acordeão depois que o usuário o fecha. Os dados podem incluir datas, como data de efeito e data de vencimento, com formatação configurada.

## 18.6. Modais

Também foi demonstrado um elemento configurado como modal ou pop-up.

A parametrização diferencia elementos mostrados diretamente na tela de elementos exibidos em uma janela modal disparada por ação.

## 20. Perguntas e respostas relevantes

## 20.1. Onde ficam os estilos de componentes novos?

### Pergunta

Foi perguntado se, ao criar um componente, os estilos ficam no arquivo específico do componente ou são obtidos de uma fonte centralizada.

### Resposta

Os estilos ficam centralizados em uma biblioteca de dependência, citada como `TronMaterialTeam`.

### O que isso esclarece

A arquitetura busca padronização visual transversal. Um componente novo deve usar o conjunto de estilos e controles fornecidos pela biblioteca comum, em vez de criar uma aparência isolada para cada front-end.

---

## 20.2. Há ação ou listener para mudanças de campo?

### Pergunta

Foi perguntado se existe uma ação ou função executada quando um campo é selecionado ou quando seu valor muda.

### Resposta

Foi citado um mecanismo semelhante a `subscribe to value changes`, fornecido pelo `Basic Component`, permitindo observar mudanças de valores.

### O que isso esclarece

Os componentes funcionais não dependem apenas de ações de botão parametrizadas. Eles podem reagir a eventos de alteração de formulário, inclusive para atualizar filtros de listas, realizar validações ou disparar ações.

## 22. Riscos e desafios

## 22.1. Riscos explicitamente evidenciados

- **Alterações manuais em banco:** podem não acompanhar a promoção entre ambientes.
- **Configuração modificada por outros usuários em desenvolvimento:** pode alterar o comportamento demonstrado e dificultar testes reprodutíveis.
- **Ambientes indisponíveis ou instáveis:** podem impedir demonstrações e validações.
- **Dependência de aliases corretos:** o componente precisa ser registrado e referenciado pelo alias correto na parametrização.
- **Complexidade de listas de valores:** filtros compartilhados e atualização reativa exigem coordenação entre serviços e componentes.
- **Componentes não dinâmicos:** certas listas podem não refletir mudanças posteriores de filtros.

## 22.2. Desafios derivados do contexto

> **Leitura analítica, não declaração literal dos participantes.**

A arquitetura centraliza flexibilidade em tabelas de configuração. Isso tende a reduzir desenvolvimento repetitivo, mas amplia a importância de:

- qualidade dos scripts SQL;
- rastreabilidade das alterações de parametrização;
- consistência entre aliases Angular, identificadores de banco e managers Java;
- testes de fluxo completos;
- conhecimento compartilhado sobre regras de precedência entre configuração padrão, banco e Java.

Também há um desafio de governança: uma parametrização muito poderosa pode produzir diferenças de comportamento difíceis de entender se não houver documentação, convenções e controles adequados.

## 23. Transformações estruturais identificadas

> **Esta seção é analítica e consolida implicações do modelo apresentado.**

## 23.1. De telas específicas para composição declarativa

A principal transformação é a mudança de um desenvolvimento de tela mais específico por operação para uma composição baseada em:

- componentes técnicos comuns;
- componentes funcionais reutilizáveis;
- regras e estruturas parametrizadas em banco.

## 23.2. De lógica de navegação codificada para navegação configurável

Passos, transições, condições e ordem de regras são representados em tabelas. Isso sugere uma separação entre:

- o motor de navegação genérico;
- a definição de cada jornada de negócio.

## 23.3. De formulários rígidos para formulários configuráveis

Um mesmo componente funcional pode aparecer de modos distintos conforme a configuração de:

- campos visíveis;
- campos obrigatórios;
- editabilidade;
- layout técnico;
- estado inicial.

## 23.4. De chamadas específicas para despacho orientado por ação

Em vez de uma rota de negócio por botão, a transcrição descreve um serviço REST comum que recebe ação e dados, localiza o manager aplicável pela parametrização e executa a lógica correspondente.

## 23.5. De valores estáticos para filtros reativos

As listas de valores podem responder a mudanças em dados compartilhados do fluxo. Isso aproxima o comportamento da interface de um modelo reativo, no qual alterações em dados como ramo atualizam as opções dependentes.

## 25. Conclusões

A reunião apresentou uma plataforma de front-end configurável, na qual a experiência do usuário é construída pela combinação de elementos persistidos em banco, bibliotecas técnicas comuns, componentes funcionais Angular e processamento Java selecionado por parametrização.

O modelo procura equilibrar reutilização e flexibilidade: componentes funcionais são construídos em torno de conceitos lógicos amplos, enquanto a parametrização define o recorte de campos, ações, estados e navegação necessário para cada fluxo.

O script SQL reentrante é um elemento central de confiabilidade operacional, pois transforma a configuração do banco em artefato reproduzível e promovível entre ambientes. A demonstração prática reforçou essa função ao restaurar a configuração de um fluxo que havia sido alterada em desenvolvimento.

A arquitetura também traz complexidade própria: é necessário coordenar registros de componentes, aliases, tabelas de configuração, actions, managers, configurações de campo, listas de valores e filtros reativos. Assim, a padronização não elimina a necessidade de engenharia; ela desloca parte importante da engenharia do código de telas específicas para o desenho consistente de componentes e parametrizações.
