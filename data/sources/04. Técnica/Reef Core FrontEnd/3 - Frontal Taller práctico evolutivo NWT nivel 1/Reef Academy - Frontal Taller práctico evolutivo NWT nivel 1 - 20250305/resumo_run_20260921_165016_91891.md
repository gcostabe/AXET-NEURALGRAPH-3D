# Análise técnica e funcional — treinamento de rastreabilidade, depuração e componentes do front-end Neutron

> **Escopo e rastreabilidade:** esta análise foi construída exclusivamente a partir da transcrição fornecida. ## 1. Síntese executiva

A sessão teve caráter predominantemente prático e de treinamento técnico. O foco foi demonstrar como rastrear uma operação da interface até sua execução no servidor e, quando aplicável, até o procedimento ou pacote de banco de dados referido na reunião como **PL**.

A explicação percorreu o fluxo completo de uma aplicação baseada em AngularJS, componentes e diretivas associados a Neutron/Gaia, serviços Java, interfaces e implementações, proxies para PL e banco Oracle. Foram demonstradas duas direções de investigação:

- **De cima para baixo:** partir de um botão, campo ou erro visual na tela e identificar controlador, serviço de front-end, URL, endpoint Java, implementação e chamada ao PL.
- **De baixo para cima:** partir de um pacote, método ou estrutura de banco e pesquisar possíveis consumidores na camada Java e, posteriormente, no front-end.

Além da rastreabilidade, a reunião apresentou mecanismos de depuração no navegador e no IntelliJ, comportamento de erros de validação, estrutura de componentes reutilizáveis — listas de valores, grids, modais, formulários e mensagens — e uma demonstração de uma área de testes com mocks.

A principal mensagem é que a investigação técnica depende de compreender convenções de nomenclatura, a separação entre componentes de interface, controladores e serviços, e as limitações práticas da rastreabilidade por busca textual. Embora exista documentação de requisitos e rastreabilidade em ferramentas mencionadas como Confluence e possivelmente Jira, o diagnóstico por código ainda é descrito como bastante manual em determinados cenários.

## 4. Fluxo técnico reconstruído: da tela até o PL

Abaixo está uma consolidação analítica do fluxo demonstrado. Não foi apresentado como um diagrama formal único, mas foi reconstruído a partir das etapas explicadas.

```text
Elemento da tela
  ↓
Atributo AngularJS, como ng-click
  ↓
Diretiva ou view
  ↓
Controller JavaScript
  ↓
Função acionada pelo botão/evento
  ↓
Montagem de DTO e chamada de serviço de front-end
  ↓
URL da requisição HTTP
  ↓
Interface Java / Controller Java
  ↓
Implementação Java
  ↓
Serviço ou proxy associado ao PL
  ↓
Pacote e método PL no banco
```

### 4.1. Partida pelo elemento visual

O procedimento começa pela inspeção da tela no navegador, normalmente com as ferramentas de desenvolvedor acessadas por F12. O instrutor mostra que um botão pode expor um atributo como `ng-click`, apontando para a função que será executada.

A função vinculada ao clique é o primeiro elemento de rastreabilidade. Entretanto, ela precisa ser interpretada dentro do componente correto, pois uma busca global pelo nome pode retornar múltiplas ocorrências.

### 4.2. Identificação da diretiva ou view

A tela pode ser composta por:

- uma **diretiva**, identificada por atributos associados a Neutron;
- uma **view**, cujo identificador costuma estar relacionado ao controller;
- estruturas de formulário, divisões HTML e componentes intermediários.

Quando o componente é uma diretiva, o caminho indicado foi:

1. inspecionar o atributo da diretiva;
2. copiar seu nome ou valor;
3. procurar esse elemento na aba de fontes;
4. localizar a definição da diretiva;
5. identificar o controller associado;
6. procurar nele a função acionada pelo botão.

Quando o componente é uma view, a orientação foi procurar o identificador da view no arquivo `states`, pois esse arquivo permite confirmar precisamente o controller correspondente. Foi ressaltado que o nome da view pode “normalmente” coincidir com o controller, mas a consulta ao `states` é considerada mais segura.

### 4.3. Localização do controller e do método

Após localizar o controller, a busca deve procurar a função apontada pelo `ng-click`. O treinamento alerta para uma limitação importante: em arquivos JavaScript concatenados, como um arquivo associado à pasta ou módulo “isu”, o mesmo nome de função pode aparecer em diversos controllers.

Por isso, a recomendação prática é:

- confirmar que se está no controller correto;
- usar contexto do arquivo e da estrutura visual;
- evitar assumir que a primeira ocorrência encontrada corresponde à operação investigada;
- usar breakpoint no início da função quando possível.

### 4.4. Depuração no navegador

Depois de inserir um breakpoint, o acionamento real do botão interrompe a execução no ponto escolhido. A partir desse momento, é possível:

- seguir linha a linha;
- entrar em métodos;
- verificar condições;
- observar a criação do DTO;
- inspecionar valores presentes no `scope`;
- identificar o momento em que a chamada HTTP é preparada;
- analisar a URL e os dados enviados.

O instrutor mostrou um caso em que a função verificava uma condição antes de decidir entre dois fluxos. A ferramenta permitia avaliar a expressão e confirmar que, naquele exemplo, a condição era falsa, conduzindo o fluxo pelo `else`.

### 4.5. Identificação da URL e chegada à camada Java

A chamada ao servidor foi descrita como uma composição de URL base e método. A URL pode ser observada:

- no código do serviço de front-end;
- na aba **Network** do navegador;
- na requisição efetivamente emitida.

Quando o objetivo é apenas chegar rapidamente ao PL, a orientação foi usar a aba Network, copiar a URL e pesquisá-la nos arquivos Java. Isso evita percorrer todo o fluxo JavaScript quando a intenção é identificar o endpoint e o processamento de servidor.

A URL leva a uma interface Java em uma camada referida como API. A partir dela, o IDE pode navegar para as implementações. Em alguns casos, foram encontradas duas implementações:

- uma implementação de mock, que retornava objeto vazio e não realizava processamento efetivo;
- uma implementação real, que deveria ser usada para continuar a investigação.

## 6. Convenções de nomenclatura e rastreabilidade

A nomenclatura é apresentada como um fator central para navegação entre camadas.

### 6.1. Conversão entre PL e Java

A explicação indica que:

- nomes em PL podem conter underscores;
- no Java, o underscore é removido e o caractere seguinte passa para maiúscula;
- o nome base tende a ser preservado;
- certos prefixos ligados à instalação podem desaparecer ou variar;
- a sigla ou prefixo territorial pode mudar conforme o país ou instalação.

Foi dado um exemplo hipotético de variação territorial, com menção a México e a um prefixo parecido com `MMX`. A transcrição não permite confirmar a convenção completa nem a lista de instalações válidas.

### 6.2. Limitações da busca por nome

A busca por nome não garante uma rastreabilidade completa porque:

- um método pode ter múltiplas ocorrências;
- uma interface pode ser importada e receber nomes diferentes quando injetada;
- um serviço pode ser referenciado por alias, como `servicio`;
- arquivos concatenados podem conter códigos de múltiplos controllers;
- podem existir componentes antigos não removidos;
- o mesmo pacote pode possuir interfaces e implementações em estruturas distintas.

A reunião recomenda não tratar a busca textual como prova definitiva da cadeia de chamadas.

## 7. Rastreamento inverso: do banco para a tela

Foi levantada uma pergunta sobre como partir de uma tabela Oracle ou de um componente inferior para descobrir quem o chama.

A resposta foi que esse caminho tende a gerar uma “árvore de possibilidades”. Ao subir da base para o front-end, pode haver múltiplos consumidores e não é possível saber automaticamente qual deles corresponde ao cenário específico sem investigação adicional.

O processo sugerido foi:

```text
Pacote/método PL
  ↓
Busca por interfaces e implementações Java
  ↓
Identificação de controladores ou serviços consumidores
  ↓
Busca por URL ou referência do serviço no front-end
  ↓
Localização de controllers, views ou diretivas que o acionam
```

### Limitação principal

O instrutor caracteriza a análise de impacto de alterações de banco como “bastante manual”. A busca por nome pode encontrar referências, mas não fornece automaticamente toda a árvore de dependências nem o fluxo funcional completo.

### Papel esperado da documentação

Foi mencionado que a documentação deveria oferecer rastreabilidade entre requisitos e elementos técnicos. As ferramentas citadas foram Confluence e, com menor segurança na própria fala, Jira.

A expectativa relatada é que, ao localizar um requisito na documentação, fosse possível ver elementos relacionados acima ou abaixo na cadeia. Contudo, a reunião não demonstrou essa documentação nem confirmou seu nível de atualização ou cobertura.

## 8. Tratamento de sessão, login e carregamento

No início, ocorreu uma falha associada à sessão ou à conexão com a base. A mensagem transcrita contém uma expressão semelhante a “Oracle não se pode inserir, null de la sesión”, cuja redação provavelmente foi afetada por reconhecimento de voz.

A interpretação sustentada pelo diálogo é:

- foi sugerido verificar logs dos servidores;

Posteriormente, foi demonstrado o uso de Single Sign-On.

### Single Sign-On

A explicação foi que o login realizado em Fuji também envolve o carregamento de Neutron. Uma janela de login pode ser bloqueada pelo navegador, impedindo o acesso posterior até que o bloqueio seja liberado e a página seja recarregada.

A justificativa apresentada para o pré-carregamento de Neutron foi de desempenho percebido: se Neutron não for carregado previamente, o usuário poderia esperar aproximadamente cinco segundos após acionar uma opção de menu até visualizar a tela. Esse número foi citado como exemplo durante a explicação e não como medição formal.

## 11. Erros, validação e associação com campos

Um trecho relevante da sessão demonstrou como erros de validação são devolvidos e apresentados na tela.

## 11.1. Erros controlados

Em um primeiro teste, ocorreu uma chamada que não gerou erro visível porque o erro era “controlado”. Em outro fluxo, ao acionar uma validação, múltiplos campos foram exibidos em vermelho.

Isso indica que a aplicação possui tratamento estruturado para erros de negócio ou validação, em vez de depender exclusivamente de erros técnicos não tratados.

## 11.2. Código de término

Na resposta de uma operação, foi mostrado um parâmetro chamado “terminação”. O valor `3` foi explicado como indicação de que houve erros.

A estrutura relatada foi aproximadamente:

```text
Resposta
  ├─ terminação geral
  └─ elementos detalhados
       ├─ terminação do elemento
       ├─ detalhe do erro
       └─ identificação da propriedade associada
```

Quando a terminação de um item também é `3`, o item contém detalhes de erro, incluindo mensagens originadas no banco.

## 11.3. `propertyName` e `Neutron field ID`

A associação entre erro e campo foi apresentada como baseada em um identificador de propriedade, citado como `propertyName`, e em uma diretiva ou atributo chamado `Neutron field ID`.

O mecanismo explicado é:

1. cada campo relevante recebe um identificador único;
2. a resposta de validação retorna a propriedade relacionada ao erro;
3. o front-end mapeia a propriedade para o campo;
4. o campo é destacado;
5. ao clicar na mensagem, o usuário pode ser levado ao input correspondente.

Esse fluxo foi demonstrado como uma convenção do front-end, não como comportamento automático de qualquer campo sem configuração.

## 12. Variáveis globais, sessão e testes de PL

A reunião abordou a dificuldade de testar chamadas ao PL de forma isolada.

Foi dito que, em determinados fluxos, o resultado de executar um teste diretamente no PL pode não reproduzir o comportamento da tela porque existem variáveis globais, estado de sessão ou dados anteriores necessários para a operação.

A explicação relatada é que:

- em novas interfaces, haveria uma tentativa de não depender de sessão;
- em Neutron, essa dependência teria sido parcialmente tratada ou simulada;
- possivelmente existe uma tabela que armazena informações equivalentes a variáveis globais;
- se o fluxo não foi percorrido antes, os dados necessários podem não estar carregados nessa estrutura.

A frase sobre a tabela foi apresentada com incerteza pelo próprio participante (“se não me equivoco”), portanto não deve ser tratada como especificação confirmada.

### Implicação prática

Para reproduzir um cenário de PL, a sugestão foi:

1. iniciar a operação pela tela;
2. interromper a execução antes da chamada;
3. capturar os parâmetros e o contexto;
4. usar essas informações para montar um teste;
5. reconhecer que a sessão pode ser parte indispensável da reprodução.

## 24. Limitações reconhecidas

1. **Busca por código não é rastreabilidade automática**
   - chamadas podem usar aliases;
   - métodos podem ter nomes repetidos;
   - arquivos concatenados dificultam a identificação;
   - referências podem não existir mais.

2. **Pode haver código não utilizado**
   - um serviço analisado aparentemente não era chamado de nenhum lugar;
   - o instrutor explicou que isso é comum após mudanças de fluxo ou tela, quando código antigo não é removido.

3. **Mocks não representam a implementação real**
   - alguns mocks retornam objetos vazios;
   - é necessário selecionar a implementação real para compreender o processamento.

4. **Testes diretos no PL podem falhar em reproduzir o comportamento da tela**
   - variáveis globais e estado de sessão podem estar ausentes;
   - a execução precisa ocorrer dentro do contexto adequado.

5. **Nem todos os detalhes de arquitetura foram demonstrados**
   - a sessão mostrou navegação e depuração, não uma especificação completa de infraestrutura, segurança ou implantação.

6. **Terminologia pode estar sujeita a erro de transcrição**
   - alguns nomes de componentes, métodos, pacotes e siglas aparecem deformados ou incompletos.

- perda de sessão e falha de carregamento de dados;

- inexistência de referências para código aparentemente legado;

## 25.2. Desafios derivados do contexto

> **Leitura analítica, não afirmação literal dos participantes.**

A combinação de AngularJS, arquivos concatenados, convenções de nomes entre Java e PL, dependência de sessão e componentes reutilizáveis sugere que a manutenção exige conhecimento transversal de front-end, backend e banco.

Também há indícios de que a qualidade da documentação de rastreabilidade é importante para reduzir investigação manual. Quando a documentação está incompleta ou a nomenclatura não é seguida, a análise de impacto pode se tornar lenta e sujeita a falsos positivos.

## 27. Transformações e direcionamentos identificados

> **Leitura analítica baseada no conjunto da reunião.**

### 27.1. Da navegação manual para investigação orientada por camadas

A sessão procura formar um método repetível de diagnóstico: não basta procurar uma string no código; é necessário entender a cadeia tela → controller → serviço → URL → Java → PL.

### 27.2. De telas isoladas para componentes configuráveis

A presença de botoneras configuráveis, listas de valores, grids, modais, calendários e formulários dinâmicos indica uma direção de reutilização por configuração. Em vez de cada tela recriar todos os elementos, ela declara propriedades e comportamentos sobre componentes comuns.

### 27.3. De validações apenas visuais para retorno estruturado de erro

O uso de código de terminação, detalhes de erro e associação por `propertyName`/`fieldId` mostra uma abordagem em que os erros retornados pelo backend podem ser mapeados de volta para elementos específicos da tela.

### 27.4. De testes isolados para testes contextualizados

A discussão sobre variáveis globais e sessão reforça que, em certos fluxos, testar apenas uma chamada PL pode não ser suficiente. O contexto operacional produzido pela própria tela pode ser parte essencial do cenário de teste.

## 28. Conclusão

A reunião documenta um treinamento de engenharia reversa e manutenção de aplicações com foco em depuração ponta a ponta. O método ensinado começa pela interface, identifica componentes AngularJS e Neutron, acompanha a construção de DTOs e chamadas HTTP, chega ao Java e termina na fronteira com o PL.

O conhecimento mais importante transmitido não é apenas o uso de uma ferramenta específica, mas a disciplina de investigação: validar o contexto antes de concluir, distinguir mocks de implementações reais, usar breakpoints em vez de depender apenas de busca textual, observar o payload efetivamente enviado e reconhecer que nomenclatura e documentação são auxiliares — não substitutos — da confirmação por execução.

A reunião também evidencia limites relevantes: rastreabilidade ascendente é manual, código antigo pode permanecer sem uso, a sessão pode alterar o resultado de testes e vários detalhes arquiteturais não podem ser deduzidos apenas a partir dos exemplos demonstrados.
