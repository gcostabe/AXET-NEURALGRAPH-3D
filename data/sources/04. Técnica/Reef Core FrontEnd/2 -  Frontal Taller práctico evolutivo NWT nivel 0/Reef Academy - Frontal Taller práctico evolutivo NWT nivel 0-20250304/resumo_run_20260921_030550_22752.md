## 1. Síntese executiva

A reunião combina duas frentes: a preparação prática de um ambiente local de desenvolvimento e uma apresentação técnica da arquitetura de uma aplicação chamada **Neutron**. O treinamento percorre o front-end legado em AngularJS, a camada Java intermediária e o backend que expõe funcionalidades da base de dados por meio de serviços.

O problema operacional imediato era fazer os módulos funcionarem localmente: o *Control Panel* já conseguia se conectar ao ambiente de integração, enquanto outro módulo apresentava falhas relacionadas a URLs incompatíveis entre versões, proxy, dependências Maven, configuração de JDK, perfis de execução, certificado e ausência do backend local.

A explicação arquitetural descreve o Neutron como uma solução composta por:

```text
Front-end cliente AngularJS
        ↓ REST
Front-end servidor Java (FE)
        ↓ HTTP Invoker
Backend Java (BE)
        ↓ PL Invoker
Camada de base de dados / PL
```

O front-end concentra grande parte da interação e da lógica de apresentação; a camada FE recebe chamadas REST, organiza ou encadeia chamadas ao BE e devolve respostas; o BE, na maior parte dos casos, atua como uma ponte estruturada para serviços da base de dados. A transcrição destaca padrões de nomenclatura, estruturas de objetos, componentes reutilizáveis, integração com Fuji e Gaia Frontend, além de riscos técnicos acumulados no código legado.

A sessão terminou antes de uma demonstração prática mais completa do backend. Foi informado que a continuação ocorreria no dia seguinte e que os vídeos seriam disponibilizados no SharePoint.

## 2. Contexto e antecedentes

O encontro aparenta ser um treinamento técnico prático para pessoas que precisam conhecer, executar e evoluir uma aplicação existente. A condução alterna entre:

- resolução de problemas de execução local;
- atualização de repositórios e branches;
- explicação da estrutura do código;
- demonstração da aplicação em funcionamento;
- descrição dos padrões adotados;
- discussão de limitações e débitos técnicos.

A aplicação abordada é chamada de **Neutron**. Ela utiliza um front-end baseado em **AngularJS**, componentes de uma biblioteca chamada na transcrição de **Gaia Frontend** e integra-se a algo chamado **Fuji**. Pelo contexto, Fuji parece ser um contêiner, portal ou camada de navegação que fornece elementos como usuário, companhia, menu e cabeçalho. A transcrição não permite afirmar com segurança a natureza exata de Fuji além desse papel de integração de interface e contexto.

A solução também possui camadas Java denominadas:

- **FE**: “frontal servidor”, recebendo solicitações originadas do front-end;
- **BE**: backend, que expõe principalmente operações da base de dados;
- **PL**: camada da base de dados acessada por meio de um mecanismo citado como **Gaia PL Invoker**;
- **SR / SSR**: camada de serviços na base de dados ou nos módulos de backend.

## 3. Problemas identificados

### 3.1. Incompatibilidade entre a versão local e o servidor de integração

Um dos problemas apresentados foi o erro ao realizar login ou chamar endpoints como `api`, `userInfo` e outros. A investigação levou à hipótese de que o código local estava em uma branch ou versão anterior, enquanto o servidor utilizado já tinha mudanças relacionadas a **Spring Boot** e à habilitação mencionada como “Gaia 2x enable”.

A consequência é que as URLs esperadas pelo front-end antigo não corresponderiam mais às URLs disponíveis no servidor atualizado.

**Relação de causa e efeito apresentada:**

```text
Servidor com alterações de Spring Boot / Gaia
        ↓
Mudanças na estrutura de URLs e APIs
        ↓
Front-end em branch anterior chama endpoints antigos
        ↓
Falhas no login e em chamadas como userInfo
        ↓
Necessidade de atualizar a branch local
```

A transcrição não detalha quais endpoints foram alterados nem o conteúdo exato das mudanças.

### 3.2. Dificuldade de executar a versão anterior localmente

Foi explicado que, naquela versão, a aplicação ainda não possuía a execução direta via Spring Boot. Por isso, seria necessário gerar o artefato WAR e implantá-lo em um Tomcat.

A configuração prática mencionada inclui:

- usar Tomcat 8;
- criar um arquivo aparentemente chamado `setenv.bat` dentro da pasta `bin`;
- configurar a rota do JDK;
- copiar o WAR gerado em `target` para `webapps`;
- remover o sufixo de versão do nome do WAR para evitar uma URL extensa de contexto;
- interromper instâncias de Tomcat iniciadas pelo Eclipse antes de tentar subir outra instância.

Há incerteza em alguns nomes de arquivos devido ao reconhecimento de voz. O nome “setm.gato” registrado na transcrição aparentemente se refere a `setenv.bat`, mas essa correção é contextual, não uma confirmação literal.

### 3.3. Restrições de proxy e atualização de repositórios

Durante o treinamento houve falhas de `fetch`, clonagem ou download de dependências. A explicação associou o problema a um possível proxy corporativo e à configuração do Git no ambiente virtual.

Foi mencionado um arquivo `gitconfig` no diretório do usuário, possivelmente contendo:

- configuração de proxy HTTP;
- usuário associado ao proxy;
- `credential helper`, com referência a algo parecido com `Wincred`.

A transcrição não fornece os valores, comandos ou configuração final aplicável. O ponto central é que o ambiente virtual possuía restrições que podiam impedir a atualização de repositórios e a obtenção de dependências.

### 3.4. Falha ao compilar por dependência ou arquivo bloqueado

Ao tentar compilar um módulo, foi relatado erro de não autorização pelo proxy durante o download de uma dependência e, em outro momento, falha na tentativa de remover um JAR.

A explicação não determina definitivamente a causa do bloqueio de remoção. Foram consideradas hipóteses como:

- arquivo aberto ou utilizado por algum processo;
- servidor ainda executando;
- conflito entre projetos distintos;
- comportamento do ambiente de desenvolvimento.

Não há evidência suficiente para fechar uma causa raiz.

### 3.5. Dependência do backend e certificados para execução completa

O front-end pôde ser iniciado, mas retornava erro HTTP 500 por não encontrar o backend esperado. A transcrição indica que o FE precisava apontar para um BE específico, possivelmente em outra porta, e que o acesso a um ambiente seguro demandaria certificado instalado na máquina virtual Java.

A relação apresentada é:

```text
FE iniciado localmente
        ↓
FE tenta chamar o endpoint do BE
        ↓
BE não está disponível no endereço configurado
        ↓
Erro HTTP 500 / máquina não encontrada
```

A configuração de certificado foi citada como necessária em algum cenário, mas não ficou claro se seria obrigatória para execução local, para uso em ambiente virtual ou apenas para acesso à integração.

## 4. Solução e direcionamento apresentados

O direcionamento técnico principal foi alinhar o ambiente local à branch atual e configurar corretamente a execução dos módulos FE e BE.

### 4.1. Para versões mais antigas

A orientação foi utilizar Tomcat e implantar o WAR gerado:

```text
Código compilado
        ↓
Artefato WAR em target
        ↓
Cópia para Tomcat/webapps
        ↓
Configuração de JDK e ambiente
        ↓
Inicialização no Tomcat
```

### 4.2. Para a release mais recente

Foi informado que a release em curso, identificada na transcrição como **2502**, já permitiria iniciar a aplicação diretamente com Spring Boot, dispensando o Tomcat externo.

A reunião associa essa evolução a uma atualização ocorrida “desde o início de fevereiro”, mas não é possível estabelecer o ano absoluto apenas pela transcrição.

### 4.3. Para a configuração local

Foi explicado que os perfis de execução distinguem ambientes e podem configurar:

- segurança;
- endpoint do backend;
- conexões com base de dados;
- comportamento de execução local.

No FE, a configuração local parece exigir sobretudo o endpoint do BE. No BE, os perfis são mais sensíveis porque definem as conexões com a base de dados.

A transcrição menciona um perfil similar a `M local` e arquivos `POM` dentro de uma área de configuração. Entretanto, não permite estabelecer os nomes exatos de todos os perfis nem afirmar qual deveria ser usado em cada máquina.

## 5. Arquitetura lógica reconstruída

> **Nota:** o diagrama abaixo é uma consolidação analítica baseada na explicação verbal; não foi apresentado literalmente dessa forma.

```text
Usuário
   ↓
Fuji / Portal ou contêiner de interface
   ↓
Neutron — Front-end cliente AngularJS
   ├── Estados, controladores e diretivas
   ├── Formulários, grids e listas de valores
   ├── Serviços Angular
   ├── Gestão de sessão, erros e navegação
   └── Comunicação com Fuji
   ↓ REST
FE — Front-end servidor Java
   ├── APIs REST
   ├── Interfaces e implementações
   ├── DTOs
   └── Orquestração de chamadas ao BE
   ↓ HTTP Invoker
BE — Backend Java
   ├── Serviços Gaia
   ├── Interfaces, implementações e proxies
   └── Exposição de operações da base
   ↓ Gaia PL Invoker
PL / Serviços de Base de Dados
   ├── Funções e procedimentos expostos
   ├── Objetos de negócio e processo
   └── Retorno de dados e terminações
```

A mensagem arquitetural central é que o front-end não acessa diretamente a base de dados. Ele chama serviços REST do FE, que por sua vez utiliza serviços BE. O BE chama a camada de base de dados por contratos e proxies específicos.

## 6. Front-end cliente: estrutura e funcionamento

### 6.1. Localização e organização do código

A transcrição localiza o código front-end em uma estrutura semelhante a:

```text
JS / web / src / main / front
```

Foram mencionadas pastas como:

- `commons`;
- `ISU`;
- `LSS`;
- `Nibisu`;
- `THP`;
- `TSI`.

Essas pastas foram descritas como “verticais” ou áreas funcionais diferentes. A reunião associa algumas delas a domínios como:

- emissão;
- sinistros;
- tesouraria;
- terceiros.

A transcrição contém trechos pouco claros sobre o mapeamento integral de cada sigla para seu domínio. Portanto, não é possível afirmar com precisão a responsabilidade de todas as pastas.

### 6.2. Aplicação de página única

O Neutron foi descrito como uma **Single Page Application**. O arquivo `index` carrega:

- JavaScript;
- HTML;
- CSS;
- dependências;
- módulos Angular;
- bibliotecas comuns.

O conteúdo funcional não fica diretamente no `index`; ele possui um contêiner, mencionado como `WebView`, no qual os fluxos são inseridos dinamicamente.

Também foi citado um componente associado a alertas ou pop-ups de erro, chamado de forma semelhante a “Neutron Alerts”.

### 6.3. Pré-carregamento de módulos grandes

Os verticais de emissão e sinistros foram citados como módulos grandes. Em vez de carregar seus arquivos apenas no momento de acesso ao menu, eles são pré-carregados no início.

O motivo apresentado foi reduzir a espera percebida pelo usuário ao entrar nesses módulos.

```text
Carregamento sob demanda tardio
        ↓
Demora ao acessar emissão ou sinistros
        ↓
Pré-carregamento na entrada da aplicação
        ↓
Redução da espera ao navegar para esses módulos
```

### 6.4. Estado inicial: Neutron

O estado inicial da aplicação é chamado de **Neutron**. O estado é configurado por meio de `ui-router`, segundo a transcrição.

Quando o usuário entra pela integração com Fuji:

- Fuji já fornece elementos como usuário, menu e companhia;
- a interface do Neutron não precisa mostrar novamente sua própria estrutura de cabeçalho e menu;
- o fluxo é carregado em uma estrutura descrita como `Uniframe`.

Quando a aplicação é acessada diretamente, fora de Fuji, o Neutron precisa exibir os elementos de interface e contexto que Fuji normalmente forneceria.

## 7. Integração com Fuji e Uniframe

Fuji foi descrito como uma camada que já carrega dados e elementos de experiência do usuário, incluindo:

- usuário;
- companhia;
- menu;
- cabeçalho;
- possivelmente idioma.

Quando o Neutron roda dentro de Fuji, sua própria estrutura de cabeçalho, navegação e menu pode ser ocultada. Nessa condição, o Neutron renderiza principalmente o fluxo solicitado.

O **Uniframe** foi apresentado como uma janela ou camada sobreposta usada para abrir fluxos sem perder o estado do fluxo atual. Ele é utilizado, por exemplo, para:

- abrir fluxos externos, como GDC;
- abrir outro fluxo do próprio Neutron;
- retornar ao ponto original após uma seleção.

O caso demonstrado envolve emissão de orçamento e seleção de terceiro:

```text
Fluxo de emissão de orçamento
        ↓
Necessidade de selecionar um terceiro
        ↓
Abertura de rotina de terceiros em Uniframe
        ↓
Seleção de um DNI
        ↓
Fechamento do Uniframe
        ↓
Retorno ao fluxo original com o valor selecionado
```

A implementação desse comportamento foi associada ao serviço de **Parallel Navigation**.

O nome foi reconhecido de forma incerta como “Ocheformed Service”. Pelo contexto, é um serviço utilitário muito usado para:

- atualizar dados de um objeto sem perder sua referência;
- limpar objetos;
- verificar terminações;
- controlar formulários;
- definir propriedades como visível, modificável e obrigatório.

O comportamento destacado foi o uso de algo chamado `AsyncValues`, que atualiza os dados de um objeto sem trocar sua referência.

A estrutura é documentada nos próprios estados para facilitar a leitura, mesmo quando as views poderiam ser definidas diretamente no HTML.

## 12. Modelo de comunicação entre controladores e diretivas

### 12.1. Uso de objetos de configuração

A orientação técnica é evitar acesso direto entre *scopes* de diferentes níveis. Em vez disso, o controlador pai cria objetos de configuração — chamados na transcrição de algo semelhante a `confData` — e passa referências explicitamente para os filhos.

A lógica é:

```text
Controlador pai
   ↓ cria objeto de configuração
Controlador ou diretiva filha
   ↓ recebe apenas dados e funções necessários
Componente interno
```

A justificativa é manter visíveis as dependências do componente, evitando que um componente inferior busque dados arbitrariamente em ancestrais distantes.

### 12.2. Diretivas com escopo isolado

As diretivas possuem escopo isolado e recebem explicitamente os parâmetros necessários. Isso impede que tenham acesso indiscriminado ao contexto externo.

A diretiva:

1. é renderizada;
2. emite um evento indicando que está pronta;
3. disponibiliza sua função de pré-carga ou inicialização ao pai;
4. é inicializada pelo pai no momento adequado.

### 12.3. Organização interna de controladores

Foi apresentada uma ordem recorrente dentro dos controladores:

1. constantes;
2. funções locais;
3. funções expostas ao `$scope`;
4. objetos de configuração;
5. pré-carga;
6. eventos de tela, como clique, `blur` ou alteração de dados;
7. lógica de processo;
8. chamadas de inicialização.

A transcrição apresenta essa estrutura como padrão desejado, não como garantia de que todo o código existente esteja organizado dessa maneira.

## 13. Serviços do front-end e chamadas REST

Os serviços front-end são responsáveis principalmente por realizar solicitações ao servidor. O fluxo esperado é:

```text
Controlador ou diretiva
        ↓
Serviço Angular terminado em SRV
        ↓
Montagem ou recebimento do objeto/DTO
        ↓
Criação de promessa
        ↓
Chamada REST
        ↓
Verificação da terminação retornada
        ↓
Atualização do objeto com AsyncValues
        ↓
Resolução ou rejeição da promessa
```

Quando a chamada precisa de dados específicos que não formam um objeto de domínio existente, o serviço monta um DTO apropriado.

A camada também verifica se a resposta terminou corretamente. Caso contrário, rejeita a promessa ou trata o erro conforme o fluxo.

## 14. Objetos, terminações e conversão entre camadas

A explicação dos objetos foi um dos pontos centrais do treinamento.

### 14.1. Objetos simples e objetos de processo

Foram mencionados, de forma geral:

| Tipo | Papel descrito |
|---|---|
| Objeto simples | contém dados de negócio, como textos, números e datas |
| Objeto de processo | contém informação de processamento, estado, erros, configuração de campos e terminação |
| Objeto P | combina objeto de negócio com objeto de processo |
| Lista com terminação | contém lista de objetos e o resultado da operação |
| Objeto complexo | agrega outros objetos, listas e dados simples |
| DTO | estrutura específica para comunicação entre front-end e servidor |

A terminação informa se uma operação foi concluída corretamente ou não. Esse conceito é usado em múltiplas camadas para determinar se a resposta pode continuar sendo processada, se deve gerar alerta ou se precisa sofrer tratamento específico.

### 14.2. Configuração de campos

O objeto de processo pode trazer a configuração dos campos, incluindo:

- visibilidade;
- possibilidade de alteração;
- obrigatoriedade;
- validações;
- campos de ajuda;
- outros atributos de apresentação.

A base de dados aparentemente envia essa configuração em uma estrutura de lista. Ao chegar ao front-end, serializadores podem convertê-la em um mapa indexado pelo nome do atributo, facilitando a consulta direta da configuração de cada campo.

### 14.3. Transformações de nomes e estruturas

A transcrição destaca que um mesmo conceito pode ter nomes ou estruturas diferentes conforme a camada:

```text
Base de dados / Oracle
        ↓
Java
        ↓
Front-end AngularJS
```

Foram citadas transformações como:

- `snake_case` para `camelCase`;
- troca de nomes de determinadas propriedades;
- transformação de arrays em objetos;
- conversão de um objeto de processo para uma estrutura identificada como `CNF` no front-end;
- exclusão de propriedades que não devem viajar até a base de dados.

A apresentação reforça que os serializadores fazem parte importante desse mapeamento. Porém, não detalha integralmente todas as regras de conversão.

---

## 15. Camada FE: front-end servidor Java

A camada FE recebe as chamadas REST originadas no front-end AngularJS e orquestra chamadas ao BE.

### 15.1. Responsabilidade

O FE foi descrito como uma camada que:

- recebe dados da interface;
- expõe URLs REST;
- organiza chamadas ao backend;
- encadeia chamadas quando necessário;
- devolve os dados ao front-end.

A apresentação sustenta que o “grosso” da lógica fica no front-end ou no BE/PL, e que o FE normalmente possui pouca lógica própria. Sua função predominante é orquestrar.

### 15.2. Estrutura de artefatos

Para desenvolver um serviço FE, podem existir de dois a quatro artefatos, dependendo dos dados de entrada e saída:

- interface;
- implementação;
- DTOs de entrada;
- DTOs de saída.

A interface é situada em uma área de API e define, entre outros aspectos:

- URL;
- método HTTP, frequentemente `POST`;
- assinatura do método;
- contratos de dados.

A implementação fica na área de implementação, normalmente com sufixo `IMPL`, e chama o BE.

### 15.3. Mocks

Foram mencionadas implementações adicionais identificadas como `MOCK-IMPL`, com uma anotação distinta, aparentemente `Mock Controller` em vez de `Real Controller`.

A finalidade original seria permitir executar a aplicação sem serviços BE ou PL reais. Contudo, a apresentadora informou acreditar que esse recurso praticamente não é usado e que muitas implementações existem apenas para evitar erros.

Essa é uma observação importante: a reunião não confirma que o mecanismo de mocks esteja em funcionamento, mantido ou recomendado para novos desenvolvimentos.

### 15.4. Orquestração e tratamento de erro

O FE pode:

- chamar um serviço BE;
- avaliar a terminação retornada;
- realizar outra chamada condicional;
- montar um DTO de saída;
- adaptar mensagens de erro.

Foi dado o exemplo de um serviço que, diante de determinada resposta, filtra o erro técnico e retorna uma mensagem mais adequada, como “não foram encontrados dados”.

---

## 16. Camada BE: backend Java

### 16.1. Responsabilidade predominante

O BE foi apresentado como ainda mais simples que o FE em muitos casos. Sua função principal é expor, em Java, operações existentes na base de dados.

O padrão mais comum é:

```text
Interface BE
        ↓
Implementação BE
        ↓
Proxy de comunicação
        ↓
Gaia PL Invoker
        ↓
Função ou serviço PL
```

A apresentação estima que “90%” dos serviços BE seguem esse padrão de receber parâmetros e repassá-los ao proxy. Esse número é uma afirmação do treinamento, não uma medição auditada.

### 16.2. Interfaces, implementações e proxy

O BE possui:

- uma interface de serviço;
- uma implementação;
- uma interface de comunicação com a base;
- um proxy que usa o PL Invoker.

A interface de serviço é identificada por uma anotação chamada `Gaia Service`. A implementação utiliza uma anotação de serviço correspondente e chama o proxy.

O proxy precisa respeitar estritamente:

- nome;
- ordem dos parâmetros;
- assinatura;
- nomenclatura compatível com a função PL exposta.

### 16.3. Nomenclatura para PL

A apresentação ensinou uma regra para localizar a função PL a partir da nomenclatura Java:

1. partir do nome do serviço;
2. remover o prefixo de interface;
3. converter maiúsculas em palavras separadas por `_`;
4. acrescentar um prefixo ao método, citado como `F_`.

Essa regra foi apresentada como um padrão prático para identificar o PL chamado. Não há garantia explícita de que seja universal para todos os artefatos históricos.

### 16.4. Serviços REST e SOAP no BE

Foi explicado que o BE já expôs serviços REST e SOAP diretamente para consumidores externos. Isso teria sido mais comum quando o Neutron era o principal consumidor e ainda não existiam APIs dedicadas.

O direcionamento atual informado é diferente:

```text
Necessidade de expor um serviço externo
        ↓
Não criar diretamente REST/SOAP no BE
        ↓
Expor por meio das APIs
```

Isso sugere uma direção de centralização da exposição externa em uma camada de APIs. A transcrição não descreve essa camada de APIs em profundidade.

## 17. Modelo de integração consolidado

```text
[AngularJS: controlador ou diretiva]
             ↓
[Serviço Angular / SRV]
             ↓ REST
[FE: interface Controller]
             ↓
[FE: implementação]
             ↓ HTTP Invoker
[BE: interface Gaia Service]
             ↓
[BE: implementação]
             ↓
[BE: Proxy]
             ↓ PL Invoker
[PL / Base de dados]
```

### Princípios explicitamente apresentados

- O front-end deve chamar serviços Angular, não construir toda a lógica de comunicação diretamente em controladores.
- O FE expõe REST para o front-end.
- O FE utiliza HTTP Invoker para se comunicar com o BE.
- O BE utiliza uma camada de proxy para invocar funcionalidades de base de dados.
- A terminação retornada deve ser avaliada em cada etapa necessária.
- DTOs devem ser usados quando a chamada exige combinação específica de parâmetros.
- O uso de referências e objetos de configuração é preferível a navegação indiscriminada entre scopes.

## 18. Problemas de arquitetura e código reconhecidos

### 18.1. Uso excessivo de eventos

A reunião alertou que eventos Angular facilitam a comunicação porque evitam passar parâmetros de componente em componente. Contudo, isso prejudica rastreabilidade e depuração.

Os problemas identificados são:

- dificuldade para descobrir quem consome um evento;
- possibilidade de múltiplos consumidores;
- dificuldade de rastrear o fluxo de execução;
- nomes genéricos que tornam buscas pouco confiáveis.

### 18.2. Registro de listeners no rootScope

Foi apresentado um problema concreto: listeners registrados no `rootScope` podem persistir porque esse escopo não é destruído ao sair de uma operação.

O efeito pode ser:

```text
Entrada repetida na mesma operação
        ↓
Registro repetido de listeners
        ↓
Um único evento é disparado
        ↓
Várias execuções idênticas ocorrem
```

A apresentadora afirmou que já houve situações com diversos listeners iguais, fazendo uma ação ser executada várias vezes. A conclusão foi taxativa: esse padrão “não pode ser feito”.

### 18.3. Uso de `$parent`

Também foi desaconselhado o acesso repetido via `$parent`, pois isso cria dependências implícitas e obriga um componente filho a pressupor a estrutura do pai.

A recomendação é usar objetos de configuração passados explicitamente.

### 18.4. Objetos genéricos como “saco sem fundo”

Foram mencionados objetos como `origin`, `scope`, `flow` e `data`, usados em alguns pontos como recipientes genéricos para diversos parâmetros.

O risco descrito é que esses objetos permitam que qualquer parte do fluxo acesse tudo, tornando as dependências difusas e dificultando manutenção, rastreamento e entendimento do código.

### 18.5. Duplicidades e inconsistências históricas

A apresentação reconhece:

- botoneiras duplicadas;
- nomenclaturas que não correspondem ao tipo real;
- views implementadas como diretivas;
- padrões teóricos que não foram seguidos em todos os pontos;
- fluxos especiais que adotam arquitetura intermediária entre o legado e novos front-ends.

### 19.1. Emissão de apólice

## 20. Configuração de execução local: FE e BE

### 20.1. FE

Para o FE, foram citadas configurações de JVM como:

- *time zone*;
- encoding;
- porta;
- *context path*;
- configuração de debug, opcional;
- localização do Java/JRE.

A apresentação indicou que, se a porta não for especificada, provavelmente seria usada a 8080, mas isso foi dito com incerteza. Portanto, não deve ser tratado como regra confirmada.

Também foi mencionado que o FE poderia estar configurado, por exemplo, para uma porta 8081, a depender do perfil e do ambiente.

### 20.2. BE

No BE, a configuração de perfil é mais relevante porque inclui conexão com base de dados. Durante o treinamento, foi observado que determinado perfil apontava para um ambiente associado a JBoss/JNDI e, por isso, não serviria para execução local.

A orientação foi procurar um perfil local compatível com a base de dados necessária, mas a transcrição não confirma qual perfil foi efetivamente escolhido nem se a execução foi concluída com sucesso.

### 20.3. Certificados

Foi levantada a necessidade de adicionar certificado à JVM ou máquina para acessar um backend em ambiente seguro. Não ficou definido:

- qual certificado seria utilizado;
- como instalá-lo;
- se seria exigido em todos os ambientes;
- se a necessidade se aplicava ao ambiente virtual ou à máquina local.

## 21. Perguntas e respostas relevantes

### Pergunta: o que havia sido compilado, backend ou front-end?

**Resposta:** houve a necessidade de identificar se o artefato compilado era BE ou FE, pois o procedimento de execução e publicação dependeria disso.

**O que esclarece:** a solução possui módulos separados e o processo de inicialização não é uniforme entre eles.

---

### Pergunta: por que não era possível iniciar diretamente pela IDE?

**Resposta:** naquela versão ainda não havia Spring Boot, então seria necessário levar o WAR para Tomcat. Foi mencionado que isso mudaria na release mais nova.

**O que esclarece:** coexistem modelos de execução de versões diferentes: implantação em Tomcat para versões antigas e inicialização direta para versões atualizadas.

---

### Pergunta: por que o login e as chamadas de usuário falhavam?

**Resposta:** a hipótese principal foi diferença entre a branch local e o servidor, que já tinha alterações relacionadas a Spring Boot/Gaia. As URLs e APIs teriam mudado.

**O que esclarece:** problemas de integração não eram tratados como mero erro de login, mas como possível incompatibilidade de contrato entre versões.

---

### Pergunta: por que o `fetch` ou download não funcionava no ambiente virtual?

**Resposta:** foi considerada a ausência de configuração de proxy no Git, especialmente no `gitconfig` do usuário.

**O que esclarece:** o ambiente de desenvolvimento possui restrições de rede que exigem configuração explícita.

---

### Pergunta: o front-end pode ser executado sem alterações adicionais?

**Resposta:** o FE pode ser iniciado, mas ainda precisa alcançar um BE válido. Caso a configuração aponte para um BE inexistente, ocorrerão erros.

**O que esclarece:** iniciar o processo Java não equivale a disponibilizar uma aplicação funcional fim a fim.

---

### Pergunta: por que determinados perfis não servem para execução local?

**Resposta:** alguns perfis foram preparados para ambientes com JBoss e JNDI, não contendo a configuração direta de banco necessária para execução local.

**O que esclarece:** perfil de build/executação é parte essencial da arquitetura operacional, e não uma mera escolha de conveniência.

---

### Pergunta: qual a diferença entre o fluxo de apólice e o de orçamento?

**Resposta:** embora visualmente parecidos, são fluxos diferentes, com telas, pré-cargas e serviços próprios. O fluxo de emissão de apólice possui particularidades arquiteturais.

**O que esclarece:** similaridade visual não deve ser usada para deduzir compartilhamento técnico integral.

---

### Pergunta: por que evitar eventos e `$parent`?

**Resposta:** ambos podem simplificar a implementação no curto prazo, mas reduzem rastreabilidade e criam dependências implícitas. Eventos no `rootScope` podem ainda se acumular e provocar execuções repetidas.

**O que esclarece:** o treinamento prioriza explicitude de dependências, rastreabilidade e controle de ciclo de vida.

---

## 23. Riscos e desafios

### 23.1. Riscos explicitamente mencionados

| Risco | Consequência indicada |
|---|---|
| Branch desatualizada contra servidor atualizado | URLs e APIs incompatíveis |
| Proxy não configurado | impossibilidade de `fetch`, clone ou download de dependências |
| Perfil inadequado | conexão incorreta com banco ou dependência de JNDI/JBoss |
| FE sem BE acessível | falhas HTTP e aplicação incompleta |
| Certificado ausente em ambiente seguro | indisponibilidade de comunicação com backend |
| Eventos no `rootScope` acumulados | múltiplas execuções da mesma ação |
| Uso excessivo de eventos genéricos | dificuldade de depuração e rastreio |
| Uso recorrente de `$parent` | acoplamento e dependências implícitas |
| Objetos genéricos de contexto | perda de clareza sobre dados e responsabilidades |

### 23.2. Desafios derivados do contexto

> **Leitura analítica:** estes pontos decorrem da reunião, mas não foram todos declarados literalmente como riscos formais.

- A coexistência de arquitetura antiga baseada em Tomcat e arquitetura mais recente baseada em Spring Boot tende a aumentar a complexidade de onboarding e suporte.
- A transformação de objetos entre base, Java e Angular introduz risco de inconsistência de contratos, especialmente quando há serializadores e mudanças de nomes.
- A arquitetura possui uma cadeia longa de camadas. Embora isso separe responsabilidades, também dificulta localizar rapidamente a origem de uma falha.
- O forte uso de convenções de nomenclatura pode acelerar a navegação no código, mas inconsistências históricas reduzem sua confiabilidade.
- A dependência de configuração de ambiente e rede indica que a reprodutibilidade local exige documentação operacional precisa.

## 24. Transformações observadas

### 24.1. De implantação em Tomcat para execução com Spring Boot

A reunião descreve uma evolução de modelo operacional:

```text
Versão anterior
WAR + Tomcat externo
        ↓
Versão mais recente
Inicialização direta com Spring Boot
```

Essa mudança parece buscar simplificar execução e desenvolvimento local. A transcrição não detalha se a migração está concluída para todos os módulos.

### 24.2. De exposição direta no BE para APIs

Foi apresentado um direcionamento de não criar mais serviços REST ou SOAP diretamente no BE para consumidores externos. O objetivo aparente é concentrar novas exposições na camada de APIs.

> **Leitura analítica:** isso sugere uma tentativa de separar serviços internos de acesso à base de dados da camada de integração externa.

### 24.3. De componentes ad hoc para componentes reutilizáveis

A existência de grids, botoneiras, listas de valores e diretivas reutilizáveis aponta para uma tentativa de padronizar a interface e reduzir duplicidade.

Ao mesmo tempo, a própria reunião reconhece que existem duplicidades e desvios históricos, o que indica uma padronização incompleta.

### 24.4. De comunicação implícita para dependências explícitas

A recomendação de substituir acessos por `$parent` e uso indiscriminado de eventos por objetos `confData` expressa uma direção arquitetural clara:

```text
Acesso implícito e difícil de rastrear
        ↓
Dependências explícitas por configuração
        ↓
Melhor legibilidade e depuração
```

## 28. Conclusão

A reunião transmitiu uma visão prática e arquitetural de uma solução legada em evolução. O Neutron foi apresentado como um front-end AngularJS organizado em estados, controladores, diretivas e componentes corporativos, integrado a Fuji e apoiado por uma cadeia de serviços Java até a base de dados.

O treinamento não descreve uma arquitetura simples: há múltiplas camadas, convenções rígidas, serializações entre representações de objetos, integração com sistemas de interface e dependências operacionais de ambiente. Ao mesmo tempo, há sinais de evolução tecnológica, especialmente a migração de execução baseada em Tomcat para Spring Boot e o direcionamento de novas exposições externas por APIs.

A principal mensagem técnica é que, para trabalhar com segurança nessa solução, não basta entender uma tela ou um serviço isolado. É necessário acompanhar o fluxo completo — do controlador Angular até o serviço de base de dados — e reconhecer tanto os padrões pretendidos quanto as exceções acumuladas no código existente.
