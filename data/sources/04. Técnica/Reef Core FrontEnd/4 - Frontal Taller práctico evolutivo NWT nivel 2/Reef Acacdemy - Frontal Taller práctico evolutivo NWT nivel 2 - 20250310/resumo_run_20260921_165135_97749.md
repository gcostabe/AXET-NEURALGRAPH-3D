## 1. Síntese executiva

A reunião teve caráter de treinamento prático para preparar e executar localmente aplicações compostas por uma parte Java e uma parte Angular. O encontro começou com a tentativa de diagnosticar um problema de inicialização de um front-end já configurado, aparentemente relacionado à ausência de arquivos estáticos dentro de um artefato web implantado em um servidor chamado na transcrição de “Tonka”.

Na sequência, o grupo passou a revisar a estrutura de projetos mais novos em Angular, os requisitos de desenvolvimento — incluindo editor/IDE, Node.js, Angular CLI, dependências e acesso ao Azure — e a configuração necessária para iniciar o front-end em modo de desenvolvimento. O arquivo `proxy.conf` foi apresentado como o ponto de configuração que define para qual servidor back-end a aplicação Angular direciona suas chamadas.

A explicação diferencia dois modos principais de trabalho:

1. **Execução em desenvolvimento do front-end Angular**, utilizando o comando `start`, um servidor local e recarga automática das alterações;
2. **Empacotamento/publicação de arquivos estáticos**, para disponibilizar o front-end em um servidor de aplicações identificado como “Tonka”.

Também foram discutidos perfis de execução Java, construção com Maven, geração de artefatos como `FATJAR` e WAR, uso de um painel de controle (“control panel”), possibilidade de apontar o front-end para servidores locais, ambientes de integração ou mocks, e uma condição especial para testar navegação entre fluxos que depende de um componente denominado “Fuji”.

A principal mensagem do treinamento é que o ambiente local depende da configuração coordenada de várias camadas: repositório, dependências, versão compatível de Node.js, build Java/Maven, geração de estáticos, configuração do proxy Angular e escolha adequada do alvo de back-end.

## 3. Problemas identificados

### 3.1. Front-end não inicializa corretamente

Foi relatado que um componente chamado “beweb” não iniciava. Também houve menção de que o front-end (“FE”) não apresentava exatamente o mesmo erro, mas retornava problemas como falha de login ou página não encontrada.

A causa exata não foi comprovada durante a reunião. Contudo, foi levantada a hipótese de que os arquivos estáticos do front-end não estivessem incluídos no WAR que estava sendo iniciado no servidor.

> **Hipótese levantada na reunião, não conclusão confirmada:** a ausência de estáticos no WAR poderia explicar o comportamento de página não encontrada ou indisponibilidade do front-end.

### 3.2. Dependência da geração prévia dos estáticos

Os participantes discutiram que iniciar a aplicação por meio do “control panel” aparentemente gera os arquivos estáticos antes da criação do WAR. Se esse processo não tiver sido executado, o WAR poderia ser produzido sem os estáticos necessários.

A cadeia de causa e efeito apresentada pode ser reorganizada assim:

```text
Control panel não executado previamente
↓
Estáticos podem não ser gerados
↓
WAR pode ser montado sem os estáticos
↓
Front-end implantado no servidor pode não responder como esperado
```

Essa reconstrução representa a relação sugerida pelos participantes; a transcrição não registra uma validação final do diagnóstico.

### 3.3. Incompatibilidade com versões recentes do Node.js

Foi afirmado explicitamente que a versão mais recente de Node.js não funciona com os projetos Angular tratados no treinamento. Por isso, o grupo utiliza um gerenciador de versões de Node, referido como “Node version manager”, para alternar entre versões quando necessário.

O problema é relevante porque a execução local do front-end depende de uma versão compatível de runtime. Instalar apenas a versão mais nova de Node.js não é suficiente — e, segundo a apresentação, pode impedir o funcionamento do projeto.

### 3.4. Primeira carga e indexação do projeto

Durante a tentativa de iniciar o ambiente, foi observado que o IDE poderia estar indexando módulos e baixando componentes pela primeira vez. Isso explicaria maior lentidão após o primeiro clone ou abertura do repositório.

O grupo tratou esse atraso como comportamento esperado na primeira preparação do ambiente, não como falha funcional confirmada.

### 3.5. Erro de sintaxe/configuração no `proxy.conf`

Em determinado momento, a aplicação Angular apresentou uma mensagem envolvendo JSON e posição 19 no arquivo de proxy. Um participante sugeriu que o problema poderia estar em um comentário no arquivo.

A transcrição não registra a correção nem a confirmação da causa. O único fato seguro é que houve uma falha de interpretação do arquivo de configuração do proxy durante a execução.

## 4. Solução e modelo de trabalho apresentados

A solução operacional demonstrada foi preparar e executar uma aplicação com dois blocos principais:

- **Back-end Java**, construído e iniciado localmente;
- **Front-end Angular**, configurado para consumir esse back-end ou outro endpoint disponível.

O fluxo de trabalho apresentado não é um único comando. Ele depende de um conjunto de preparações:

1. Clonar ou abrir o repositório;
2. Configurar o ambiente Java/Maven;
3. Definir a versão de Node.js compatível;
4. Garantir que Angular CLI esteja disponível;
5. Autenticar-se ou conectar-se ao Azure para instalar dependências;
6. Configurar o alvo do back-end no `proxy.conf`;
7. Escolher o perfil Java apropriado;
8. Construir e/ou iniciar o back-end;
9. Executar o front-end Angular pelo comando `start`;
10. Acessar a aplicação na porta local definida.

A reunião não apresenta esse processo como documentação formal nem fornece comandos completos reproduzíveis. Ainda assim, o modelo mental transmitido é claro: o desenvolvimento local exige que o front-end esteja apontando para um back-end acessível, seja ele local, de integração ou simulado.

### 5.1. Fronteira entre front-end e back-end

O front-end Angular não parece conter a lógica de back-end nem operar de forma isolada. O `proxy.conf` é utilizado para declarar o endpoint do servidor que atenderá as requisições da interface.

Foi explicado que esse endpoint pode ser:

- um servidor local iniciado pelo próprio desenvolvedor;
- um servidor já implantado em algum endpoint;
- um ambiente de integração;
- um servidor de mocks levantado separadamente.

### 5.2. Dois modos de disponibilização do front-end

A reunião diferencia implicitamente:

| Modo | Finalidade | Característica principal |
|---|---|---|
| Servidor Angular local | Desenvolvimento do front-end | Atualiza/recarga automaticamente conforme os arquivos Angular são modificados |
| Estáticos no WAR / servidor “Tonka” | Execução como aplicação implantada | Requer geração prévia de estáticos e empacotamento/publicação |

A fala indica que, quando a pessoa está alterando HTML, Angular ou partes visuais, o servidor de desenvolvimento é preferível porque evita recompilar tudo a cada alteração.

## 6.12. Mocks

A reunião discutiu a alternativa de usar mocks para o desenvolvimento, mas não a apresentou como o caminho mais comum no contexto demonstrado.

### Fatos explicitamente citados

- Seria necessário levantar um servidor de mocks;
- Em alguns projetos, como “GDC” ou “Fuji”, há mocks já gerados;
- Nos front-ends mais novos, normalmente não há muitos mocks;
- Os mocks podem ser gerados pelo desenvolvedor;
- A geração seria mais complexa porque as telas são dinâmicas e possuem muita parametrização;
- A prática mais habitual seria apontar o front-end para o próprio servidor local ou para um ambiente.

### Consequência prática

O grupo parece adotar uma estratégia prioritária de integração real com um back-end local ou ambiente compartilhado, deixando mocks como alternativa para cenários em que eles estejam disponíveis ou possam ser gerados com esforço justificável.

## 7. Modelo de integração

## 7.1. Integração front-end → back-end

O mecanismo explicitamente citado é o proxy configurado no projeto Angular.

```text
Aplicação Angular em desenvolvimento
↓
Arquivo proxy.conf
↓
Servidor/endpoint configurado
↓
Back-end local, ambiente de integração ou servidor de mocks
```

A configuração do `proxy.conf` é, portanto, uma parte crítica da integração local. A aplicação Angular pode ser iniciada localmente, mas sua funcionalidade depende de um destino válido para as chamadas ao back-end.

## 7.2. Integração com ambiente de integração

Foi sugerido que o grupo poderia testar o front-end contra um ambiente de integração enquanto a aplicação local ainda estivesse sendo preparada.

Isso indica que o processo não depende exclusivamente de uma stack local completa. Há flexibilidade para usar um endpoint remoto compartilhado, desde que configurado no proxy.

## 7.3. Integração por mocks

A integração por mocks existe como possibilidade, mas depende de um servidor de mocks e de respostas representativas. Como as telas são descritas como dinâmicas e altamente parametrizadas, a criação de mocks é percebida como mais complexa.

## 7.4. Integração entre fluxos com Fuji

Para navegação entre fluxos, a integração aparentemente não funciona apenas por endpoints externos independentes: há uma necessidade operacional de hospedar o front-end e Fuji no mesmo servidor de aplicações.

A transcrição não permite afirmar se isso ocorre por restrições de origem, roteamento interno, recursos compartilhados ou outra dependência.

## 8. Modelo operacional de desenvolvimento

### 8.1. Preparação do ambiente

O ambiente requer, no mínimo:

- repositório disponível localmente;
- IDE referido como Visual Studio;
- Java e configuração associada;
- Maven;
- versão compatível de Node.js;
- gerenciador de versões Node;
- Angular CLI;
- acesso ao Azure para dependências;
- configuração do proxy;
- perfil adequado para o back-end.

### 8.2. Desenvolvimento do front-end

O servidor Angular é apresentado como o modo preferível quando há alterações frequentes no front-end, pois ele recarrega a aplicação conforme modificações são feitas em HTML ou outros arquivos Angular.

Isso reduz a necessidade de gerar novamente os estáticos e republicar o WAR após cada mudança visual.

### 8.3. Desenvolvimento do back-end

Quando a alteração está na parte Java ou em componentes chamados de “managers”, a fala final sugere que é necessário iniciar novamente o back-end. A transcrição não descreve mecanismos de *hot reload* para Java.

### 8.4. Build e empacotamento

O processo pode gerar:

- arquivos estáticos;
- um WAR;
- um executável associado a “FATJAR”.

A criação de estáticos parece ocorrer antes ou durante etapas específicas do fluxo de build. O grupo interrompe uma execução para reduzir lentidão, após observar que o processo estava executando duas atividades em paralelo.

A versão mais atual de Node.js funciona com o projeto?

### Resposta

Não. Foi afirmado que a versão mais recente não funciona e que é necessário alternar versões usando um gerenciador de versões de Node.

### O que isso esclarece

A compatibilidade do front-end depende de versões específicas do runtime. Atualizações indiscriminadas de Node.js representam risco de indisponibilidade do ambiente local.

---

## 10.4. Como o front-end sabe para qual servidor enviar requisições?

### Pergunta

Onde se configura o servidor local, remoto ou de integração consumido pelo Angular?

### Resposta

No arquivo `proxy.conf`, referenciado pelo script de inicialização no `package.json`.

### O que isso esclarece

O proxy é o ponto de desacoplamento operacional entre o front-end e o destino do back-end. A mesma aplicação Angular pode ser usada com alvos diferentes alterando essa configuração.

---

## 10.5. É possível executar várias aplicações Angular ao mesmo tempo?

### Pergunta

Como evitar conflito quando mais de um projeto front-end é iniciado localmente?

### Resposta

Cada aplicação deve usar uma porta diferente.

### O que isso esclarece

As portas configuradas no script de inicialização são parte relevante do planejamento do ambiente local.

---

## 10.6. É possível usar mocks?

### Pergunta

O front-end pode operar sem um back-end real, utilizando respostas simuladas?

### Resposta

Sim, mas seria necessário levantar um servidor de mocks. Alguns projetos possuem mocks gerados; nos front-ends mais novos, eles não são comuns. A geração é considerada complexa porque as telas são dinâmicas e muito parametrizadas.

### O que isso esclarece

Mocks não foram descartados, mas não são a alternativa operacional predominante no cenário apresentado.

---

## 10.7. Quando é necessário usar Fuji no mesmo servidor?

### Pergunta

Como testar navegação entre fluxos?

### Resposta

É necessário iniciar Fuji e colocar tanto Fuji quanto o front-end no mesmo “Tonka”, pois a navegação precisa comunicar-se com Fuji.

### O que isso esclarece

Nem todos os testes podem ser feitos com front-end e back-end executados de forma completamente independente. Há fluxos que dependem de uma composição específica de aplicações no servidor.

## 11. Limitações reconhecidas

### Limitações técnicas explicitamente mencionadas

- A versão mais recente de Node.js não é compatível com o projeto;
- A primeira abertura do repositório pode ser lenta devido a indexação e download de componentes;
- O uso de mocks pode ser complexo por causa da geração dinâmica e parametrizada das telas;
- A navegação entre fluxos depende de Fuji e da implantação conjunta em um mesmo servidor;

## 17. Conclusões principais

A reunião documenta um treinamento prático de onboarding técnico para aplicações híbridas Java e Angular, com foco no preparo do ambiente local e na execução integrada entre front-end e back-end.

O conhecimento mais relevante transmitido foi:

1. **O front-end Angular depende de uma configuração correta de versão, dependências e proxy.**
2. **A versão mais recente de Node.js não deve ser adotada automaticamente; é necessário usar uma versão compatível.**
3. **O `proxy.conf` define o servidor de destino consumido pelo front-end e é central para testar localmente, em integração ou com mocks.**
4. **O servidor Angular local é o modo recomendado para alterações rápidas de interface, pois permite atualização automática.**
5. **A geração de estáticos parece ser uma pré-condição importante para que o front-end funcione quando empacotado em WAR e publicado no servidor.**
6. **Mocks são possíveis, mas não constituem o caminho mais simples nos projetos novos devido à natureza dinâmica e parametrizada das telas.**
7. **Alguns testes integrados, especialmente navegação entre fluxos, exigem uma composição específica com Fuji e o servidor citado como “Tonka”.**
8. **O treinamento não foi concluído funcionalmente: o grupo planejou retomar no dia seguinte para explorar o funcionamento e executar testes.**

A documentação resultante deve ser usada como referência de contexto inicial, mas não substitui instruções operacionais versionadas. Para tornar o procedimento reproduzível, ainda seriam necessários exemplos validados de configuração, versões suportadas, comandos de build, perfis Maven, configuração de proxy e processo de autenticação no Azure.
