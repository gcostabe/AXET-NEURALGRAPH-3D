## 1. Síntese executiva

A sessão explicou o papel do **backend Java** dentro do ecossistema Rift, com foco na aplicação **Neutron**. Neutron foi apresentado como uma aplicação baseada no framework corporativo **Gaia**, estruturada em múltiplas camadas: front-end executado no navegador, front-end de servidor e backend Java. A lógica de negócio histórica, porém, permanece majoritariamente concentrada no banco de dados Oracle, em procedimentos identificados na transcrição como **PL**.

O backend Java de Neutron funciona, em grande medida, como uma camada de serviços e integração. Ele recebe solicitações provenientes das telas, expõe serviços por diferentes tecnologias — REST, SOAP e HTTP Invoker — e encaminha operações para a base Oracle. Embora a apresentação ressalte que essa camada possui pouca lógica de negócio complexa no caso de Neutron, ela contém validações, verificações, organização de responsabilidades e mecanismos que simplificam a comunicação com a base de dados.

A apresentação também abordou dois temas estratégicos. O primeiro é o modelo de desenvolvimento baseado em interfaces, injeção de dependências e serviços simulados, que permite avançar em diferentes camadas sem dependência total entre equipes. O segundo é a evolução do modelo de personalização por país: em vez de os países estenderem diretamente o código do core, a direção atual é utilizar **user exits**, pontos controlados de extensão expostos pelo core e consumidos por meio de APIs locais.

A principal transformação descrita é uma mudança de personalizações acopladas ao código e à evolução do core para um modelo mais desacoplado, governado e compatível por contrato HTTP/REST. Isso busca diminuir o esforço de atualização, reduzir regressões e ampliar a reutilização do core entre países.

## 3. Problemas e necessidades que sustentam o modelo apresentado

### 3.1 Lógica de negócio historicamente concentrada no Oracle

O principal condicionante arquitetural é que a lógica de negócio de Rift já existia historicamente na base Oracle. Por isso, embora Gaia preveja uma camada Java voltada à lógica de negócio, Neutron não concentra nessa camada a maior parte das regras complexas.

O fluxo dominante apresentado é:

```text
Tela / front-end
↓
Serviços do backend Java
↓
Chamadas à base de dados Oracle
↓
Procedimentos PL e lógica histórica do sistema
```

A consequência é que o backend Java tende a operar como mediador entre a experiência de tela e a lógica persistida no banco. Isso não significa ausência total de programação Java: existem validações, verificações e responsabilidades técnicas, mas não a concentração da regra de negócio principal.

### 3.2 Complexidade potencial da comunicação entre camadas

O desenvolvimento poderia exigir que programadores lidassem diretamente com:

- exposição de serviços;
- serialização e contratos;
- abertura e fechamento de conexões;
- chamadas JDBC;
- mapeamento entre nomes e tipos Java e Oracle;
- execução de procedimentos da base.

A solução apresentada reduz essa complexidade por meio de convenções, anotações Spring e utilitários fornecidos pelo framework.

### 3.3 Dependência entre camadas durante o desenvolvimento

Outro problema abordado é a dependência entre desenvolvedores e camadas. Se cada camada só pudesse avançar quando a anterior estivesse concluída, o desenvolvimento seria bloqueado ou sequencial demais.

A separação entre interfaces e implementações, associada ao uso de implementações simuladas — chamadas na transcrição de serviços “moqueados” — é apresentada como forma de permitir avanço paralelo. Assim, uma camada pode consumir uma interface já definida, mesmo que a implementação definitiva da camada subsequente ainda não esteja pronta.

### 3.4 Personalizações locais dificultando a evolução do core

O problema mais enfatizado na segunda metade da sessão é o modelo anterior de personalização por extensão. Países podiam herdar classes e alterar comportamentos do core para atender necessidades locais. Isso oferecia flexibilidade, mas aumentava o acoplamento entre a customização local e a evolução do produto central.

Quando o core evoluía, os países precisavam atualizar a versão utilizada e enfrentar possíveis impactos:

- adaptação de código local;
- mudanças de comportamento;
- alterações em dados;
- necessidade de testes de regressão;
- risco de incompatibilidades, mesmo quando a intenção era manter retrocompatibilidade.

A resposta apresentada é substituir gradualmente a extensão direta do core por um mecanismo de **user exit**.

## 4. Solução apresentada

A solução descrita combina uma arquitetura Java baseada em Gaia, uma organização por responsabilidades técnicas e funcionais e um modelo de personalização desacoplado.

Em termos conceituais, o backend Java é responsável por:

- receber solicitações das camadas superiores;
- expor serviços consumíveis pelas telas e, eventualmente, por outras aplicações;
- aplicar verificações e lógicas complementares;
- encaminhar solicitações à base Oracle;
- abstrair detalhes técnicos de acesso a dados;
- organizar serviços e implementações;
- suportar tarefas Java executadas por um lançador de tarefas;
- permitir que APIs reutilizem a lógica de acesso a dados já presente no backend Neutron.

Em paralelo, o novo modelo de personalização desloca extensões locais de dentro do código herdado do core para APIs específicas do país, chamadas em pontos controlados pelo próprio core.

A lógica geral do novo modelo pode ser representada assim:

```text
Fluxo do Core
↓
Ponto de user exit previamente definido
↓
Chamada HTTP/REST para API local do país
↓
Processamento específico do país
↓
Retorno ao Core
↓
Continuidade do fluxo normal
```

A apresentação deixa claro que esses pontos devem ser adicionados sob demanda e não podem proliferar sem controle.

A apresentação identifica três formas principais pelas quais o backend Java pode expor serviços.

| Tecnologia | Finalidade descrita | Observações |

### 6.1 HTTP Invoker

HTTP Invoker é apresentado como uma tecnologia própria do Spring. A motivação explicitada para seu uso no caso descrito é desempenho, pois os dados trafegariam internamente em binário.

Mesmo quando as camadas Java são implantadas no mesmo servidor, a comunicação pode continuar sendo remota, por HTTP. Gaia, contudo, permitiria gerar um artefato único contendo front-end e backend Java. Nesse caso, a chamada deixaria de ocorrer por HTTP e passaria a ocorrer por chamada direta entre classes.

A transcrição afirma que essa alteração pode ser obtida por configuração, sem exigir mudança de código de programação.

### 6.2 REST

REST aparece em dois contextos:

1. como forma de o front-end de servidor expor serviços às telas;
2. como contrato de comunicação entre o core e APIs específicas dos países no modelo de user exit.

No segundo caso, a apresentação ressalta que a evolução desses contratos exige compatibilidade. Não seria permitido, por exemplo, remover subitamente um parâmetro de um serviço ou alterar seu tipo. Como estratégia mais simples para manter compatibilidade, foi citado o versionamento de serviços.

### 6.3 SOAP

SOAP foi citado como capacidade de exposição de serviços do backend Java. A reunião não esclarece quais módulos o utilizam, em quais países é usado, se está em uso ativo ou se representa apenas uma capacidade suportada pelo framework.

A finalidade prática é desacoplar consumidores da forma concreta de execução. Isso permite, por exemplo:

- trocar implementações;
- configurar comportamentos diferentes;
- usar implementações simuladas;
- desenvolver camadas em paralelo;
- reduzir dependências de entrega entre equipes.

### 7.3 Serviços simulados

A transcrição chama os serviços simulados de “moqueados”. Eles devolvem um valor controlado, permitindo que uma camada avance mesmo sem depender da conclusão de outra.

Em Neutron, seria possível implantar o projeto em modo de desenvolvimento e usar a implementação simulada por configuração.

## 8. Mecanismo de acesso à base: “PL Invoker”

> **Cautela terminológica:** a transcrição registra “pele invoker”. Pelo contexto, trata-se aparentemente de um mecanismo chamado **PL Invoker**, relacionado à invocação de procedimentos PL no Oracle. A grafia e o nome oficial não podem ser confirmados apenas pela transcrição.

Esse mecanismo é descrito como uma ferramenta intensivamente utilizada para simplificar o acesso à base de dados. A ideia central é que o desenvolvedor não precise lidar diretamente com detalhes como abrir ou fechar conexões.

O fluxo descrito é:

1. o desenvolvedor define uma interface;
2. utiliza uma anotação que identifica ou permite inferir o procedimento PL a chamar;
3. informa os parâmetros necessários;
4. o framework cria, em tempo de execução, o comportamento necessário para a chamada ao banco.

A apresentação indica que, quando a interface e o método seguem uma convenção de nomenclatura e tipos compatíveis com o procedimento no Oracle, pode não ser necessário declarar explicitamente qual procedimento PL deve ser invocado.

As convenções citadas são:

| Contexto | Convenção mencionada |
|---|---|
| Oracle | Maiúsculas e palavras separadas por underscore (`_`) |
| Java | Camel case |

Essa abstração reduz o código necessário para chamar procedimentos da base e padroniza a integração entre Java e Oracle.

### Limitação importante

A transcrição não esclarece:

- como são tratados erros de banco;
- como são gerenciadas transações;
- como ocorre o mapeamento de tipos complexos;
- como são controlados timeouts;
- como são tratadas conexões simultâneas;
- como o mecanismo resolve ambiguidades de nomes;
- quais requisitos de segurança ou autorização existem nas chamadas.

## 12. Tarefas Java

Existe em Rift e na base de dados um conceito chamado **tarefas**. Essas tarefas são processos lançados por uma ferramenta denominada **lançador de tarefas**.

Uma tarefa pode executar um processo mais pesado e realizar ações como:

- gerar arquivos;
- ler arquivos;
- processar arquivos;
- executar outras operações não detalhadas.

Historicamente, as tarefas em Neutron Web eram procedimentos PL. Posteriormente, foi introduzida a possibilidade de implementar tarefas em Java.

O comportamento descrito é:

```text
Lançador de tarefas
↓
Nome da tarefa + parâmetros
↓
Identificação interna do tipo de tarefa
├── Tarefa PL clássica
└── Tarefa Java
↓
Execução do processo correspondente
```

As tarefas Java são desenvolvidas no backend Java de Neutron.

### 12.1 Reutilização pelas APIs

A sessão destaca que as APIs usam o backend Neutron como biblioteca. Dessa forma, a lógica de acesso a dados disponível no backend também pode ser usada pelas APIs.

Uma consequência apontada é que, como as tarefas Java estão atualmente no backend Neutron, as APIs também podem ter capacidade de dispará-las por meio dessa reutilização.

A apresentação não detalha:

- se todas as APIs possuem autorização para disparar tarefas;
- quais tarefas estão disponíveis;
- se há limites de concorrência;
- como falhas são registradas;
- como é feito acompanhamento de execução;
- se tarefas Java possuem agendamento nativo.

## 13. Perguntas e respostas

### Pergunta: as tarefas Java podem ser executadas sob demanda e agendadas como processos batch?

A pergunta buscou entender se, além da execução manual ou sob demanda, as tarefas Java poderiam ser programadas para rodar em determinado dia ou horário, como um processo batch.

### Resposta

A resposta diferencia dois conceitos:

1. **a tarefa em si**, isto é, o processo que será executado;
2. **o mecanismo que dispara ou agenda a tarefa**, que pode variar por instalação, instância de Rift ou país.

Foi afirmado que um planejador teria capacidade de disparar a tarefa porque existe uma API Rift que permite isso. Contudo, a forma concreta de agendamento depende do contexto de cada instalação ou país.

Também foi mencionado que há países que usam ferramentas específicas de controle ou agendamento, mas o nome citado na transcrição não está suficientemente claro para ser registrado com segurança.

### O que essa resposta esclarece

A resposta estabelece que tarefas Java não devem ser confundidas com o agendador. A tarefa é a unidade de processamento; o agendamento é uma responsabilidade externa ou separada, ainda que a API Rift permita o disparo.

### O que permanece indefinido

A reunião não permite concluir:

- qual agendador é utilizado em cada país;
- se há um planejador oficial de Rift;
- se existe uma solução padrão corporativa;
- se há suporte a recorrência, calendário, dependências ou reprocessamento;
- como são tratados falhas, alertas e retentativas de tarefas agendadas.

## 14. Modelo anterior de personalização por extensão

O modelo anterior era baseado em personalização por extensão ou herança.

O fluxo descrito pode ser resumido assim:

```text
Core Neutron publicado
↓
Projeto específico de um país inclui o Core como biblioteca
↓
País cria classes herdadas das classes do Core
↓
País altera ou adiciona comportamento
↓
Spring prioriza a implementação local por anotação
```

A transcrição menciona o uso da anotação `@Primary` para que uma classe local, derivada da implementação de core, seja escolhida pelo Spring no lugar da original.

Um exemplo simplificado foi apresentado: caso um país queira que o backend Java chame um procedimento PL diferente daquele previsto pelo core, poderia herdar a classe original e inserir seu próprio comportamento.

Esse mecanismo também permitiria ampliar objetos de negócio, incluindo propriedades adicionais.

### 14.1 Características do projeto local

O projeto local do país começa como um projeto Gaia básico, praticamente vazio, contendo principalmente configuração. Gradualmente, cada país adiciona classes e extensões para atender necessidades particulares.

### 14.2 Vantagem reconhecida

A principal vantagem é liberdade de personalização local. Cada país pode adaptar comportamento e objetos de negócio ao seu contexto.

### 14.3 Problema estrutural

Essa liberdade cria dependência direta entre o código local e o core. Quando o core evolui, cada país precisa avaliar e absorver os impactos da atualização.

Mesmo com preocupação de manter retrocompatibilidade, podem ocorrer:

- alterações de interfaces;
- mudanças sutis de comportamento;
- mudanças de dados;
- necessidade de adaptação;
- regressões;
- maior esforço de teste.

> **Relação de causa e efeito reconstruída a partir da apresentação:**
>
> ```text
> Extensões locais por herança
> ↓
> Acoplamento entre país e implementação interna do Core
> ↓
> Evolução do Core afeta implementações locais
> ↓
> Atualizações exigem adaptação e regressão
> ↓
> Necessidade de modelo de personalização mais desacoplado
> ```

## 15. Novo modelo de personalização por user exit

O modelo mais novo, descrito como o atualmente utilizado, baseia-se em **user exits**.

### 15.1 Conceito

Um user exit é um ponto específico do fluxo do core no qual o core permite a execução de comportamento fornecido pelo país.

Em vez de o país modificar, herdar ou substituir diretamente código do core, o core chama uma API do país. Essa API recebe os dados que o core está processando naquele momento, executa a lógica específica local e devolve o resultado para que o fluxo principal continue.

```text
Core processa um fluxo
↓
Core encontra um ponto de user exit
↓
Core chama a API específica do país
↓
País processa a necessidade local
↓
País devolve resposta ao Core
↓
Core continua o fluxo padrão
```

### 15.2 Comunicação

A comunicação entre core e APIs locais é feita por HTTP, usando APIs REST.

Os exemplos de países citados como em funcionamento dentro do Rift da América Central foram:

- Panamá;
- Honduras.

Não foram detalhados os domínios funcionais cobertos em cada um desses países, além de referências posteriores a Honduras.

### 15.3 Benefícios apresentados

| Benefício | Explicação |
|---|---|
| Separação de artefatos | O core e a solução local do país são implantados de forma independente. |
| Menor necessidade de reimplantação local | Atualizações do core podem ocorrer sem que seja necessário reimplantar automaticamente toda a aplicação do país. |
| Contrato explícito | A integração ocorre por APIs REST, não por dependência direta da implementação interna. |
| Menor acoplamento | O país deixa de herdar diretamente classes do core para inserir comportamento. |
| Evolução mais controlada | A evolução precisa respeitar compatibilidade de contrato. |
| Redução de artefatos locais | Em vez de um artefato local para cada módulo, há um artefato próprio do país dedicado ao mecanismo de user exit. |

### 15.4 Compatibilidade

A independência não significa ausência de dependência. A sessão enfatiza que existe dependência em tempo de execução e que compatibilidade precisa ser preservada.

Exemplos de mudanças que não deveriam ser feitas diretamente em um serviço existente:

- remover um parâmetro;
- alterar o tipo de um parâmetro.

A estratégia citada como mais simples para evoluir contratos sem romper consumidores é publicar novas versões dos serviços.

### 15.5 Limite de crescimento dos user exits

Foi dito explicitamente que user exits são adicionados sob demanda. Também foi ressaltado que o ideal é evitar crescimento descontrolado desses pontos de extensão.

Isso indica uma preocupação de governança: cada novo ponto amplia a superfície de customização e precisa ser justificado.

## 16. Centralização de necessidades no Core

O novo modelo não é apresentado apenas como mudança técnica. Ele também altera a forma como necessidades locais devem ser tratadas.

A orientação descrita é que uma necessidade de país deve primeiro passar pelo core para avaliação. O objetivo é verificar se faz sentido transformar aquela necessidade em funcionalidade mais genérica, utilizável por outros contextos.

A intenção parece ser fazer o core crescer de forma mais global e reutilizável, reduzindo personalizações isoladas.

> **Leitura analítica:** esse direcionamento sugere uma evolução de uma lógica de “cada país adapta sua cópia ou extensão” para uma lógica de produto central que absorve capacidades reaproveitáveis. A transcrição não apresenta um processo formal de priorização, comitê decisório ou critérios de aceite, mas indica claramente a preferência por avaliar necessidades no core antes de criar customizações locais.

## 22. Limitações e ressalvas reconhecidas

### 22.1 Lógica de negócio Java limitada em Neutron

A camada Java prevista por Gaia pode ser destinada a lógica de negócio, mas, no caso de Neutron, a apresentação afirma que a lógica complexa geralmente não está nessa camada. Ela permanece historicamente no Oracle.

### 22.3 User exits não devem crescer sem controle

### 22.4 Compatibilidade continua necessária

## 23. Riscos e desafios

### 23.1 Riscos explicitamente mencionados

| Risco ou desafio | Origem |
|---|---|
| Regressões ao atualizar o core | Países com extensões diretas precisam validar mudanças de comportamento, dados ou interfaces. |
| Necessidade de adaptação de código local | Evoluções do core podem exigir alterações nos projetos dos países. |
| Quebra de consumidores de API | Alterar ou remover parâmetros de APIs REST pode romper integrações. |
| Proliferação descontrolada de user exits | Aumenta complexidade e reduz governabilidade das extensões. |
| Dependência de infraestrutura local para agendamento | O comportamento operacional pode variar por instalação ou país. |

### 23.2 Desafios derivados do contexto

> **Os itens abaixo são análises derivadas do conteúdo apresentado, não afirmações literais dos participantes.**

1. **Equilibrar generalização e necessidade local**  
   A orientação de avaliar necessidades no core antes de personalizar sugere um desafio contínuo: decidir o que deve se tornar capacidade global e o que deve permanecer específico de um país.

2. **Evitar que APIs locais se transformem em novo ponto de divergência**  
   O user exit reduz o acoplamento por herança, mas introduz contratos distribuídos. A disciplina de versionamento e compatibilidade se torna essencial para que a separação não apenas desloque o problema.

3. **Gerenciar lógica distribuída entre Java e Oracle**  
   Como a regra de negócio histórica está no banco, mudanças podem exigir entendimento conjunto de procedimentos PL, serviços Java, telas e contratos de integração.

4. **Preservar consistência entre desenvolvimento simulado e execução real**  
   Serviços simulados aceleram o desenvolvimento, mas exigem validações adequadas para evitar que comportamentos mockados se afastem do comportamento real das integrações.

5. **Evoluir a plataforma sem interromper instalações heterogêneas**  
   A coexistência de opções como servidores de aplicação tradicionais, possíveis contêineres, versões de Spring e instalações por país indica uma provável necessidade de estratégias de migração cuidadosas.

## 24. Transformações estruturais identificadas

### 24.1 Transformação arquitetural: de extensão interna para integração por contrato

O movimento mais claro da sessão é a substituição gradual de personalização por herança de classes do core por integração através de APIs REST e user exits.

```text
Antes
Core + herança local + substituição de beans
↓
País depende de detalhes internos do Core

Depois
Core + ponto de extensão + API local
↓
País depende de um contrato explícito
```

Isso indica uma direção de desacoplamento técnico e de maior estabilidade de evolução.

### 24.2 Transformação de produto: de adaptações locais para capacidades reutilizáveis

A orientação de levar necessidades primeiro ao core revela uma mudança de mentalidade: uma necessidade local deixa de ser automaticamente uma modificação local e passa a ser avaliada como possível capacidade reutilizável para outros países.

```text
Necessidade local
↓
Avaliação no Core
↓
Capacidade genérica, parametrização ou user exit
↓
Uso mais amplo e menor duplicidade potencial
```

### 24.3 Transformação operacional: atualizações mais independentes

No modelo anterior, nova versão de core tendia a exigir atualização e reimplantação das aplicações dos países. No modelo de user exit, core e API local podem ser atualizados de modo mais independente, desde que preservem os contratos.

### 24.4 Transformação na organização do desenvolvimento

O uso de interfaces, injeção de dependências e serviços simulados favorece a separação entre contratos e implementação. Isso permite desenvolvimento menos bloqueado por dependências entre camadas.

## 26. Conclusões

A sessão apresenta Neutron como uma aplicação multicamada do ecossistema Rift, construída sobre o framework Gaia e fortemente integrada a uma base Oracle onde permanece a lógica de negócio histórica.

O backend Java é essencial como camada de exposição de serviços, organização técnica, verificações, integração e acesso simplificado à base de dados. Seu desenho usa Spring, interfaces, injeção de dependências, abstrações para invocação de procedimentos PL e capacidade de execução de tarefas Java.

A evolução mais relevante não está apenas no código Java, mas na forma de personalizar o produto. O modelo anterior de extensão direta do core oferecia flexibilidade, porém elevava o custo de atualização e regressão. O modelo de user exit busca preservar necessidades locais por APIs de país e contratos REST, reduzindo dependência da implementação interna do core.

A reunião não descreve uma plataforma completamente desacoplada ou sem dependências. Pelo contrário: ela reconhece que compatibilidade, versionamento, governança de extensões e disciplina arquitetural continuam sendo necessários. A principal diferença é que essas dependências passam a ser tratadas de forma mais explícita, por contratos e pontos controlados de extensão, em vez de por herança direta do código central.
