# Análise estruturada — Neutron, microfrontends e TronWeb no ecossistema RIF

## 1. Síntese executiva

A sessão apresentou três artefatos de front-end do ecossistema RIF: **Neutron**, a nova arquitetura de **microfrontends** e **TronWeb**. O eixo comum foi a evolução de uma base tecnológica legada para uma abordagem mais modular, parametrizável e reutilizável.

O **Neutron** foi apresentado como o artefato que concentra grande parte do core de RIF, construído sobre a arquitetura corporativa **Gaia**, com AngularJS no front-end cliente e Spring MVC na camada Java de front-end. Embora tenha introduzido separação de responsabilidades e componentes reutilizáveis, sua tecnologia está fora de suporte e a personalização por país tornou-se cara. Por isso, novos desenvolvimentos devem seguir a arquitetura de microfrontends; no Neutron permanecem apenas manutenção e pequenos evolutivos, avaliados caso a caso.

A arquitetura de **microfrontends** busca reduzir código customizado e tornar telas, fluxos e comportamentos configuráveis por parametrização em banco de dados. Ela combina componentes técnicos reutilizáveis, componentes funcionais de negócio, geração de componentes a partir de definições de dados, ações de front-end e serviços Java de apoio. Os componentes são versionados e publicados em Azure Artifacts para reutilização entre aplicações e domínios funcionais.

Já o **TronWeb** foi caracterizado como uma solução ainda mais legada: uma aplicação Java Swing com cliente pesado, dependente de Windows e de Java 1.3 no lado cliente. É usada principalmente em telas de tesouraria e está em processo de descontinuação. A orientação atual é realizar apenas correções, sem novos evolutivos, até que suas funções sejam migradas ou substituídas.

## 3. Contexto e antecedentes

### 3.1. Ecossistema de front-ends

O RIF possui ou possuiu diversos artefatos de front-end integrados por meio de **Fuji**, descrito como o ponto a partir do qual é possível acessar diferentes frontais, incluindo GDC, Neutron e outros artefatos.

A transcrição sugere uma evolução histórica composta por pelo menos três momentos:

```text
TronWeb
↓
Neutron / Gaia
↓
Microfrontends
```

Essa sequência não foi apresentada como uma linha do tempo formal, mas emerge da explicação sobre tecnologias e estratégias de modernização.

### 3.2. Problema de evolução do legado

A reunião descreve dois legados principais:

- **Neutron**, baseado em AngularJS, tecnologia que já não possui suporte;
- **TronWeb**, baseado em Java Swing e Java 1.3 no cliente, com severas restrições de atualização.

Além da obsolescência tecnológica, a preocupação central é operacional e de manutenção: personalizações locais, especialmente por país, passaram a exigir esforço significativo e a gerar custo elevado de evolução.

### 3.3. Direção de transformação

A direção apresentada é migrar progressivamente os processos dos legados para novos front-ends, organizados por família funcional — por exemplo, emissão, sinistros e fornecedores — com maior capacidade de reutilização e personalização parametrizada.

A transformação não parece ser uma substituição imediata e uniforme. Ela é incremental:

- pequenos ajustes no legado podem continuar sendo feitos no próprio legado;
- novos desenvolvimentos devem ocorrer nos microfrontends;
- migrações ou refatorações maiores devem ser analisadas considerando custo e complexidade;
- alguns módulos podem reutilizar serviços ou bibliotecas existentes enquanto a transição acontece.

## 4. Problemas identificados

## 4.1. Obsolescência do AngularJS no Neutron

O Neutron foi construído sobre AngularJS. A reunião afirma que AngularJS já está fora de suporte.

### Consequência

A migração direta para Angular em versões 2 ou superiores não seria simples. Segundo a apresentação, a passagem exigiria refazer os desenvolvimentos existentes, pois não havia uma forma fácil de migrar o conjunto de código.

### Relevância

Essa limitação reduz a sustentabilidade tecnológica do Neutron e foi um dos fatores que motivaram a nova arquitetura de microfrontends.

---

## 4.2. Alto custo de personalização do Neutron

O Neutron permite customização por país, mas essa customização foi descrita como muito custosa.

A dificuldade não se limita ao desenvolvimento inicial. A reunião indica que, uma vez criada uma personalização, sua manutenção futura também pode se tornar onerosa.

### Relação de causa e efeito reconstruída

```text
Personalizações locais no Neutron
↓
Mais código específico por país
↓
Maior custo de manutenção e evolução
↓
Dificuldade de reaproveitamento
↓
Necessidade de parametrização e componentes reutilizáveis
↓
Arquitetura de microfrontends
```

Essa cadeia é uma consolidação analítica fiel ao raciocínio apresentado, não uma formulação literal de um participante.

---

## 4.3. Reutilização limitada de controladores no Neutron

Embora o Neutron reutilize bastante a parte visual, a apresentação reconhece que a reutilização de controladores é menor.

Há muitos controladores replicados por operação, cujas diferenças podem estar restritas à chamada de um serviço distinto ou ao envio de parâmetros diferentes.

### Consequência

A duplicação de controladores tende a ampliar a base de código e tornar a evolução mais difícil. A reunião associa essa limitação à motivação para a arquitetura de microfrontends.

---

## 4.4. Lógica de negócio avançando para camadas de front-end

A camada Java de front-end do Neutron deveria, em princípio, resolver funcionalidades de interface, sem concentrar lógica de negócio. Contudo, a apresentação reconhece que a separação entre a camada Java de front-end e o back-end não está muito bem delimitada no Neutron.

### Implicação

A nova arquitetura procura reduzir essa presença de lógica de negócio no front-end e mantê-la nas camadas que deveriam ser responsáveis por ela.

---

## 4.5. Restrições tecnológicas severas no TronWeb

O TronWeb utiliza cliente Java Swing e requer Windows no computador do usuário. O cliente depende de Java Virtual Machine 1.3, sem possibilidade prática de atualização segundo os testes e tentativas relatados.

Tentativas de elevar a versão do Java encontraram problemas de adaptação ou exigiriam mudanças grandes no código.

### Consequência

O TronWeb possui restrições de compatibilidade, manutenção e evolução. A decisão de manter apenas manutenção corretiva está diretamente relacionada a esse cenário.

---

## 5. Solução e direcionamento apresentados

## 5.1. Posicionamento atual do Neutron

O Neutron continua sendo relevante porque contém grande parte do core de RIF. Está organizado em famílias funcionais, como emissão e sinistros.

A tesouraria foi citada como exceção: ela estaria sendo migrada para novos front-ends ou ainda estaria no TronWeb durante o processo de migração. A expectativa mencionada era que essas presenças desaparecessem ao longo daquele ano ou no início do ano seguinte. Como não há data absoluta da reunião, não é possível determinar com segurança a que anos esse horizonte se refere.

### Política de evolução apresentada

| Tipo de demanda | Direcionamento informado |
|---|---|
| Correção pequena em Neutron | Pode ser feita no próprio Neutron, após análise |
| Pequeno evolutivo | Pode permanecer no Neutron, dependendo do caso |
| Novo desenvolvimento | Deve ser realizado nos microfrontends |
| Refatoração ou mudança de grande porte | Deve ser analisada conforme custo, lógica existente e viabilidade |
| Novo front-end no core ou em país sobre Neutron | Não deve ser criado |

A apresentação enfatiza que cada caso deve ser analisado individualmente. Não existe uma regra de “reescrever tudo” diante de qualquer alteração no legado.

## 5.2. Estratégia dos microfrontends

A nova arquitetura foi proposta para:

- reduzir código manual;
- concentrar a maior parte da composição de telas em parametrização;
- permitir reutilização de componentes entre aplicações;
- simplificar personalizações de países;
- preservar componentes funcionais reutilizáveis;
- facilitar a evolução de versões do Angular;
- diminuir a lógica de negócio presente no front-end;
- melhorar produtividade, manutenção e desempenho.

O modelo não elimina desenvolvimento. O desenvolvedor ainda cria:

- componentes funcionais;
- parametrizações de fluxos e telas;
- dependências entre conceitos lógicos;
- managers Java que expõem serviços para o front-end.

O que é reduzido é a necessidade de construir manualmente toda a estrutura de página, fluxo, comportamento visual e repetição de lógica de interface.

---

## 5.3. Estratégia para o TronWeb

O TronWeb está em processo de descontinuação. A orientação expressa foi:

- realizar somente correções de código;
- não desenvolver novos evolutivos;
- migrar ou substituir gradualmente suas funções, especialmente as relacionadas à tesouraria;
- manter sua presença apenas enquanto ainda houver necessidade em implementações ou países específicos.

## 9. Arquitetura de microfrontends

## 9.1. Motivação

A arquitetura de microfrontends surgiu da combinação de fatores:

- tecnologia AngularJS do Neutron fora de suporte;
- dificuldade de migrar diretamente para Angular moderno;
- alto custo de personalização por país;
- alto custo de manutenção de customizações;
- necessidade de reutilizar conceitos funcionais;
- experiência anterior com GDC e parametrização;
- intenção de gerar telas dinamicamente a partir de configurações.

A reunião menciona que o GDC permitia manutenção rápida baseada em parametrização, usando uma ferramenta descrita como “Wixi Wix” ou expressão semelhante. O nome pode ter sido afetado pelo reconhecimento de voz; não é possível confirmar sua grafia ou natureza exata apenas a partir da transcrição.

Entretanto, o GDC era insuficiente para aplicações complexas. A nova arquitetura buscou preservar a flexibilidade da parametrização sem limitar o desenvolvimento a cenários simples.

A abordagem cria artefatos por aplicação ou domínio funcional, por exemplo:

- emissão;

A característica central da arquitetura é a geração de telas e fluxos com base em parametrização armazenada em banco de dados.

Podem ser parametrizados, entre outros:

- agrupamento de campos;
- dependências entre conceitos lógicos;
- ações executadas em determinados estados.

### Exemplo conceitual apresentado

Uma tela pode exibir três formulários — A, B e C — em determinada ordem, com botões como “validar” e outras ações. A estrutura visual, os botões e o comportamento de composição podem ser definidos por parametrização.

Esses componentes não precisam ser recriados a cada funcionalidade. Quando surge uma necessidade realmente nova, é possível desenvolver um componente técnico adicional para a arquitetura e disponibilizá-lo para uso por parametrização.

## 9.6. Conceitos lógicos ou componentes funcionais

Além dos componentes técnicos, existem conceitos lógicos ligados ao domínio, como:

- atividade;
- endereço;
- terceiro;
- ordens de pagamento;
- outros objetos de negócio.

Esses são componentes Angular propriamente ditos e representam a parte que o desenvolvedor efetivamente constrói ou ajusta.

### Geração de componentes

A reunião menciona uma ferramenta chamada **generator** — grafia ou nome exato não confirmado — que cria um componente Angular com base na definição de um objeto em banco de dados.

O componente gerado contém os campos definidos para aquele objeto. Depois, é possível aplicar ajustes visuais, por exemplo:

- organizar campos em três colunas;
- definir campos superiores e inferiores;
- agrupar campos;
- organizar blocos visuais.

Uma vez criado, o mesmo componente pode ser reutilizado em diferentes telas e fluxos. Em cada contexto, a parametrização define quais campos aparecem, sua ordem, agrupamento, estado e comportamento.

## 9.7. Ações, managers e APIs

A arquitetura possui ações pré-definidas para operações mais comuns, como:

- validar;
- sair;
- avançar;
- outras ações associadas a componentes técnicos.

Também é possível definir ações específicas quando necessário.

Essas ações acionam **managers** na camada Java de front-end. Os managers expõem serviços para resolver as necessidades das telas e, por sua vez, invocam as APIs necessárias.

### Modelo lógico consolidado

```text
Usuário
↓
Tela composta dinamicamente
↓
Componentes técnicos + componentes funcionais
↓
Ações parametrizadas
↓
Managers Java de front-end
↓
APIs necessárias para a funcionalidade
↓
Camadas de negócio e dados
```

A reunião destaca que, como o front-end consulta como a tela deve ser desenhada ao entrar em determinada etapa, a arquitetura evita o uso de sessão para manter esse estado de tela.

A transcrição não detalha como esse modelo lida com autenticação, autorização, concorrência, estado transacional ou recuperação após falhas.

## 10. Modelo de integração e reutilização

## 10.1. Integração por APIs

A diretriz apresentada é que os microfrontends integrem com **APIs**, não diretamente com a “paqueteria” ou bibliotecas internas de outros sistemas.

Essa informação surgiu em resposta à pergunta sobre uso do back-end Java do Neutron.

### Princípio declarado

```text
Microfrontend
↓
API exposta
↓
Serviço necessário
```

e não:

```text
Microfrontend
↓
Dependência direta da estrutura interna de outro módulo
```

Essa orientação sugere busca por menor acoplamento entre aplicações, embora a reunião não tenha detalhado padrões de API, governança de contratos ou versionamento.

---

## 10.2. Exceções e coexistência com o legado

A orientação por APIs não é absoluta na situação atual. Foram citados casos específicos:

- **Tesouraria**: utiliza um conector que recobre serviços de PL, conforme a fala transcrita. O termo “PL” pode ter sido reconhecido incorretamente; não é possível identificar com segurança o sistema ou tecnologia referida.
- Outros casos podem consumir serviços que existiam no back-end do Neutron.
- Pode haver APIs expostas no “CEMEN” ou termo semelhante; a nomenclatura não está suficientemente clara na transcrição.
- **Fornecedores** e **módulo de documentos** foram citados como módulos mais recentes que funcionam por integração via APIs.
- A refatoração do processo de **emissão** utiliza camada e bibliotecas de back-end existentes para reaproveitar lógica de negócio, devido ao volume e complexidade dessa lógica.

### Leitura analítica

A arquitetura parece buscar desacoplamento futuro por APIs, mas aceita reaproveitamento controlado de ativos legados quando reimplementar a lógica teria custo elevado. Essa é uma interpretação do conjunto de respostas fornecidas.

## 10.3. Publicação e versionamento de componentes

Os componentes são:

1. versionados;
2. publicados em **Azure Artifacts**;
3. consumidos por outras aplicações que necessitem deles.

A intenção é permitir reutilização entre famílias funcionais. Por exemplo, uma aplicação de tesouraria poderia usar um componente ligado a terceiros caso ele fosse necessário.

A reunião não detalha:

- critérios de publicação;
- aprovação de componentes;
- política de versionamento;
- compatibilidade entre versões;
- repositórios específicos;
- processo de rollback;
- gestão de dependências.

## 10.4. Marketplace de componentes

Foi mencionado um marketplace de componentes no qual o desenvolvedor pode:

- localizar componentes existentes;
- verificar como eles são exibidos;
- visualizar campos;
- experimentar ocultação ou exibição de campos;
- alterar obrigatoriedade;
- avaliar o resultado antes de usá-los.

A comparação feita foi com Google Play e com o Gaia Play demonstrado anteriormente, no sentido de descoberta e experimentação.

### Finalidade percebida

O marketplace foi apresentado como mecanismo de descoberta e reutilização, evitando que componentes já existentes sejam recriados desnecessariamente.

## 12. Arquitetura do TronWeb

## 12.1. Papel no ecossistema

O TronWeb integra o ecossistema RIF como uma aplicação legada associada a uma lógica de negócio “Tron”. A apresentação distingue duas áreas na base de dados ou na lógica relacionada:

- TronWeb “clássico”;
- uma parte posterior relacionada ao Neutron.

A formulação da transcrição não permite determinar com precisão se essa divisão corresponde a schemas, módulos físicos, domínios de dados ou apenas agrupamentos lógicos.

A aplicação que consome a lógica de negócio é o próprio TronWeb, além de um componente mencionado como **API Core**.

---

## 12.2. Cliente pesado Java Swing

O TronWeb é uma aplicação Java Swing com cliente pesado.

### Requisitos citados

| Aspecto | Informação apresentada |
|---|---|
| Sistema operacional do cliente | Windows |
| Tecnologia cliente | Java Swing |
| JVM exigida no cliente | Java 1.3 |
| Atualização de Java | Não viável sem problemas ou grandes mudanças de código |
| Estado atual | Processo de descontinuação |
| Evolutivos novos | Não devem ser realizados |
| Manutenção permitida | Correções de código |

A exigência de Java 1.3 foi tratada como uma limitação concreta, decorrente do modo como as telas foram desenvolvidas.

---

## 12.3. Lado servidor

No lado servidor, o TronWeb é composto por vários servlets que escutam e processam solicitações do cliente.

As solicitações incluem:

- obtenção das telas que serão executadas pelo cliente;
- operações realizadas dentro das telas;
- acesso à base de dados;
- execução de processos próprios do TronWeb.

O servidor é empacotado como um artefato **WAR** — a transcrição registra “guard”, mas o contexto de implantação em Tomcat indica que provavelmente se trata de WAR.

Esse WAR é normalmente implantado em **Tomcat**, embora a fala admita a possibilidade de implantação em servidores.

### Compatibilidade citada

| Componente | Versões mencionadas |
|---|---|
| Tomcat | 5.5 até 9 |
| JVM no Tomcat | 1.5 até 1.8, dependendo da versão do Tomcat |

---

## 12.4. Conexão com banco de dados

A apresentação destaca que o TronWeb utiliza conexão dedicada ao banco de dados.

Embora possua um pool próprio, ele mantém conexões enquanto o cliente mantém a execução do programa. Isso foi contrastado com aplicações web mais modernas, que tipicamente usariam pools de conexão em outro modelo de uso.

### Implicação analítica

Esse comportamento pode significar maior pressão sobre conexões de banco conforme aumentam os clientes ativos. Contudo, a reunião não apresentou números, incidentes ou avaliações de capacidade; portanto, isso deve ser considerado uma implicação técnica possível, não um problema quantificado no encontro.

---

## 12.5. Personalização por país

Cada país pode possuir um TronWeb próprio: uma aplicação personalizada que inclui internamente a biblioteca ou o core do TronWeb.

O projeto de país pode não conter telas próprias inicialmente, mas ainda assim executa a funcionalidade e as telas de core que vêm incluídas.

Quando há necessidade de personalização, telas específicas são adicionadas ao projeto daquele país.

### Estratégia atual para implantação em RIF

Quando um país possui TronWeb:

1. o TronWeb atual do país é tomado como ponto de partida;
2. as telas específicas são avaliadas;
3. verifica-se se ainda são necessárias;
4. busca-se minimizar a presença dessas telas no RIF;
5. o que permanecer necessário é incluído no projeto personalizado.

O TronWeb conecta à base de dados por um schema próprio de país, específico para o TronWeb.

---

## 12.6. Obtenção dinâmica de telas

O cliente TronWeb é iniciado localmente e apresenta um menu. As telas não necessariamente estão presentes localmente no cliente.

Quando o usuário seleciona uma opção:

```text
Cliente TronWeb
↓ solicita uma tela
Servidor TronWeb
↓ obtém a tela do diretório no servidor
Servidor TronWeb
↓ envia a tela ao cliente
Cliente TronWeb
↓ executa a tela
```

Esse mecanismo de o cliente pedir as telas ao servidor continua existindo no modelo atual.

---

## 12.7. Processo antigo de desenvolvimento e execução

A apresentação descreve um processo antigo no qual desenvolvimento e execução estavam fortemente conectados.

Existiam elementos chamados:

- cliente RCS de Eclipse;
- servidor RCS.

O termo “RCS” pode estar correto, mas a reunião não explica sua sigla ou tecnologia em detalhe.

Nesse modelo, uma alteração feita pelo desenvolvedor em uma tela podia ser sincronizada diretamente com o servidor. Esse comportamento ainda existiria em alguns países.

No novo modo, esse tipo de alteração em execução não é permitido. O processo passa a ser:

1. gerar o WAR;
2. incluir internamente as telas;
3. realizar o deploy do artefato;
4. impedir modificação direta das telas no ambiente executado.

## 14. Estrutura do projeto personalizado por país no TronWeb

O projeto personalizado de um país é um único projeto, dividido logicamente em duas áreas.

```text
Projeto TronWeb do país
├── Cliente
│   ├── Telas específicas do país
│   ├── Módulos funcionais
│   └── Exceções herdadas de outros contextos, quando necessárias
└── Servidor
    └── Configurações ou propriedades específicas, especialmente no BOM/Maven
```

A área cliente contém as telas específicas do país. Foi citado um exemplo associado a “Mapfre Honduras”, aparentemente identificado por um prefixo ou módulo no projeto.

Foram mencionadas exceções em que um projeto de país pode conter telas de core ou telas relacionadas a outro país, como Panamá, por peculiaridades de herança do projeto original.

A área servidor normalmente requer poucas alterações específicas do país, salvo propriedades de configuração, especialmente quando se utiliza Maven.

## 15.2. Pergunta: novos evolutivos de Neutron devem ser feitos diretamente em microfrontends?

### O que se buscava entender

O participante quis confirmar se qualquer necessidade de modificação em Neutron deveria ser transferida para a nova arquitetura.

### Resposta

Não necessariamente. Cada caso deve ser avaliado:

- um pequeno bug pode ser corrigido diretamente no Neutron;
- não faria sentido “jogar tudo fora” por uma alteração pequena;
- novos desenvolvimentos, entretanto, devem ser feitos na arquitetura de microfrontends.

### O que isso esclarece

A migração é pragmática e incremental. Não há regra de reescrita automática, mas há uma diretriz clara para novos investimentos.

## 15.3. Pergunta: microfrontends usam o back-end Java do Neutron ou são independentes?

### Resposta

A resposta foi que, em princípio, não há dependência direta. A ideia é integrar por APIs, não pela paqueteria interna.

Foram reconhecidas exceções:

- tesouraria recobre serviços existentes por um conector;
- alguns casos podem usar serviços de back-end do Neutron;
- emissão reutiliza camada e bibliotecas de back-end para aproveitar lógica de negócio existente;
- fornecedores e módulo de documentos seguem o modelo de APIs.

### O que isso esclarece

Há um princípio arquitetural de integração por contrato/API, mas a transição aceita exceções motivadas por legado e custo de reimplementação.

## 16. Limitações reconhecidas

## 16.1. Neutron

- AngularJS está fora de suporte.
- A migração para Angular 2 ou superior exigiria refazer desenvolvimentos.
- A personalização por país é cara.
- A manutenção de customizações também é cara.
- Há reutilização limitada de controllers.
- A fronteira entre front-end Java e back-end não está bem delimitada em todos os casos.
- A tesouraria ainda estava em processo de migração ou permanecia em TronWeb, conforme contexto.
- Não devem ser feitos novos front-ends ou funcionalidades novas no Neutron, nem no core nem em nível de país.

## 16.2. Microfrontends

- A arquitetura não elimina a necessidade de desenvolvimento de componentes funcionais e managers Java.
- Algumas integrações ainda dependem de serviços legados ou conectores.
- A refatoração da emissão precisa reutilizar bibliotecas existentes devido à carga de lógica de negócio.
- A transcrição não detalha mecanismos de governança de parametrizações, controle de mudanças ou validação dessas configurações.
- Não foram apresentados limites funcionais para telas dinâmicas, componentes ou cenários de personalização.

## 16.3. TronWeb

- Cliente limitado a Windows.
- Dependência de Java 1.3 no cliente.
- Atualização de Java considerada inviável sem grandes alterações.
- Tecnologia Java Swing considerada obsoleta.
- Novos evolutivos não devem ser feitos.
- Ainda pode ser necessário por país ou por processos específicos.
- Mantém um modelo de obtenção dinâmica de telas pelo cliente.
- Em alguns países, o modelo antigo de sincronização de mudanças com o servidor ainda pode persistir.

## 18. Transformações estruturais identificadas

## 18.1. Transformação tecnológica

A evolução descrita é de tecnologias mais antigas para uma base mais atual:

```text
Java Swing + Java 1.3
↓
AngularJS + Spring MVC
↓
Angular + Spring Boot + componentes versionados
```

Essa leitura é sustentada pelas tecnologias explicitamente citadas. Entretanto, a reunião não apresenta um plano completo nem um cronograma fechado para a remoção de todas as tecnologias anteriores.

---

## 18.2. Transformação de código para parametrização

O Neutron possui componentes e fluxos construídos com maior presença de código e controllers específicos. Nos microfrontends, a proposta é configurar o máximo possível:

```text
Código específico de tela
↓
Componentes funcionais reutilizáveis
+
Parametrização de composição, comportamento e fluxo
```

A mudança busca reduzir repetição de código e simplificar personalizações locais.

---

## 18.3. Transformação de integração interna para integração por APIs

A resposta sobre o uso do back-end Neutron aponta uma direção arquitetural:

```text
Dependência de componentes internos
↓
Integração via APIs
```

Há exceções temporárias ou motivadas por custo, especialmente quando existe grande volume de lógica de negócio legada.

---

## 18.4. Transformação de projeto para ativos reutilizáveis

A publicação de componentes em Azure Artifacts e a existência de marketplace apontam para uma mudança de foco:

```text
Desenvolvimento isolado por aplicação ou país
↓
Componentes descobertos, versionados e reutilizáveis
```

A reunião associa essa estratégia à redução de duplicidade e à possibilidade de reaproveitar capacidades entre famílias funcionais.

## 20. Conclusões

A reunião apresenta uma estratégia de modernização gradual dos front-ends do RIF.

O **Neutron** continua sendo parte importante do core, mas deve receber somente manutenção e evoluções pequenas quando justificadas. Novas funcionalidades devem seguir a arquitetura de **microfrontends**, que combina Angular, Spring Boot, componentes reutilizáveis, parametrização em banco de dados, managers Java e integração por APIs.

A principal proposta dos microfrontends é reduzir o custo de desenvolvimento e personalização, especialmente para países, evitando que cada adaptação resulte em uma nova massa de código difícil de manter. Componentes funcionais são desenvolvidos uma vez, versionados em Azure Artifacts e reutilizados em diversas aplicações, enquanto a tela final é composta dinamicamente por configuração.

O **TronWeb** representa o legado mais restritivo: cliente pesado Java Swing, Windows e Java 1.3. Seu uso permanece para necessidades existentes, sobretudo tesouraria e cenários específicos de país, mas não deve receber novos evolutivos e tende a desaparecer progressivamente.

A visão geral transmitida é de uma transição de front-ends monolíticos, customizados e tecnologicamente obsoletos para um ecossistema mais modular, orientado a capacidades reutilizáveis, integração por APIs e composição parametrizada de experiências de usuário.
