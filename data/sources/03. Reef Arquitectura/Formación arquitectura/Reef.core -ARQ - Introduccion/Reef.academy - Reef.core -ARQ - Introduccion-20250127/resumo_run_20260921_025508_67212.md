A sessão inaugura uma série de treinamentos sobre a arquitetura do **RIF**, com foco específico em seu **core**. A mensagem principal é que o RIF está em processo de evolução arquitetural: parte de uma base tecnológica legada, centralizada em Oracle e fortemente associada ao modelo Tron/Tron 2000, para uma arquitetura mais modular, orientada a APIs, eventos, componentes reutilizáveis, parametrização, contêineres e serviços cloud.

# 6. Camada de front-end

## 6.1. Visão geral

A apresentação identifica quatro elementos principais de front-end:

1. Tronweb;
2. Neutron;
3. GDC;
4. micro front-ends.

O componente **Fuji** atua como ponto unificado de entrada para os usuários e reduz a necessidade de múltiplas URLs ou experiências de acesso fragmentadas.

## 6.2. Tronweb

### Finalidade e situação atual

O Tronweb é apresentado como uma ferramenta antiga, existente há muitos anos na organização. A transcrição registra que foi desenvolvida em “Javasuin 1.3”, termo que provavelmente sofreu distorção pelo reconhecimento de voz. A intenção aparente é indicar uma tecnologia Java antiga, mas o nome exato da tecnologia não pode ser determinado com segurança apenas pela transcrição.

O ponto relevante é que:

- a ferramenta não recebe mais evolução funcional;
- são realizados apenas corretivos;
- restam nela as telas relacionadas à tesouraria;
- essas telas estão em processo de migração para outros front-ends;
- após a migração, a ferramenta deverá ser descontinuada.

### Limitação arquitetural

Apesar do nome “Tronweb”, foi afirmado que ela não funciona como uma aplicação web integrada pelo navegador. A sessão a descreve como um cliente, sem integração natural com os demais front-ends.

### Roadmap citado

A intenção é migrar os front-ends Tronweb do Core para outro front-end do RIF. A apresentação menciona a expectativa de concluir isso “este ano” ou, possivelmente, estender parte da iniciativa para “o ano que vem”.

Como a reunião não contém uma data absoluta, não é possível determinar com segurança a que anos de calendário essas expressões se referem.

## 6.3. Neutron

### Finalidade

O Neutron é apresentado como o front-end em que está uma grande parte do Core. Segundo a sessão:

- contém processos e famílias do Tron;
- exclui as telas de tesouraria ainda mantidas no Tronweb;
- concentrou evoluções realizadas nos últimos anos.

### Tecnologia

Foi mencionado que o Neutron é desenvolvido com:

- AngularJS;
- “ExperientMUSC” ou termo semelhante.

O segundo nome não está suficientemente claro na transcrição para ser registrado como tecnologia confirmada.

### Modelo de componentes

O Neutron foi construído com uma lógica de componentes modulares e reutilizáveis. As telas eram formadas por componentes funcionais utilizados em diferentes contextos.

Entretanto, a apresentação reconhece uma limitação: devido à arquitetura e à forma como esses componentes foram desenhados, eles não alcançaram o nível de reutilização esperado.

### Situação de manutenção

O AngularJS é descrito como uma tecnologia sem suporte. Por isso:

- não há intenção de criar novos desenvolvimentos no Neutron;
- podem ocorrer manutenções;
- pequenas evoluções podem ser feitas quando necessárias;
- os novos front-ends devem ser implementados em tecnologias mais atuais.

### Implicação

A decisão não parece ser apenas estética ou tecnológica. O problema apresentado é que atualizar o Neutron para uma versão moderna do Angular exigiria uma refatoração total. Assim, a estratégia adotada é substituir gradualmente suas responsabilidades por novos front-ends, em vez de promover uma atualização incremental direta.

## 6.4. GDC

### Finalidade

O GDC é uma ferramenta inicialmente pensada para manutenção de tabelas sem necessidade de desenvolver código específico para cada tela.

As telas são geradas dinamicamente a partir de parametrizações persistidas em tabelas. Essa configuração define, entre outros elementos:

- campos exibidos;
- obrigatoriedade;
- requisitos;
- validações;
- tipos de componentes;
- listas de valores.

A aplicação lê essa parametrização e monta a interface, permitindo consultar, inserir e validar registros.

### Tecnologia

O GDC é descrito como uma aplicação moderna, construída com:

- Angular;
- Spring Boot;
- um stack associado a “Mardor 0” ou “Mardos.0”.

O nome desse stack não pode ser confirmado com segurança pela transcrição. Ele aparece em mais de um momento e pode se referir a uma base tecnológica interna.

### Regras e validações

A apresentação diferencia dois tipos de validação:

- validações de apresentação e componentes da tela;
- validações de negócio ou funcionais, realizadas por APIs.

Isso sugere uma separação entre responsabilidade de interface e responsabilidade de negócio, embora o detalhamento técnico dessa separação não tenha sido apresentado.

## 6.5. Micro front-ends

### Estratégia

A nova direção de front-end consiste na criação de micro front-ends organizados por domínio funcional.

Foram citados como exemplos de domínios:

- emissão;
- sinistros;
- provedores;
- documentos;
- e outros.

A transcrição contém o termo “alumínio funcional”, que, pelo contexto, aparentemente se refere a **domínio funcional**.

### Papel dos países

A apresentação cita a Turquia como exemplo de país que começou a criar seus próprios front-ends. A ideia é que o país possa utilizar funcionalidades do Core e, simultaneamente, acrescentar capacidades locais necessárias.

O Core, por sua vez, fornece front-ends organizados por domínio funcional.

### Funcionamento

A proposta combina:

1. **componentes técnicos**, fornecidos pela arquitetura;
2. **componentes funcionais**, relacionados a formulários e comportamentos de negócio na interface;
3. **parametrização**, usada para compor as telas.

Os componentes técnicos podem incluir, conforme os exemplos apresentados:

- colapsadores;
- botões ou barras de ações;
- agrupadores laterais;
- outros elementos de interface.

Os componentes funcionais representam comportamentos mais ricos, tais como:

- alteração de campo que dispara atualização visual;
- exibição ou ocultação condicional de campos;
- agrupamentos de formulário;
- regras de comportamento no front-end.

A parametrização determina a composição da tela: quais formulários, listagens, ordem, dependências e demais características devem ser exibidos.

### Integração com backend

O componente responsável por renderizar a tela lê a parametrização, monta a interface e chama “managers”, descritos como classes Java que resolvem a funcionalidade do front-end. Esses managers chamam APIs para executar a funcionalidade necessária.

### Benefícios esperados

Foram destacados os seguintes benefícios:

- uso de versões mais modernas e atualizáveis;
- módulos menores;
- redução do risco de um front-end monolítico;
- ciclos de vida independentes;
- deploys mais rápidos;
- reutilização de componentes;
- maior uso de parametrização.

O Fuji é apresentado como o ponto de acesso dos usuários aos diferentes front-ends.

Seu objetivo é evitar que o usuário precise memorizar ou acessar diversas URLs para aplicações distintas.

O backend Java foi descrito como a camada intermediária entre os front-ends e a base de dados do RIF.

Os dois casos principais apresentados foram:

O Neutron Backend permite que o front-end Neutron acesse procedimentos armazenados na base de dados de forma simplificada.

A transcrição não detalha critérios objetivos para decidir quando a lógica deve estar na API e quando deve permanecer exclusivamente na base de dados.

# 8. Personalização por país e User Exit

## 8.1. Problema do modelo anterior

O modelo anterior de personalização consistia em projetos específicos que herdavam funcionalidades do Core.

Isso gerava dificuldades quando uma nova versão do Core era publicada. Mesmo com esforço de retrocompatibilidade, adaptar o código personalizado após uma atualização era complexo.

O problema é especialmente relevante porque o RIF é descrito como um sistema grande. A atualização de componentes customizados herdados do Core podia exigir ajustes e gerar risco operacional.

---

## 8.2. Novo modelo

A personalização passa a ser baseada em um mecanismo chamado **User Exit**.

Os pontos de extensão são ativados em locais concretos do código, conforme a necessidade. Quando um país precisa de personalização no backend Java, ele possui um módulo próprio de APIs para:

- implementar suas personalizações;
- criar novos serviços específicos.

### Benefícios declarados

O modelo procura permitir que:

- o Core seja atualizado de forma transparente;
- a parte personalizada não precise ser redeployada junto com o Core;
- a parte específica do país possa ser implantada sem dependência direta da implantação do Core.

### Relação de causa e efeito

```text
Projetos locais herdando o Core
  ↓
Dificuldade de atualização após novas versões
  ↓
Necessidade de reduzir dependência entre Core e customizações
  ↓
Uso de User Exit e módulos de país
  ↓
Atualização mais independente entre Core e país
```

# 9. Backend Core Oracle

## 9.1. Versão Oracle mencionada

A apresentação informa que a última versão certificada da instalação é o **Oracle 19**.

A transcrição não especifica se isso se refere ao Oracle Database 19c, embora essa seja uma possível interpretação. Para manter a fidelidade ao conteúdo, registra-se apenas que a versão citada foi “Oracle 19”.

---

## 9.2. Origem histórica: Tron 2000

O backend do RIF é descrito como derivado de um sistema existente desde a década de 1990.

Originalmente, o Tronweb operava com um único esquema chamado **Tron 2000**. Nesse esquema coexistiam:

- acesso a dados;
- lógica de negócio;
- mecanismos de consumo dessas lógicas pela aplicação;
- toda a funcionalidade do sistema.

Essa centralização trazia uma vantagem: qualquer recurso podia ser acessado a partir de qualquer ponto necessário.

Entretanto, o modelo apresentava um problema relevante: não havia clareza suficiente sobre onde terminava o acesso a dados e onde começava a lógica de negócio.

---

## 9.3. Reorganização por camadas e esquemas

A apresentação descreve uma reestruturação da programação original do Tron 2000 em novos esquemas e camadas.

Foram citados:

- esquemas de dados;
- esquemas de validação de atributos funcionais;
- esquemas relacionados à lógica de negócio;
- esquemas de serviço;
- níveis de exposição para fora da base de dados;
- níveis de orquestração de objetos;
- níveis de orquestração de atributos dos objetos;
- esquemas de integração entre a lógica original e os novos componentes.

Diversos nomes de esquemas aparecem com reconhecimento de voz imperfeito, como “DL”, “BL”, “SR”, “LSRBL” e outras combinações. A transcrição demonstra que existe uma convenção de camadas e nomenclatura, mas não permite reconstruir com segurança todos os nomes formais nem todas as responsabilidades exatas de cada esquema.

---

## 9.4. Integração entre legado e novo backend

Houve necessidade de acessar a lógica original do Tron 2000 a partir dos esquemas associados ao Neutron. Para isso, foi criado um esquema de integração.

Posteriormente, o fluxo também foi estabelecido no sentido inverso: a lógica do Tron 2000 passou a poder acessar componentes novos do backend Core.

A apresentação indica uma transição gradual, e não uma substituição imediata de toda a lógica histórica.

---

## 9.5. Restrição à alteração direta do Core

Anteriormente, países podiam desenvolver e compilar funcionalidades diretamente:

- no Tron 2000;
- ou em esquemas Core compartilhados.

Também era possível personalizar o Core por substituição de sinônimos.

Esse modelo foi considerado inadequado para uma instalação RIF com múltiplos países na mesma instância. Caso cada país substituísse sinônimos de forma própria, seria necessário criar mecanismos de roteamento — chamados de “dispatchers” na reunião — para decidir, por exemplo, qual lógica nacional usar conforme a entidade ou outro dado de contexto.

A solução adotada foi fechar a possibilidade de alterar diretamente componentes e sinônimos centrais do Core.

Quando um país precisa personalizar um fluxo, o Core passa a executar dinamicamente um procedimento ou função definido por parametrização.

### Implicação

A apresentação aponta para uma política de customização governada: o país pode estender comportamentos, mas não modificar arbitrariamente o núcleo compartilhado.

---

## 9.6. Type Records e Type Objects

### Modelo anterior

O sistema Tron 2000 utilizava um modelo lógico baseado em **type records**. Esses records estavam acoplados ao modelo físico porque suas definições eram baseadas nos tipos das tabelas.

Isso trazia uma conveniência: alterações no modelo físico podiam refletir-se automaticamente no modelo lógico.

Por outro lado, alterações destrutivas, como a remoção de elementos do modelo físico, podiam exigir refatoração completa.

### Modelo novo

No novo backend Core, são utilizados **type objects**.

A finalidade declarada é desacoplar:

- o modelo físico de dados;
- o modelo lógico utilizado para manipular informações.

### Leitura analítica

A mudança sugere um esforço de estabilizar contratos de domínio e reduzir o impacto direto de mudanças estruturais no banco sobre o restante da aplicação.

---

## 9.7. Restrições relacionadas à orientação cloud

A arquitetura define limitações para a programação no banco de dados, em razão da transição para ambientes cloud.

Foi explicitado que se deve evitar:

- acesso direto ao sistema de arquivos a partir da programação do banco;
- uso de bibliotecas como `UTL_FILE`;
- bibliotecas de acesso externo a partir da base;
- chamadas diretas a serviços externos pela programação da base de dados.

Historicamente, por exemplo, relatórios podiam ser gerados diretamente em arquivos pela programação Oracle. Esse tipo de prática deixa de ser adequado quando não há acesso direto ao sistema de arquivos.

### Motivo técnico apontado

Chamadas externas realizadas pela própria base de dados podem causar congestionamento. Se uma integração tiver problemas de desempenho, isso não afeta apenas um processo isolado: pode comprometer todos os processos que dependem da base.

Por isso, o uso é desaconselhado. A apresentação menciona que existiriam, em sessões futuras, serviços parametrizáveis para tratar determinadas invocações externas.

---

## 9.8. Esquemas de produto e acessos externos

Foi citado um esquema específico para produtos liberados pelo Core, chamado de forma semelhante a **TRPXXDL**.

Segundo a explicação:

- esse esquema não possui liberdade para acessar todos os demais esquemas;
- seu acesso à lógica Tron é limitado a pacotes ou funcionalidades chamadas de “PTD”.

O objetivo declarado é limitar e controlar quais funcionalidades podem ser utilizadas.

Também foram mencionados esquemas de acesso externo usados por programação Java. Esses esquemas:

- possuem apenas sinônimos e permissões;
- não devem armazenar objetos;
- são restringidos por razões de segurança.

Foram citados nomes ou pacotes semelhantes a:

- `TRON2000PP`;
- `NEUTRON MAPP Data Model`;
- `NEUTRON APP`.

Como a transcrição pode conter erros nos nomes, esses identificadores devem ser validados diretamente na documentação técnica ou no ambiente antes de uso operacional.

# 10. Estrutura de personalização no banco por país

A arquitetura local por país segue o mesmo princípio de separação por responsabilidades usado no Core:

- esquema de dados;
- esquema de negócio;
- esquema de serviços;
- esquema de produto;
- esquema para type objects.

A convenção citada utiliza um acrônimo de dois caracteres para representar o país, combinado com sufixos de camada, como DL, BL e SR.

A reunião não fornece uma tabela completa dos acrônimos nacionais nem a nomenclatura definitiva de todos os esquemas.

---

## 10.1. Esquema Tron 2000 por país

Para facilitar a migração de países que possuem Tron instalado localmente para uma instância RIF, foi introduzido um esquema temporário, referido como algo semelhante a `TRON2000` seguido do acrônimo do país.

O caso de Honduras foi citado como exemplo de incorporação recente desse modelo.

### Funcionamento descrito

Quando o RIF correspondente ao país é criado:

1. é feita uma “fotografia” dos objetos existentes no Tron 2000 local;
2. são criados sinônimos e permissões sobre o esquema Tron 2000 do país;
3. o esquema é usado para adaptar a lógica existente e preservar funcionamento durante a transição.

### Limitação essencial

Esse esquema é explicitamente considerado **efêmero**:

- não deve evoluir como solução permanente;
- não deve receber evolução do modelo físico;
- contém lógica herdada e acoplada ao modelo físico do Core;
- serve para facilitar a migração;
- deve ser posteriormente refatorado para a arquitetura Neutron/RIF.

### Objetivo final

O objetivo declarado continua sendo permitir a instalação de versões de Core sem que o país precise:

- refatorar seu software local;
- adaptar continuamente código próprio;
- ou alterar a lógica central compartilhada.

## 10.2. Sessões conectadas e desconectadas

### Modelo Tronweb

O Tronweb era uma aplicação de sessão conectada:

- cada usuário estabelecia uma sessão com a base;
- a sessão permanecia aberta;
- havia uso intensivo de variáveis globais em pacotes Oracle.

Esse modelo pode facilitar certos comportamentos, mas aumenta o consumo conforme cresce o número de sessões.

### Modelo novo

No modelo mais recente, a sessão é desconectada:

- cada transação solicita uma conexão de um pool;
- a conexão é usada para a transação;
- o sistema não mantém a mesma sessão de banco aberta por usuário.

### Compatibilidade com legado

Como o software antigo pode depender de variáveis globais de pacotes, a arquitetura precisa de mecanismos de compatibilidade:

1. gravar as variáveis globais em uma tabela específica;
2. restaurá-las quando uma nova transação for iniciada;
3. reconstituir o estado necessário no pacote de globais.

A transcrição não detalha a estrutura dessas tabelas, o algoritmo de restauração ou os limites de consistência concorrente desse mecanismo.

# 11. Integração por APIs

## 11.1. Papel das APIs

As APIs são apresentadas como uma das formas fundamentais de integrar sistemas ao RIF.

Seu objetivo é permitir que aplicações externas acessem funcionalidades do RIF Core de maneira:

- controlada;
- segura;
- mediada por catálogo de serviços;
- protegida da complexidade interna da plataforma.

---

## 11.2. API Core

A API Core expõe funcionalidades do Core e se comunica diretamente com o backend Oracle.

Ela usa uma linguagem próxima:

- ao modelo de dados do RIF;
- à estrutura de informação existente no Core;
- à nomenclatura própria do RIF.

A API Core é organizada por domínios funcionais. Foram citados os domínios:

- emissão;
- tesouraria;
- sinistros;
- terceiros;
- comuns.

Ela parece ser voltada principalmente a aplicações internas ou sistemas locais dos países, embora possa ser utilizada por outras aplicações.

---

## 11.3. API Batch

A API Batch é um caso especial dentro da API Core.

Ela serve para chamadas relacionadas a processos pesados, incluindo:

- serviços que retornam grande volume de dados;
- serviços com tempo de processamento elevado;
- tarefas herdadas do Tron;
- tarefas implementadas na base de dados;
- tarefas implementadas em Java.

O mecanismo oferece um serviço específico para chamar essas tarefas.

A transcrição não detalha o comportamento assíncrono ou síncrono da API Batch, tampouco informa se há fila, agendamento, persistência de status, tratamento de cancelamento ou recuperação de falhas.

---

## 11.4. API Local ou API de País

A API local representa a forma de expor personalizações específicas de um país.

Ela está associada ao mecanismo de User Exit: pontos do Core podem ser configurados para invocar serviços implementados na API local.

Esse desenho permite que a funcionalidade nacional seja conectada em pontos específicos do fluxo sem alterar diretamente o código central.

---

## 11.5. API Business

A API Business é apresentada como uma camada acima da API Core.

Seu objetivo é oferecer uma linguagem:

- mais clara;
- mais uniforme;
- menos orientada à nomenclatura do Tron;
- menos dependente da estrutura interna do Core.

Internamente, ela traduz chamadas para a API Core.

O RIF fornece:

- um catálogo de serviços;
- uma implementação padrão, chamada de “preconstruída”, responsável por fazer essa tradução.

### Leitura analítica

A API Business parece funcionar como uma camada anticorrupção ou de abstração de domínio para consumidores que não deveriam depender diretamente do modelo técnico legado do Core. Essa é uma interpretação arquitetural; a reunião não usou essa terminologia.

---

## 11.6. Capacidades transversais das APIs

Foi afirmado que as APIs já vêm “de fábrica” com:

- segurança;
- cache;
- geração de logs.

A reunião não esclarece:

- qual protocolo de segurança é utilizado para todas as APIs;
- se o cache é distribuído ou local;
- como são definidos tempos de expiração;
- onde os logs são persistidos;
- padrões de auditoria;
- versionamento;
- limites de consumo;
- SLA;
- governança de publicação.

# 13. Integração orientada a eventos

## 13.1. Conceito apresentado

Enquanto as APIs são usadas para realizar uma ação específica de forma síncrona, eventos representam fatos que já ocorreram no sistema.

Exemplos citados:

- emissão de uma apólice;
- cobrança de um recibo;
- alteração de cadastro;
- abertura de sinistro;
- resolução de controle técnico.

O RIF publica esses eventos em uma plataforma de eventos. Outros módulos ou sistemas podem consumi-los e reagir.

---

## 13.2. Objetivo: desacoplamento

A justificativa principal para eventos é o desacoplamento entre sistemas.

Em uma integração síncrona, se o serviço chamado estiver indisponível ou lento, a execução pode ficar bloqueada.

Com eventos:

- o sistema produtor publica o fato ocorrido;
- não precisa conhecer todos os consumidores;
- consumidores podem reagir de forma independente;
- a indisponibilidade de um consumidor não precisa impedir a operação original.

---

## 13.3. Plataforma citada

A plataforma de eventos é fornecida por **Confluent**, implantada em **AWS**, na região da **Irlanda**.

A transcrição menciona “resistências” e “integração pre y pro”, expressões possivelmente afetadas por reconhecimento de voz. Não é possível determinar com segurança se tratam de ambientes, topologias, alta disponibilidade ou outro conceito específico.

Os clientes acessam tópicos para publicar ou consumir eventos, com validação OAuth por meio do provedor de identidade **Azure Entra ID**.

---

## 13.4. Produção de eventos a partir do Core

A partir da versão **23.01 do RIF Core**, foi disponibilizada conectividade para gerar eventos diretamente a partir da base de dados.

Como grande parte da lógica de negócio está em PL/SQL, foi implementado um mecanismo baseado em uma fila citada como “ColasaQ”, provavelmente uma referência a uma tecnologia de filas Oracle. O nome técnico exato não deve ser assumido sem validação.

O fluxo apresentado é:

```text
Lógica PL/SQL no Core
  ↓
Fila de mensagens
  ↓
Conector
  ↓
Broker / plataforma de eventos
  ↓
Consumidores de eventos
```

Esse mecanismo também pode permitir o envio de mensagens a partir de instâncias Tron disponibilizadas localmente, desde que estejam em versões compatíveis.

---

## 13.5. Eventos disponíveis mencionados

A apresentação indica que os eventos disponíveis evoluem ao longo das versões. Foram mencionados eventos relacionados a:

- emissões;
- cotações;
- orçamentos;
- movimentos associados a controles técnicos;
- apólices;
- recibos em condição de inadimplência;
- entrada e saída de inadimplência;
- atualização de clientes;
- atualização de fornecedores;
- abertura de sinistros.

A consulta aos eventos disponíveis pode ser feita por páginas ou contratos de **AsyncAPI**, mencionados na transcrição como “SYNCAPI”.

A intenção é equivalente à documentação que uma especificação de APIs oferece no mundo síncrono, porém aplicada a eventos assíncronos.

---

## 13.6. Observabilidade de eventos

A observabilidade dos clientes de eventos é realizada com **Dynatrace**.

A plataforma monitora:

- estado dos consumidores;
- problemas de consumo;
- alertas associados a padrões de comportamento;
- criticidade dos alertas.

Conforme a criticidade, alertas podem ser direcionados para:

- canais do Microsoft Teams;
- chamadas ao operador responsável.

O objetivo declarado é obter visibilidade ponta a ponta do que ocorre na plataforma.

# 14. APIs e eventos: comparação apresentada

| Critério | APIs | Eventos |
|---|---|---|
| Objetivo principal | Executar uma ação | Comunicar que algo ocorreu |
| Tipo de interação | Síncrona | Assíncrona |
| Acoplamento | Forte | Fraco |
| Modelo de relacionamento | Ponto a ponto | Produtor publica; consumidores reagem |
| Conhecimento dos consumidores | O chamador conhece o serviço chamado | O produtor não precisa conhecer consumidores |
| Latência | Pode bloquear quem aguarda resposta | Pode ser irrelevante, conforme o caso de uso |
| Flexibilidade | Limitada pela interface publicada | Consumidores podem ser adicionados ou removidos |
| Resiliência | Menor em caso de indisponibilidade do serviço | Maior, pois eventos podem ser consumidos posteriormente |
| Complexidade destacada | Dependência de disponibilidade e tempo de resposta | Tratamento do caminho de erro |

A apresentação não trata APIs e eventos como alternativas excludentes. Elas são descritas como mecanismos complementares.

---

## 14.1. Tratamento de erros em eventos

Foi enfatizado que o caminho mais complexo em arquiteturas orientadas a eventos é o cenário negativo.

Entre as estratégias citadas estão:

- política de retentativas;
- uso de tópico de retry;
- encaminhamento para “Dead Letter”.

A transcrição registra “Natil Letter”, aparentemente uma referência a **Dead Letter** ou uma fila/tópico de mensagens não processáveis. Essa interpretação tem alta confiança contextual, mas o nome exato da implementação não foi confirmado.

A decisão de reprocessar, desistir ou encaminhar eventos para tratamento posterior depende de cada caso de uso.

# 22. Limitações e ressalvas reconhecidas

## 22.1. Limitações tecnológicas

- Tronweb é tecnologia antiga e não recebe novas evoluções funcionais.
- AngularJS, usado no Neutron, está fora de suporte.
- Neutron não deve receber novos desenvolvimentos relevantes.
- O modelo legado Tron 2000 possui lógica fortemente acoplada ao modelo físico.
- O esquema Tron 2000 por país é provisório e não deve ser evoluído como solução permanente.

## 22.2. Limitações de personalização

- Países não devem alterar diretamente sinônimos ou componentes do Core.
- Personalizações devem ocorrer por mecanismos parametrizados e User Exit.
- O modelo anterior de herança de projetos Core trouxe dificuldades de atualização.

## 22.3. Limitações de programação no banco

- Não se deve acessar diretamente o sistema de arquivos a partir da base de dados.
- Não se deve utilizar determinadas bibliotecas de acesso externo, como `UTL_FILE`.
- Chamadas diretas a serviços externos a partir do banco devem ser evitadas.
- Integrações lentas no banco podem afetar toda a plataforma.

## 22.4. Limitações de eventos

- Eventos não eliminam a necessidade de tratamento de falhas.
- O caso negativo é considerado mais complexo que o caso positivo.
- Cada caso de uso precisa definir estratégia de retentativa, retry ou Dead Letter.
- A latência pode ser irrelevante em alguns casos, mas depende do cenário funcional.

## 22.5. Limitações de informação

# 23. Riscos e desafios

## 23.1. Riscos explicitamente mencionados

| Risco | Consequência apresentada |
|---|---|
| Customização herdando diretamente o Core | Dificuldade de atualização após novas versões |
| Uso de AngularJS sem suporte | Limitação de evolução do Neutron |
| Chamadas externas pela base de dados | Congestionamento do banco e impacto sobre múltiplos processos |
| Integrações síncronas indisponíveis ou lentas | Bloqueio de funcionalidades dependentes |
| Falha de consumidor de eventos | Necessidade de recuperação, retentativa ou tratamento posterior |
| Uso excessivo de sessões e variáveis globais | Maior consumo de recursos no modelo conectado |
| Dependência de licenças do front-end documental | Necessidade de dimensionar custo de licenciamento |

## 23.2. Desafios derivados do contexto — leitura analítica

### Governança de contratos

À medida que APIs e eventos se tornam mecanismos centrais de integração, cresce a necessidade de governar contratos, versões, compatibilidade e evolução de consumidores. A reunião menciona catálogos de APIs e AsyncAPI, mas não detalha a governança desses contratos.

### Coexistência de legado e modernização

O RIF mantém convivência entre Tron 2000, Neutron, novos esquemas Oracle, APIs, micro front-ends e componentes cloud. Essa coexistência permite migração gradual, mas pode aumentar temporariamente a complexidade operacional e de conhecimento.

### Consistência de dados entre sistemas

Os casos de sincronização de terceiros, Golden Record, cotizadores, sistemas locais e bases consumidoras indicam a necessidade de gerenciar consistência eventual e recuperação de falhas. A apresentação não informa como duplicidades, ordenação de eventos, reprocessamento ou conflitos são resolvidos.

### Dependência de parametrização

A parametrização é central em GDC, micro front-ends, documentos e personalizações. Isso tende a aumentar flexibilidade, mas exige governança de configuração, controle de mudanças, auditoria e validação rigorosa. Essa é uma interpretação decorrente da arquitetura apresentada.

# 25. Conclusões principais

1. **O RIF é apresentado como uma plataforma integrada**, cujo Core Oracle é central, mas que depende de diversos satélites, front-ends, APIs, eventos e serviços externos.

2. **A modernização ocorre de maneira gradual**, preservando convivência entre Tron/Tron 2000, Neutron e novos componentes.

3. **O Tronweb está em retirada**, mantendo apenas telas de tesouraria enquanto ocorre a migração para outras soluções de front-end.

4. **O Neutron segue relevante para o Core atual**, mas não é a base para novos desenvolvimentos devido à condição de suporte do AngularJS e ao custo de uma atualização estrutural.

5. **Micro front-ends e parametrização constituem a direção preferencial para a experiência de usuário**, buscando modularidade, reutilização e ciclos de deploy independentes.

6. **O Fuji centraliza a experiência de acesso**, oferecendo autenticação, permissões, idioma, seleção de companhia e navegação integrada entre front-ends heterogêneos.

7. **A arquitetura do banco evolui para separar dados, negócio, serviço e objetos de domínio**, reduzindo o acoplamento característico do modelo Tron 2000.

8. **A personalização por país é controlada**, migrando de alteração direta e herança do Core para extensões via User Exit, parametrização e módulos específicos.

9. **APIs e eventos são complementares**: APIs executam ações síncronas; eventos comunicam fatos e habilitam reações desacopladas.

10. **A orientação a eventos é uma aposta estratégica**, aplicada a inadimplência, fornecedores, clientes, cotizadores, controles técnicos, antifraude, métricas e novos módulos.

11. **A operação cloud já está presente em diferentes modelos**, incluindo OCI para América Central e AWS com ECS, Fargate e RDS Oracle para o RIF Vida.

12. **Observabilidade, segurança e eficiência econômica aparecem como preocupações concretas**, com uso de Dynatrace, alertas, OAuth via Azure Entra ID, Okta, Kafka e redução de custos de licenciamento documental.

13. **Ainda há lacunas relevantes de documentação técnica**, especialmente sobre contratos, segurança, governança, infraestrutura, resiliência e nomes oficiais de componentes afetados pela transcrição automática.
