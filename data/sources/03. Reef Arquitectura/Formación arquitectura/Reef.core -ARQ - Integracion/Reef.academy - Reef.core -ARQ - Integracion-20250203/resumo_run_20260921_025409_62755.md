# Análise técnica e funcional — Integrações síncronas e assíncronas na plataforma RIF

## 1. Síntese executiva

A sessão da **RIF Academy** apresentou o modelo de integração da plataforma RIF, dividido em dois mecanismos complementares:

1. **APIs**, para interações predominantemente síncronas, nas quais um consumidor solicita uma operação e recebe uma resposta;
2. **Eventos**, para publicação assíncrona de fatos de negócio ocorridos no sistema, permitindo que outros sistemas reajam de forma desacoplada.

A apresentação descreve uma arquitetura em camadas que parte do core RIF — associado a componentes como Tron Web, Neutron, procedimentos armazenados e banco de dados — e expõe suas capacidades por meio de APIs REST. Sobre essas APIs de core, existe uma camada de **API de negócio**, cujo objetivo é tornar os contratos mais padronizados, compreensíveis e menos dependentes da nomenclatura interna de cada core.

Também foi detalhado o mecanismo de personalização por país. A abordagem antiga, baseada em extensão de projetos e substituição de implementações, continua possível, mas é apresentada como menos desejável devido ao impacto de atualizações do core. A direção recomendada é o uso de **user exits**, nos quais o core invoca APIs locais parametrizadas por companhia, sem exigir alteração do código do core para cada personalização.

Na parte assíncrona, foi apresentada uma plataforma de eventos baseada em **Confluent Cloud**, centralizada na AWS Irlanda. Ela utiliza tópicos, consumer groups, esquema de mensagens, controle de acesso via OAuth/OAuth2 e Azure AD, observabilidade com Dynatrace, além de padrões de retry e tratamento de mensagens com erro. O modelo busca permitir integrações reativas e desacopladas, sem transferir ao processo produtor a responsabilidade pelos pós-processamentos.

A mensagem central da reunião é que o RIF evolui para um ecossistema de integração governado, no qual:

```text
Operações síncronas
→ APIs REST com contratos definidos

Fatos de negócio assíncronos
→ eventos publicados em broker

Personalizações locais
→ APIs locais e user exits configuráveis

Governança
→ contratos, segurança, observabilidade, nomenclatura e compatibilidade
```

## 4. Problemas e necessidades identificados

### 4.1 Forte acoplamento entre consumidores e o core

As APIs de core refletem diretamente o modelo, a nomenclatura e o desenho interno do RIF. Isso é útil para comunicação interna e para exposição detalhada de capacidades do core, mas pode dificultar o consumo por aplicações externas ou por consumidores que não conhecem os conceitos internos do sistema.

**Consequência:** um consumidor externo pode precisar compreender um vocabulário excessivamente técnico ou específico do core.

**Necessidade identificada:** criar uma camada mais padronizada e legível, capaz de representar funcionalidades de negócio sem reproduzir diretamente o idioma interno do RIF.

---

### 4.2 Personalizações locais com custo de manutenção

A personalização por extensão de projetos permite que países alterem implementações ou adicionem serviços próprios. Contudo, a reunião reconhece que esse modelo pode gerar ajustes quando uma nova versão de core é publicada.

**Causa descrita:** projetos locais dependem de artefatos e contratos do core.

**Consequência:** atualizações do core podem exigir adaptações em projetos customizados de cada país.

**Direção apresentada:** adotar user exits como mecanismo preferencial de personalização, reduzindo a necessidade de modificar ou substituir implementações do core.

---

### 4.3 Necessidade de pós-processamentos sem sobrecarregar a operação principal

A emissão de uma apólice, por exemplo, não precisa ser responsável por executar todos os processos posteriores derivados daquele fato. Outros sistemas podem precisar:

- gerar documentação;
- sincronizar dados;
- notificar usuários;
- atualizar aplicações satélite;
- realizar ações de autosserviço;
- acompanhar alterações em terceiros ou fornecedores.

**Problema:** se todos esses efeitos posteriores estiverem acoplados ao processo principal, a operação fica mais rígida e potencialmente mais difícil de evoluir.

**Direção apresentada:** publicar fatos funcionais como eventos, permitindo que consumidores independentes reajam conforme sua responsabilidade.

---

### 4.4 Complexidade no tratamento de falhas assíncronas

A apresentação enfatiza que integrações por eventos trazem desacoplamento, mas não simplificam automaticamente o tratamento de erro.

Em uma API síncrona, o chamador normalmente recebe uma resposta imediata de sucesso ou falha. Em eventos, o produtor pode publicar uma mensagem e o consumidor processá-la posteriormente. Isso exige decisões explícitas para situações como:

- falha temporária;
- reprocessamento;
- bloqueio de consumo ordenado;
- descarte controlado;
- encaminhamento de mensagem para tratamento posterior;
- notificação de equipes responsáveis.

A reunião trata esse ponto como crítico: não basta projetar o “caso positivo”; é necessário definir como falhas serão identificadas, registradas, alertadas e corrigidas.

# Parte I — APIs e integrações síncronas

## 6. Modelo de APIs apresentado

A reunião organiza as APIs em níveis distintos.

| Nível | Finalidade apresentada | Relação com o core |
|---|---|---|
| API de Core | Expõe capacidades diretamente ligadas ao core RIF | Alta proximidade |

## 7. API de Core

### 7.1 Finalidade

A API de Core é apresentada como a camada que expõe a funcionalidade do próprio core RIF. Por estar profundamente conectada ao core, compartilha sua nomenclatura e seu desenho conceitual.

Ela é descrita como adequada para comunicação com o core, mas não necessariamente como a forma ideal de exposição para todos os consumidores externos.

### 7.2 Módulos funcionais mencionados

Foram citados módulos ou agrupamentos de API associados a domínios como:

- **Policy**: emissão de apólices;
- **Claims**: tramitação de sinistros;
- **Billing**: temas de tesouraria ou faturamento;
- **Party**: terceiros;
- **Common**: funcionalidades comuns;
- **RPT**: relatórios, documentação ou notificações;
- **BTC / API Batch**: processos pesados;
- APIs de fornecedores.

A transcrição afirma que há mais APIs além das ilustradas na apresentação.

### 7.3 Formas de acesso a dados e lógica existente

Conforme o serviço, a API de Core pode:

- consumir procedimentos associados ao Neutron;
- consumir procedimentos associados ao Tron Web;
- consultar diretamente o modelo de dados;
- executar queries no banco.

Isso indica que a camada de API é capaz de operar sobre mais de uma rota de acesso à lógica e aos dados existentes, conforme a necessidade do serviço ou a maturidade de sua implementação.

## 8. Arquitetura interna das APIs de Core

A implementação é apresentada como aderente à arquitetura Gaia, posteriormente incorporada ou abrangida por algo registrado na transcrição como “MAR”.

A estrutura lógica descrita é:

```text
Camada de exposição
        │
        ▼
Camada de lógica de negócio
        │
        ▼
Camada de acesso a dados
```

Além da separação em camadas, cada uma delas possui separação entre:

```text
Definição de interface
        │
        ▼
Implementação
```

### 8.1 Contrato de serviço

Os contratos são definidos por Swagger — identificado como padrão de definição de serviços — contendo:

- nome do serviço;
- URL;
- parâmetros de entrada;
- objeto de saída.

O Swagger é tratado como o contrato entre a API e quem a consome.

A partir dessa definição, interfaces podem ser geradas automaticamente.

A reunião também menciona que OpenAPI é a evolução de Swagger, e que ambos os nomes podem aparecer no contexto das APIs.

### 8.2 Controladores e lógica de negócio

A camada de implementação dos serviços usa Spring e é denominada de **Controllers**.

Esses controladores implementam os serviços expostos e delegam a lógica à camada de negócio, que por sua vez trata dados, regras e chamadas necessárias para executar a funcionalidade.

### 8.3 Implementações alternativas por configuração

A API de Core pode ter diferentes implementações para uma mesma interface de negócio, dependendo da necessidade. Foram descritas possibilidades como:

- implementação baseada em procedimentos do Tron Web;
- implementação baseada em procedimentos do Neutron;
- implementação com acesso ao modelo de dados.

A seleção pode ocorrer por configuração.

Entretanto, a reunião ressalva que nem todos os serviços necessariamente possuem todas essas implementações. Em alguns casos, apenas uma implementação foi desenvolvida e é a utilizada.

### 8.4 Particularidade do acesso via Neutron

Para procedimentos do Neutron, a orientação não é desenvolver repetidamente chamadas diretas a cada procedimento. A API utiliza o que já existe no Neutron Web, especialmente a camada mais próxima ao banco de dados.

Também foi mencionado que as camadas utilizam o modelo de objetos de negócio do Neutron.

## 10. API de Negócio

### 10.1 Motivação

A API de Negócio é apresentada como uma camada acima da API de Core. Seu objetivo é expor capacidades de forma mais legível, uniforme e padronizada.

O problema que ela procura resolver é a existência de diferentes modelos e vocabulários internos em diferentes cores. A reunião usa como exemplo a comparação entre RIF/Tron e Guidewire.

A ideia é que, caso uma organização tenha múltiplos cores, cada um com conceitos próprios, uma camada superior pode oferecer uma linguagem mais uniforme aos consumidores.

### 10.2 Responsabilidades

A API de Negócio realiza principalmente:

- exposição de contratos de negócio;
- tradução entre modelos;
- mapeamento de objetos;
- orquestração de chamadas a APIs de Core;
- chamadas a outros serviços, quando necessário;
- transformações complementares.

Ela não é apresentada como uma camada de negócio tradicional que concentra todas as regras do domínio. A própria reunião a caracteriza mais como uma camada de transformação e orquestração.

### 10.3 Fluxo lógico

```text
Consumidor externo
        │
        ▼
API de Negócio
        │
        ├─ mapeia objetos
        ├─ transforma modelos
        ├─ orquestra chamadas
        └─ aplica configurações necessárias
        │
        ▼
Clientes gerados para APIs de Core
        │
        ▼
APIs de Core
        │
        ▼
RIF / Tron / Neutron / banco de dados
```

### 10.4 Uso de MapStruct

A reunião apresenta o MapStruct como mecanismo para traduzir o modelo mais padronizado da API de Negócio para o modelo mais próximo do RIF/Tron.

Esse mapeamento é necessário porque os mesmos conceitos podem possuir estruturas e propriedades diferentes entre:

- o contrato externo ou padronizado;
- o modelo da API de Negócio;
- o modelo interno do RIF;
- o modelo associado ao Tron ou ao core.

## 11. Personalização por extensão de projetos

### 11.1 Modelo anterior ou inicialmente adotado

A personalização tradicional ocorre por meio de projetos específicos por módulo. Cada projeto local depende da API de Core correspondente.

Os países podem:

- implementar novamente uma interface de serviço;
- substituir uma implementação padrão;
- estender uma classe existente;
- sobrescrever apenas parte de um comportamento;
- estender objetos de negócio;
- criar serviços próprios.

### 11.2 Formas de alteração citadas

| Situação | Mecanismo descrito |
|---|---|
| Substituir integralmente um serviço existente | Criar nova implementação da interface e marcá-la como `Primary` no Spring |
| Alterar apenas parte de uma implementação | Estender a classe do core e sobrescrever métodos específicos |
| Estender objetos de negócio | Criar extensões dos objetos do core |
| Criar operação exclusiva de país | Definir novo serviço, contrato Swagger e implementação própria |

### 11.3 Limitação reconhecida

Quando uma nova versão do core é publicada, os projetos locais podem exigir ajustes.

Essa é a razão apresentada para recomendar a adoção do mecanismo de user exit em vez de manter a personalização concentrada em extensões de projeto.

## 12. User exits

### 12.1 Conceito

O user exit é apresentado como o novo modelo recomendado de personalização.

Nele, a API de Core possui pontos previamente preparados para chamar uma API local específica de país. A existência e o destino dessa chamada são controlados por parametrização, sem necessidade de modificar o código da API de Core a cada personalização.

### 12.2 Estrutura lógica

```text
API de Core compartilhada
        │
        │ Ponto de extensão configurado
        ▼
API local do país
        │
        ▼
Lógica de personalização local
```

O exemplo menciona Honduras e Panamá, mas esses países são utilizados como ilustração de APIs locais separadas.

### 12.3 Comunicação entre API de Core e API local

A chamada entre a API de Core e a API local pode ser:

- síncrona;
- assíncrona.

A apresentação faz uma distinção importante: essa classificação se refere à comunicação interna entre API de Core e API local, não à separação conceitual maior entre APIs externas e plataforma de eventos.

Uma chamada assíncrona pode ser usada quando a API local não precisa retornar um resultado para que a API de Core conclua sua própria operação.

### 12.4 Restrições explícitas

Foram apresentadas duas restrições principais:

1. **O método deve receber a companhia como parâmetro**  
   Como a API de Core é compartilhada entre países, a companhia é necessária para identificar qual API local deve ser chamada.

2. **Parâmetros e retornos devem ser serializáveis**  
   Como as chamadas ocorrem por HTTP, os objetos de entrada e saída precisam ser serializáveis.

A reunião observa que, em implementações reais, pode ser necessário trafegar informações adicionais além dos parâmetros estritamente equivalentes ao método de core, para garantir o tratamento correto da chamada e da resposta.

### 12.5 Benefício esperado

A principal vantagem apresentada é que uma nova release do core pode ser implantada sem exigir automaticamente adaptação da API local.

Entretanto, permanece uma condição fundamental: os contratos não podem ser alterados de forma incompatível. As interfaces dos métodos precisam ser preservadas.

# Parte II — Plataforma de eventos e integrações assíncronas

## 16. Conceito de evento

A plataforma de eventos é destinada à publicação e gestão de fatos ocorridos no sistema.

Esses fatos podem ser:

- funcionais, como emissão de apólice ou ocorrência de sinistro;
- técnicos ou operacionais, potencialmente relacionados a eventos do sistema.

Apesar disso, o foco inicial da plataforma é a publicação e gestão de **eventos funcionais**.

### 16.1 APIs e eventos são complementares

A reunião é explícita ao diferenciar os dois modelos:

| Mecanismo | Papel principal |
|---|---|
| API | Solicitar a execução de uma ação |
| Evento | Publicar que um fato já ocorreu |

Exemplo conceitual:

```text
API:
“Emita uma apólice.”

Evento:
“A apólice foi emitida.”
```

O evento permite que sistemas interessados se inscrevam, sejam notificados e executem suas próprias reações.

---

## 17. Benefícios e desafios da integração por eventos

### 17.1 Benefício principal: desacoplamento

No exemplo dado, o processo que emite uma apólice não precisa executar todos os pós-processamentos derivados dessa emissão.

Ele se responsabiliza por:

1. emitir a apólice;
2. publicar o evento correspondente no broker.

Outros sistemas podem então:

- consumir o evento;
- aplicar regras próprias;
- executar atividades complementares;
- manter evolução independente.

### 17.2 Responsabilidade distribuída

A arquitetura separa claramente:

```text
Responsabilidade do produtor
→ registrar o fato e publicar o evento

Responsabilidade do consumidor
→ reagir ao fato conforme sua finalidade
```

Essa separação evita que o processo produtor acumule responsabilidades de múltiplos sistemas consumidores.

### 17.3 Complexidade de falhas

A reunião destaca que a gestão de erros é mais complexa do que em integrações por API, porque o processamento é desacoplado e pode ocorrer sem supervisão imediata do produtor.

Padrões mencionados:

- retry;
- envio para tópico de reprocessamento;
- bloqueio de consumidor quando ordem é necessária;
- dead-letter topic/queue;
- investigação posterior por equipe responsável.

---

## 18. Plataforma tecnológica de eventos

### 18.1 Broker

A plataforma utiliza o serviço da Confluent, aparentemente **Confluent Cloud**.

A infraestrutura é descrita como:

- gerenciada pelo provedor;
- atualizada pelo próprio serviço;
- capaz de escalar ou reduzir conforme a carga;
- hospedada centralmente na AWS Irlanda;
- disponível por meio de clusters separados por ambiente.

### 18.2 Modelo de contratação

O modelo não é descrito como pay-per-use puro.

Foi citado um pagamento antecipado baseado em estimativas de consumo, por meio de “tickets” consumidos ao longo do ano.

### 18.3 Tipos de cluster mencionados

Foram mencionados:

- Basic;
- Standard;
- Enterprise;
- Dedicated.

O cluster Basic é descrito como mais barato, mas com menos funcionalidades. O Dedicated oferece mais recursos, porém com custo elevado. O Enterprise é mencionado como mais voltado a volumes muito altos de eventos.

A escolha atual foi o **cluster Standard**, por equilibrar as necessidades funcionais e o custo.

## 21. Segurança da plataforma de eventos

### 21.1 Contexto de exposição

O cluster Standard é descrito como exposto à internet.

A reunião afirma que, nesse tipo de cluster, não existe conectividade privada completa nem possibilidade de estabelecer diretamente um Private Link com o serviço.

Por isso, o acesso para publicar e consumir eventos é protegido por OAuth/OAuth2 e tokens obtidos em Azure AD.

### 21.2 Modelo de autenticação e autorização

O fluxo descrito é:

```text
Aplicação cliente
        │
        ▼
Registro de aplicação no Azure AD
        │
        ▼
Obtenção de token com role
        │
        ▼
Validação no broker de eventos
        │
        ▼
Aplicação de permissões e ACLs
```

Foram citados os seguintes conceitos:

- tenant de Azure AD;
- registro de aplicação;
- Enterprise Application;
- App ID;
- token;
- role;
- workload identity;
- identity pool;
- ACLs;
- consumer group;
- padrões de tópicos.

### 21.3 Controle granular

A plataforma permite restringir, por aplicação:

- a qual cluster pode acessar;
- quais tópicos pode ler;
- quais tópicos pode publicar;
- quais schemas pode acessar;
- quais consumer groups pode utilizar;
- se a permissão é de leitura ou escrita;
- quais padrões de tópicos e consumer groups são permitidos.

O modelo é centralizado.

### 21.4 Mudança em relação ao modelo original

Originalmente, a plataforma utilizava credenciais e API keys oferecidas pela Confluent.

A reunião indica que a adoção de OAuth/OAuth2 foi escolhida porque o serviço é exposto à internet e o objetivo era ter uma abordagem mais adequada de segurança.

## 22. Fluxo de eventos originados no banco de dados

A apresentação detalha como eventos de negócio podem sair do core baseado em banco de dados até chegarem ao broker.

### 22.1 Configuração por companhia

A solução utiliza uma tabela de definição de eventos por companhia.

A tabela é registrada na transcrição como algo semelhante a:

```text
FTR / Neutron XXE U MSG
```

O nome exato da tabela não pode ser determinado com segurança.

A definição inclui, segundo a explicação:

- identificador do evento;
- descrição;
- versão;
- destino;
- fila AQ de destino, quando aplicável;
- tópico funcional;
- programa/objeto responsável pela construção do payload;
- data de validade;
- indicador de habilitação;
- informações funcionais adicionais.

### 22.2 Destino do evento

O destino pode ser:

- uma tabela;
- uma fila AQ.

A transcrição explica que, antes da integração com a plataforma de eventos, mensagens podiam ser depositadas em uma tabela. O mecanismo atual permite direcioná-las a filas AQ específicas.

O encaminhamento é sensível à companhia. Por exemplo:

```text
Companhia de Honduras
→ fila AQ de Honduras

Companhia do Panamá
→ fila AQ do Panamá
```

### 22.3 Construção dinâmica da mensagem

Cada evento possui um programa ou objeto de definição que é executado dinamicamente para construir o conteúdo da mensagem.

As mensagens são descritas como JSON.

Esse programa é responsável por preencher a estrutura e os dados funcionais do evento.

## 23. Conector JMS e tópicos técnicos

Após a publicação da mensagem em uma fila AQ, entra em ação um conector JMS.

### 23.1 Papel do conector

O conector:

1. lê mensagens da fila AQ;
2. identifica a configuração associada ao país;
3. publica as mensagens em um tópico técnico no broker.

Há um conector JMS por país ou uma configuração específica por país.

No exemplo da América Central, foram citados:

- Panamá;
- Honduras;
- Guatemala;
- El Salvador.

A reunião afirma que haveria quatro configurações do conector JMS, pois cada país possui uma fila AQ distinta.

### 23.2 Tópico técnico

As mensagens inicialmente chegam a um tópico técnico.

Esse tópico possui um esquema descrito como uma sequência de bytes ou stream bruto. A finalidade é receber o conteúdo transportado desde a origem antes de sua transformação para um evento funcional final.

---

## 24. Transformação para tópicos funcionais

Após chegar ao tópico técnico, um componente referido como:

- splitter;
- client transform;
- transformador;

lê as mensagens e executa a transformação necessária.

### 24.1 Responsabilidades do transformador

O componente:

1. lê a mensagem do tópico técnico;
2. analisa o cabeçalho;
3. identifica o tópico funcional de destino;
4. acessa o Schema Registry;
5. constrói a mensagem de acordo com o esquema esperado;
6. publica o evento no tópico funcional correspondente.

### 24.2 Exemplo: alteração de fornecedor

Foi apresentado um exemplo de alteração nos dados de um fornecedor.

Fluxo relatado:

```text
Alteração no fornecedor
        │
        ▼
Evento publicado com cabeçalho apropriado
        │
        ▼
Fila AQ
        │
        ▼
Conector JMS
        │
        ▼
Tópico técnico
        │
        ▼
Transformador valida e direciona
        │
        ▼
Tópico funcional
        │
        ▼
Consumidor do autosserviço de fornecedor
```

O consumidor verifica se houve modificação em dados como:

- endereço de e-mail;
- informações de contato.

Dependendo do resultado:

- registra automaticamente o fornecedor no sistema de autosserviço, caso ainda não esteja registrado;
- notifica o fornecedor por e-mail;
- comunica a alteração de dados relevante.

### 24.3 Implicação operacional

A apresentação associa esse fluxo à redução de intervenção humana e à centralização das alterações no core.

> **Leitura analítica:** o caso sugere uma estratégia em que o core é tratado como fonte principal de mudanças de dados funcionais, enquanto sistemas periféricos reagem aos eventos publicados, em vez de dependerem de atualizações manuais ou integrações ponto a ponto.

## 25. Agregação e especialização de tópicos

A plataforma possui mecanismos para agrupar ou especializar eventos conforme a necessidade de consumidores.

### 25.1 Tópicos agregados

Foi citado o caso de gestão de impagos, no qual uma aplicação precisa consumir eventos de movimentos de recibos de diversos países.

A solução descrita agrega eventos de múltiplos tópicos nacionais em um tópico único voltado à necessidade funcional de gestão de impagos.

### 25.2 Uso de ksqlDB / ksql

A transcrição menciona “ksql”, possivelmente ksqlDB, como mecanismo de agregação e filtragem.

Inicialmente, houve um defeito que impedia a agregação de mensagens com determinados níveis de estrutura. Esse problema teria sido resolvido posteriormente.

O mecanismo continua sendo utilizado em cenários como:

- agregação de movimentos de recibos impagados;
- identificação de emissão de apólice;
- identificação de movimentos retidos por controle técnico.

### 25.3 Especialização de eventos

A lógica descrita é:

```text
Tópico amplo de movimentos de apólice
        │
        ├─ mensagens que representam apólice emitida
        │       └─ tópico especializado de apólice emitida
        │
        └─ mensagens retidas por controle técnico
                └─ tópico especializado de retenções técnicas
```

A finalidade é simplificar o consumo por aplicações interessadas em condições específicas, evitando que cada consumidor precise repetir toda a filtragem.

## 27. Observabilidade com Dynatrace

A ferramenta de observabilidade central para RIF é apresentada como Dynatrace.

A observabilidade não se limita à infraestrutura do broker. Também cobre o comportamento de consumidores e eventos.

### 27.1 Telemetria da Confluent

A plataforma coleta telemetria fornecida pela Confluent, aparentemente com consultas a cada minuto.

Entre os dados acompanhados estão:

- tráfego de entrada;
- tráfego de saída;
- estado de consumer groups;
- consumo por tópico;
- lag de consumidores.

### 27.2 Lag

O lag representa, no contexto apresentado, o atraso entre a disponibilidade dos eventos em um tópico e o processamento pelo consumer group.

Um lag crescente indica que uma aplicação pode estar enfrentando problemas para acompanhar a publicação de eventos.

A reunião menciona um dashboard que permite selecionar:

- tópico;
- consumer group;
- situação de consumo.

### 27.3 Limitação atual

Ainda não existiam alertas automáticos baseados no lag no momento da apresentação.

A criação desses alertas é citada como uma próxima atividade.

## 28. Métricas funcionais

A reunião descreve uma evolução no modelo de métricas funcionais.

### 28.1 Situação atual

A primeira versão consulta diretamente a base de dados central, aparentemente a cada trinta minutos, para identificar indicadores como:

- quantidade de apólices emitidas;
- quantidade de sinistros abertos.

Essas consultas são caracterizadas como pesadas.

### 28.2 Direção de evolução

A intenção é que métricas funcionais passem a se apoiar nos eventos já publicados pela plataforma.

Isso reduziria a necessidade de consultar repetidamente a base central para inferir o que ocorreu no período.

### 28.3 Alternativa avaliada: Flink

A primeira alternativa avaliada foi o uso de Flink, citado como produto do ecossistema Apache.

A proposta seria:

1. ler eventos;
2. criar janelas temporais via SQL;
3. calcular métricas por minuto ou outro intervalo;
4. publicar resultados em outros tópicos;
5. criar um cliente para encaminhar essas informações ao Dynatrace.

A reunião considera Flink potente e simples para esse objetivo, mas identificou custo elevado por métrica e por período de ativação da consulta.

### 28.4 Alternativa em teste: OpenTelemetry com Spring

Como alternativa, está sendo testado o uso da biblioteca OpenTelemetry em Spring.

O fluxo esperado é:

```text
Consumidor Spring
        │

        ▼
Construção de janelas temporais
        │
        ▼
Geração de métricas
        │
        ▼
Arquivos de métricas
        │
        ▼
Ingestão contínua pelo Dynatrace
```

A motivação declarada é simplificar a solução e reduzir custos em relação à alternativa baseada em Flink.

## 29. Tratamento de erros e alertas

A reunião apresenta um padrão de tratamento de falhas para consumidores de eventos.

### 29.1 Estratégias de processamento

Quando ocorre um erro, o consumidor pode:

- tentar novamente;
- enviar a mensagem para tópico de retry;
- bloquear o consumo, quando a ordem for essencial;
- enviar a mensagem para uma dead-letter topic/queue;
- continuar o processamento das demais mensagens;
- permitir análise posterior por uma equipe responsável.

### 29.2 Padronização de logs

Foi definido um padrão de log para os processos consumidores.

Os logs são ingeridos pelo Dynatrace, que identifica o padrão e gera alertas conforme a criticidade.

Os dados citados no padrão incluem:

- momento do evento;
- criticidade;
- consumer group;
- tópico;
- chave da mensagem;
- offset;
- ambiente;
- funcionalidade;
- servidor/IP;
- erro produzido.

### 29.3 Níveis de severidade

| Nível | Tratamento descrito |
|---|---|
| 3, 4 e 5 | Informativo |
| 2 | Relevante; requer acompanhamento e análise |
| 1 | Alta criticidade; deve acionar mecanismo mais direto |

A numeração e o significado acima foram reproduzidos conforme a explicação oral. A transcrição não detalha formalmente a taxonomia completa nem garante que todos os níveis sejam usados de forma uniforme em todos os sistemas.

### 29.4 Notificação

Alertas podem ser enviados para canais do Teams.

Para eventos de nível 1, a intenção é que, além da mensagem em canal, ocorra uma chamada ao operador responsável. Essa implementação é citada como algo que ainda será realizado.

## 30. Governança da plataforma de eventos

A documentação estaria disponível no Backstage, e os participantes afirmam que enviariam os links aos participantes após a sessão.

### 30.1 Nomenclatura

Há convenções para identificar:

- país;
- tipo de evento;
- módulo;
- domínio;
- funcionalidade.

A nomenclatura permite distinguir a origem e a finalidade de tópicos e eventos.

### 30.2 Criação centralizada

A criação de eventos e tópicos é centralizada.

Esse controle abrange:

- tópicos de core;
- replicação entre instâncias;
- criação por país;
- tópicos específicos para customizações locais.

### 30.3 Versionamento e compatibilidade de schema

Cada tópico possui um contrato ou schema.

A reunião menciona políticas de compatibilidade:

- backward;
- forward;
- full.

Para tópicos geridos pelo core, a política adotada é **full compatibility**.

A finalidade é reduzir dependência entre a versão do produtor e a versão do consumidor.

### 30.4 Restrição derivada da compatibilidade full

Como consequência, as evoluções de eventos do core são limitadas a adições compatíveis, como novos atributos opcionais.

Mudanças drásticas não devem ser feitas no evento existente. Caso sejam necessárias, devem resultar na publicação de novos eventos.

> **Leitura analítica:** a decisão privilegia estabilidade de contratos e evolução segura em um cenário com múltiplos países, múltiplos RIFs e consumidores potencialmente distribuídos. Em contrapartida, aumenta a disciplina necessária para versionar e introduzir novos eventos.

## 37. Transformações estruturais identificadas

### 37.1 Do core diretamente exposto para contratos mais padronizados

A existência da API de Negócio sugere uma transição de contratos centrados no core para contratos mais apropriados a consumidores externos ou a ecossistemas com múltiplos cores.

Isso não elimina a API de Core; cria uma camada adicional de abstração.

### 37.2 De customização por extensão para pontos de extensão governados

A recomendação de user exits indica uma direção de personalização mais controlada:

```text
Antes:
extensões e substituições locais de implementações

Direção recomendada:
pontos de extensão previstos no core, configurados por país
```

Essa leitura é sustentada pelo objetivo declarado de reduzir ajustes em projetos locais quando novas releases de core são implantadas.

### 37.3 De integração ponto a ponto para integração orientada a eventos

A plataforma de eventos cria um caminho para que um produtor publique um fato uma vez e múltiplos consumidores possam reagir sem acoplamento direto ao produtor.

### 37.4 De métricas extraídas do banco para métricas derivadas de eventos

A evolução discutida para métricas funcionais aponta para o aproveitamento da plataforma de eventos como fonte de observabilidade funcional, reduzindo consultas repetitivas ao banco central.

## 40. Riscos e desafios

### 40.1 Riscos explicitamente mencionados

- Falhas em consumidores assíncronos exigem tratamento específico;
- mensagens podem precisar de retry ou encaminhamento para dead-letter;
- consumidores podem acumular lag;
- alterações de schema são restritas pela política de compatibilidade;
- conectores gerenciados demandam gestão adequada de segredos;
- o uso de Flink pode elevar custos;
- customizações locais podem sofrer impacto de novas releases quando baseadas em extensão de projetos.

### 40.2 Desafios derivados do contexto

> Os pontos abaixo são interpretações analíticas sustentadas pela arquitetura descrita; não são afirmações literais dos participantes.

1. **Governança de contratos em escala**  
   Com múltiplos países, tópicos, APIs locais, consumers e modelos de negócio, a manutenção de contratos compatíveis tende a exigir disciplina de versionamento e documentação.

2. **Operação distribuída**  
   Embora a plataforma seja centralizada, os consumidores podem estar em contextos nacionais, funcionais ou tecnológicos diferentes. Isso pode aumentar a necessidade de monitoramento e responsabilidades claras por domínio.

3. **Tratamento consistente de falhas**  
   A existência de retries, dead-letter topics e alertas exige que cada consumidor tenha estratégia definida para falhas temporárias, falhas definitivas, ordem de processamento e reprocessamento.

4. **Custos de processamento de eventos**  
   A discussão sobre Flink mostra que soluções tecnicamente convenientes podem não ser economicamente adequadas para todas as métricas ou cargas.

5. **Coexistência tecnológica**  
   O sistema convive com Tron Web, Neutron, banco de dados, PL/SQL, APIs Java, AWS Lambda, TypeScript e Python. Essa diversidade traz flexibilidade, mas pode aumentar o esforço de padronização, suporte e governança.

## 43. O que a reunião não permite concluir

A apresentação oferece visão abrangente, mas não detalha suficientemente os pontos abaixo:

- versões exatas de Java, Spring, Confluent, Dynatrace, Oracle, Kafka ou AWS;
- topologia completa de rede;
- modelo de alta disponibilidade em nível de consumidor;
- RTO, RPO, disaster recovery ou estratégia de continuidade;
- política de retenção diferenciada por tipo de tópico;
- estratégia de backup de schemas, configurações ou tópicos;
- processo de rotação de tokens e credenciais;
- ciclo de vida de registros no Azure AD;
- modelo de segregação de funções para gestão de ACLs;
- fluxo de aprovação para criação de tópico ou novo evento;
- critérios para determinar número de partições;
- limites máximos de payload;
- garantias de ordenação;
- semântica de entrega, como at-most-once, at-least-once ou exactly-once;
- idempotência dos consumidores;
- modelo de reprocessamento de dead-letter topics;
- ownership por tópico, domínio ou consumidor;
- cobertura de testes de eventos;
- CI/CD detalhado;
- custos efetivos da plataforma;
- SLA exato mencionado;
- critério formal para classificar alertas de níveis 1 a 5;
- integração completa do marketplace;
- especificação completa da API local por país;
- lista definitiva de todos os módulos de API Core;
- tecnologia exata dos componentes denominados “PLS” ou “PLE Invoker”.

## 44. Conclusão

A reunião apresentou uma arquitetura de integração em evolução, voltada a equilibrar reutilização de capacidades de core, necessidades locais de países, padronização de contratos e desacoplamento entre sistemas.

No eixo síncrono, a arquitetura organiza APIs em camadas:

```text
API de Core
→ exposição próxima ao modelo interno

API de Negócio
→ contratos mais uniformes, tradução e orquestração

BFF/API de Canal
→ adaptação para consumidores específicos

API Local
→ serviços e extensões próprias de cada país
```

No eixo assíncrono, a plataforma de eventos permite publicar fatos funcionais e distribuir responsabilidades entre múltiplos consumidores, com mecanismos de segurança, compatibilidade, observabilidade, governança e tratamento de falhas.

A direção mais relevante identificada é a combinação de:

- contratos governados;
- personalização configurável;
- desacoplamento por eventos;
- observabilidade centralizada;
- compatibilidade entre versões;
- automação de provisionamento;
- redução de dependências diretas entre produtor e consumidor.

Ao mesmo tempo, a própria reunião reconhece que a evolução não está concluída. Permanecem iniciativas abertas relacionadas a alertas de lag, métricas orientadas a eventos, marketplace AsyncAPI, conectores gerenciados e adoção mais ampla de contratos assíncronos como fonte primária de provisionamento.
