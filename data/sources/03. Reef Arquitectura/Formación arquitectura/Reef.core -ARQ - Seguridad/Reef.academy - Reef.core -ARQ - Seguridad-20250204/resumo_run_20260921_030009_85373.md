## 4. Problemas e necessidades tratados

### 4.1 Heterogeneidade entre aplicações

As diferentes aplicações do ecossistema não utilizam exatamente a mesma propriedade de configuração ou os mesmos mecanismos de autenticação.

A reunião trata essa heterogeneidade como uma necessidade prática de documentação e padronização operacional: embora exista uma direção comum de autenticação, cada tipo de aplicação precisa ser configurado de forma particular.

**Consequência:** equipes que precisam configurar ou operar aplicações diferentes devem saber quais propriedades usar em cada uma.

---

### 4.2 Transição de modelos históricos de autenticação

Foram citados modelos legados ou em descontinuação:

- autenticação contra base de dados;
- autenticação LDAP;
- um modo específico identificado como SSEO;
- fluxos ou configurações vinculados a instalações locais.

Esses mecanismos não desapareceram completamente da explicação, mas são apresentados como modos anteriores, específicos ou depreciados em diversos casos.

**Motivação implícita:** reduzir dependência de autenticações locais e convergir para um provedor corporativo de identidade.

> **Leitura analítica:** a apresentação indica uma direção de centralização de identidade. Isso não significa que todas as aplicações já tenham concluído essa migração, pois a própria reunião descreve múltiplos modos ainda disponíveis.

---

### 4.3 Controle granular de acesso

A autenticação por si só não resolve o problema de segurança funcional. A segunda parte enfatiza que, após identificar o usuário, é preciso definir:

- em quais companhias ele atua;

- quais produtos ou ramos pode consultar ou emitir;
- quais informações pode visualizar;
- quais dados pode alterar;
- quais campos podem ser apenas lidos, ocultados ou criados sem alteração posterior.

**Consequência:** o sistema precisa combinar regras globais com configurações específicas por companhia e por usuário.

## 10. Autorização e perfilamento de usuários

## 18.1 Acesso a operações de terceiros

Usuários que gerenciam terceiros — segurados, agentes, tramitadores, supervisores, fornecedores e outras figuras — precisam de permissões correspondentes às atividades que administram.

É possível:

- autorizar atividades específicas de terceiros;
- conceder acesso amplo usando o código genérico `999`.

O código `999` é apresentado como permissão genérica para todas as atividades de terceiros, evitando o cadastro individual de dezenas de ações.

---

## 18.2 Controle de acesso à informação por estrutura comercial ou produto

O sistema permite controlar acesso a dados e operações considerando elementos como:

- estrutura comercial;
- escritório;
- agente;
- produto;
- ramo.

Exemplo conceitual extraído da explicação:

```text
Usuário autorizado para qualquer escritório,
mas apenas para o ramo de automóveis
```

Também é possível configurar restrições altamente específicas, combinando:

```text
Escritório específico
    +
Agente específico
    +
Produto específico
```

A reunião ressalta que configurações específicas exigem mais registros. Se um usuário precisa atuar em vários ramos, é necessário cadastrar uma regra para cada ramo ou combinação aplicável.

---

## 18.3 Efeito das restrições de acesso

As regras de acesso afetam o comportamento da aplicação.

Exemplos mencionados:

- na emissão, o sistema mostra apenas os ramos para os quais o usuário possui permissão;
- em consultas, caso o usuário tente acessar dados não autorizados, recebe uma mensagem de usuário não autorizado;
- em Neutron, é possível limitar o uso de determinadas opções de menu ou operações.

---

## 18.4 Controle de operações em Neutron

As opções do menu Neutron são tratadas como operações passíveis de autorização.

A configuração permite definir se um usuário pode, por exemplo:

- acessar uma opção de emissão;
- emitir apólices de determinados ramos;
- executar operações para todos os ramos por meio do código `999`.

A transcrição menciona exemplos numéricos como “311”, “300” e “100”, mas não permite determinar com segurança os códigos de ramo ou o contexto exato de cada um.

## 19. Informação parcial

A funcionalidade de **informação parcial** foi apresentada como mecanismo para ocultar dados sensíveis de determinados usuários.

O exemplo principal envolve subagentes ou trabalhadores de agentes que precisam acessar o sistema para emitir apólices e realizar consultas, mas não devem visualizar todas as informações disponíveis.

Exemplo citado:

```text
Consulta de apólice
    ↓
Ocultar informações de comissão para determinados usuários
```

O controle é feito por role:

```text
Criação do role de informação parcial
    ↓
Definição dos dados a ocultar
    ↓
Atribuição do role ao usuário
    ↓
Dados restritos aparecem vazios durante a consulta
```

---

## 19.1 Formas de ocultação

Foram descritas duas modalidades principais.

| Modalidade | Efeito |
|---|---|
| Ocultar uma propriedade ou valor específico | O campo permanece na tela, mas seu valor é apresentado vazio |
| Ocultar um bloco ou conceito lógico inteiro | O usuário não consegue sequer abrir o bloco correspondente |

Foi citado o uso de um valor genérico “todo Z” para ocultar um bloco inteiro, mas essa nomenclatura pode conter erro de transcrição.

## 20. Restrições de edição e visualização de dados de terceiros

Além da ocultação de informações, o sistema possui restrições para controlar a manutenção de dados de terceiros.

A necessidade surgiu, segundo a apresentação, em casos relacionados a México e Panamá.

Exemplos apresentados:

- dados bancários que só poderiam ser modificados por um departamento específico;
- nome e sobrenome de um segurado que, no Panamá, só poderiam ser alterados pelo departamento jurídico após sua criação.

A funcionalidade permite definir restrições por:

- atividade de terceiro;
- pessoa física;
- pessoa jurídica;
- conceito lógico;
- propriedade ou campo específico.

---

## 20.1 Tipos de restrição

| Código / tipo registrado | Significado apresentado |
|---|---|
| Oculto | Não mostra a informação |
| L | Somente leitura; não permite edição |
| C | Somente criação; permite informar inicialmente, mas não modificar depois |

O exemplo de “somente criação” foi aplicado ao nome e sobrenome: o dado pode ser preenchido na criação do terceiro, mas não pode ser modificado posteriormente.

---

## 20.2 Diferença entre informação parcial e restrição de edição

| Mecanismo | Efeito principal |
|---|---|
| Informação parcial | Oculta dados em consultas para usuários com determinado role |
| Restrição de edição e visualização | Controla visualização, leitura, criação e alteração de campos de terceiros |

A reunião deixa claro que a segunda abordagem pode afetar não apenas a consulta, mas também a manutenção do dado.

## 28.2 Desafios derivados do contexto

> Esta subseção contém análise, não afirmações literais dos participantes.

### Gestão de complexidade de perfis

A combinação entre companhias, grupos, roles, produtos, ramos, escritórios, agentes e campos específicos cria um modelo flexível, mas potencialmente complexo de administrar e revisar.

### Risco de inconsistência entre ambientes

Como diferentes aplicações usam propriedades, versões e perfis distintos, existe possibilidade de comportamento divergente entre ambientes e aplicações se não houver governança operacional consistente.

### Dependência de documentação acessível

A dificuldade relatada para acessar diagramas de dados pode impactar onboarding, suporte, desenvolvimento e análise técnica. Sem acesso confiável à documentação, pessoas podem recorrer a materiais informais, como planilhas, elevando o risco de uso de informação desatualizada.

### Transição de identidade externa

A decisão de migrar ou concentrar usuários externos em Okta pode exigir coexistência temporária com Cognito e ajustes em ativos já existentes. A transcrição não detalha como esse risco será tratado.

## 31. Conclusões

A reunião apresenta uma visão de segurança baseada em duas responsabilidades distintas e complementares:

```text
Autenticação
    = comprovar quem é o usuário

Autorização
    = determinar o que esse usuário pode fazer e visualizar
```

Para usuários internos, o Entra ID é apresentado como o centro do modelo de identidade do ecossistema RIF. A implementação, entretanto, não é totalmente uniforme no nível técnico: Neutron, TronWeb, Fuji/GDC, verticais e APIs possuem configurações, perfis e limitações próprias.

Para usuários externos, a organização informou a decisão de adotar Okta como IDP, em substituição ou evolução sobre cenários anteriormente atendidos com AWS Cognito.

No nível de autorização, o sistema dispõe de controles detalhados que permitem adaptar permissões ao contexto de companhia, função, operação, produto, ramo, escritório, agência e até propriedade de dados. Esse modelo é poderoso para atender requisitos operacionais e de segregação, mas exige configuração cuidadosa e governança consistente.

Por fim, a sessão revelou uma necessidade prática adicional: garantir que a documentação técnica — especialmente modelos de dados e diagramas físicos — esteja acessível, atualizada e centralizada para os usuários que precisam dela.
