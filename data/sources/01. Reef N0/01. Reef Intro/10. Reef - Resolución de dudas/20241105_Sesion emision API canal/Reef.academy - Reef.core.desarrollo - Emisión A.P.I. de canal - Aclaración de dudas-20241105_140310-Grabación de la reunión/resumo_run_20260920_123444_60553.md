## 1. Síntese executiva

A reunião teve como foco esclarecer dúvidas técnicas sobre a arquitetura, o funcionamento, a segurança, a extensibilidade e a operação das APIs relacionadas ao core denominado **Tron** — também referido em alguns momentos como parte de “Rift”.

A principal mensagem apresentada foi que as APIs não concentram a regra de negócio principal. Elas atuam predominantemente como camadas de exposição, integração, orquestração ou acesso técnico às capacidades já existentes nos sistemas core. A lógica mais relevante de emissão, validação, cálculo e persistência permanece dentro do próprio Tron, especialmente em processos e componentes de banco de dados mencionados como PL/SQL, procedures e tabelas internas.

A arquitetura foi explicada em três níveis:

1. **API de Tron / API técnica:** expõe funcionalidades do core de forma técnica e detalhada;
2. **API Business:** orquestra chamadas a APIs de diferentes sistemas e oferece uma visão mais simples e uniforme para consumidores externos;
3. **APIs de canal:** adapta uma capacidade complexa do core a um caso de uso específico, reduzindo a quantidade de dados exigidos do parceiro externo e preenchendo o restante por parametrização.

A sessão também evidenciou uma transformação de governança: historicamente, países podiam estender ou alterar comportamentos locais com mais liberdade. A direção atual é proteger o core e evitar modificações diretas, utilizando mecanismos controlados de extensão, chamados na transcrição de **user exit**, para preservar a robustez do produto e facilitar a identificação de responsabilidades em caso de incidentes.

## 3. Problemas e necessidades discutidos

### 3.1 Complexidade técnica do core

A emissão de uma apólice pode exigir uma quantidade muito grande de informações. Foi citado, de maneira ilustrativa, que a API técnica de emissão pode receber um JSON “gigantesco”, contendo milhares de propriedades.

Isso cria um problema para integrações externas: um banco, corretor, rastreador ou outro parceiro não deveria precisar conhecer toda a estrutura interna do core para executar uma operação simples, como cotar ou emitir um produto.

### 3.2 Necessidade de abstrair o core para parceiros externos

A solução apresentada para essa complexidade é a criação de APIs de canal. Essas APIs expõem somente os campos que fazem sentido para aquele consumidor específico.

O exemplo apresentado foi uma integração com um banco, como “Santander”, em que o parceiro poderia informar apenas dados relevantes, como:

- marca;
- modelo;
- submodelo;
- cor do veículo;
- dados da pessoa;
- demais informações indispensáveis ao fluxo acordado.

Os demais atributos necessários à emissão são definidos internamente por parametrização, com valores padrão associados àquele canal.

### 3.3 Risco de customização local excessiva

Foi reconhecido que, historicamente, os países podiam receber um projeto local de APIs e alterar comportamentos por extensão de métodos Java. Essa liberdade cria risco operacional: caso ocorra uma falha em produção, torna-se mais difícil identificar se a origem do problema está no produto core ou em uma customização local.

A necessidade decorrente é manter a capacidade de adaptação local, mas sem permitir que mudanças locais comprometam a governança e a estabilidade do produto central.

### 3.4 Desempenho em integrações compostas

A API Business pode precisar consultar diversos serviços para montar uma resposta para o consumidor. Isso introduz custos de latência de rede e pode tornar fluxos sequenciais lentos.

Foi citado que uma chamada entre API Business e API técnica pode consumir aproximadamente 200 milissegundos, sendo grande parte desse tempo atribuída à rede. Assim, vinte chamadas sequenciais poderiam representar cerca de quatro segundos de latência.

A necessidade apresentada é minimizar chamadas, usar paginação e, quando apropriado, realizar operações paralelas ou em lote.

A solução descrita organiza a exposição das funcionalidades do core em camadas com responsabilidades diferentes.

```text
Consumidores externos / canais / aplicações internas
                    ↓
          API Business e APIs de canal
                    ↓
              APIs técnicas de Tron
                    ↓
          Processos e regras do core Tron
                    ↓
PL/SQL, procedures, tabelas de buzón e tabelas reais
```

> **Representação analítica:** o diagrama acima é uma consolidação do raciocínio exposto na reunião. Não foi apresentado literalmente como um diagrama oficial.

O princípio central é que a API não deve reproduzir ou duplicar a lógica do core. Ela deve receber informações, encaminhá-las para os mecanismos internos apropriados e expor respostas de maneira tecnicamente controlada.

## 5. Arquitetura e funcionamento da emissão

### 5.1 Core transacional

Tron foi descrito como o core transacional. A lógica de negócio relevante — validações, cálculos, regras de emissão e gravação definitiva — permanece dentro desse core.

A transcrição menciona que essa lógica está em “PL”, aparentemente uma referência a PL/SQL ou a componentes equivalentes de banco de dados. Como a fonte não detalha a tecnologia formalmente, não é possível afirmar com absoluta segurança toda a estrutura tecnológica utilizada.

### 5.2 API técnica de Tron

A API técnica expõe funcionalidades do core. Para uma emissão, ela recebe uma estrutura JSON extensa, pois precisa acomodar os diferentes tipos de ramos, produtos e dados suportados pelo Tron.

Segundo a explicação apresentada, o fluxo é aproximadamente:

```text
API recebe JSON de emissão
        ↓
API grava dados em tabelas intermediárias chamadas “buzones”
        ↓
API carrega variáveis globais de operação
        ↓
API chama processo batch interno
        ↓
Processo lê os “buzones”
        ↓
Core executa validações e fluxo de emissão
        ↓
Se bem-sucedido, dados são gravados em tabelas “reais”
```

As “tabelas buzón” foram descritas como estruturas intermediárias onde a API deposita a informação recebida. As “tabelas reais” correspondem às tabelas finais de negócio, como tabelas de apólices.

### 5.3 Natureza síncrona do processo

Embora a primeira pergunta mencionasse processos assíncronos enviados a filas, o participante esclareceu que o processo de emissão descrito não é considerado assíncrono.

A chamada utiliza um processo batch, mas, conforme explicado, o comportamento é síncrono: a API aciona o processo e a emissão ocorre como parte do fluxo solicitado.

Portanto, a reunião não sustenta a conclusão de que a emissão de apólices em Tron seja uma arquitetura orientada a filas ou mensageria assíncrona.

## 6. API Business

### 6.1 Finalidade

A API Business foi apresentada como uma camada que fornece uma visão unificada das capacidades da companhia para consumidores externos.

Seu papel principal é orquestrar chamadas às APIs técnicas dos diferentes sistemas, reduzindo a necessidade de o consumidor externo conhecer:

- qual core contém cada informação;
- qual API técnica deve ser utilizada;
- como os sistemas internos estão distribuídos;
- quais diferenças existem entre produtos, países ou plataformas.

### 6.2 Exemplo de orquestração

Foi usado o exemplo de uma companhia com dois cores:

- apólices de automóvel armazenadas em Tron;
- apólices de saúde armazenadas em outro sistema.

Nesse cenário, uma operação externa como “obter apólices de um cliente” pode ser implementada pela API Business. Ela consulta os sistemas adequados e fornece uma resposta unificada ao consumidor.

### 6.3 Regras de negócio

A resposta foi explícita: a API Business não deveria concentrar regras de negócio do core.

Ela pode conter lógica de orquestração, como identificar se um recibo é simples ou se corresponde a uma nota de cargo que agrupa apólices. Com base nisso, ela direciona a chamada para a API técnica adequada.

Entretanto, validações como:

- verificar se um agente pode emitir;
- verificar se um código de marca existe;
- validar regras de produto;
- executar cálculos de emissão;

devem ocorrer no core, e não na API Business.

> **Ressalva mencionada:** existem exceções e integrações muito específicas em que alguma lógica pode ter sido adicionada às APIs. A apresentação, porém, trata isso como exceção, não como padrão arquitetural.

## 7. APIs de canal

### 7.1 Objetivo

As APIs de canal são adaptações de uma capacidade do core para um consumidor ou parceiro concreto.

Elas permitem reduzir um contrato técnico complexo a uma interface menor e mais adequada ao contexto de negócio do parceiro.

### 7.2 Parametrização

Ao configurar uma API de canal, a equipe recebe os requisitos do país ou do parceiro. No caso exemplificado para a República Dominicana, foram informados elementos como:

- código de agente;
- níveis da estrutura comercial;
- quadro de comissões;
- produto ou ramo envolvido;
- dados necessários para o canal específico.

Esses parâmetros são configurados em um módulo de parametrização. A API resultante expõe somente os dados que o canal precisa fornecer.

### 7.3 Implicação de negócio

Essa abordagem reduz a complexidade para parceiros externos e evita que elementos internos, como códigos comerciais ou configurações corporativas, precisem ser conhecidos pelo consumidor da API.

A leitura analítica possível é que a organização busca equilibrar reutilização de capacidades centrais com adaptação controlada para parceiros, países e canais.

## 11. Modelo de implementação das APIs técnicas

### 11.1 Operações de escrita e execução

Foi informado que operações `PUT` e `POST`, especialmente quando são complexas, normalmente encapsulam chamadas a stored procedures ou funções de banco de dados.

A API, nesse caso, funciona como uma camada de passagem controlada entre o consumidor e a lógica implementada no banco/core.

### 11.2 Operações de consulta

Para operações `GET` e consultas, a implementação pode ocorrer diretamente em Java, em vez de chamar procedures no banco.

A justificativa apresentada é desempenho: consultas em Java podem aproveitar dados de catálogo previamente armazenados em cache, evitando joins recorrentes para recuperar descrições de códigos.

O exemplo dado foi uma consulta de apólice que, além de retornar códigos, precisa retornar descrições compreensíveis para o consumidor, como nomes de companhias, escritórios ou estruturas comerciais.

### 11.3 Granularidade

As APIs foram descritas como unidades pequenas e específicas. O objetivo é que sejam simples, rápidas e focadas em uma capacidade.

A explicação sugere que não se busca, como regra, uma API única e pesada que devolva todos os detalhes possíveis de uma apólice. Em vez disso, o consumidor ou a camada Business pode combinar operações menores conforme a necessidade.

> **Ressalva:** o participante repetiu que existem exceções e que essa descrição não deve ser tomada como uma regra absoluta para todos os casos.

## 12. Segurança, autenticação e autorização

### 12.1 Revisão de segurança para exposição externa

Quando uma API é exposta externamente, existe uma área corporativa de segurança responsável por auditar se ela atende a critérios definidos.

A área foi chamada de “Dismas” na transcrição, mas o participante afirmou que esse seria um nome histórico e que a denominação atual seria diferente. A transcrição não informa o nome atual.

### 12.2 Tratamento de erros

Um requisito de segurança destacado é evitar a exposição de informações técnicas em mensagens de erro enviadas ao cliente final.

Não devem ser devolvidos detalhes como:

- nomes de tabelas;
- colunas;
- falhas internas de banco de dados;
- stack traces;
- mensagens técnicas de componentes inferiores;
- detalhes de infraestrutura.

Quando possível, a API deve devolver uma mensagem de negócio adaptada ao erro. Caso isso não seja possível, a informação técnica deve ser omitida.

### 12.3 Códigos HTTP

Foi informado que os códigos de erro são padronizados na API Business, com menções a:

- `2xx` para operações bem-sucedidas;
- `400`;
- `403`;
- `404`;
- `204`.

A transcrição registra “211 etc.” como exemplo de sucesso, mas essa referência pode conter erro de reconhecimento. Não é possível afirmar que esse código seja efetivamente utilizado.

### 12.4 Auditoria interna

Foi citado um projeto chamado “PK”, nome que pode estar impreciso na transcrição. Esse projeto teria sido criado para registrar invocações relacionadas a determinados dados de clientes ou requisitos de auditoria.

Segundo a explicação, registros internos podem ser gravados em arquivos para fins de rastreabilidade, não apenas para APIs, mas também para outros componentes ou front-ends da organização.

A transcrição não esclarece:

- quais dados são registrados;
- por quanto tempo são retidos;
- onde os arquivos ficam armazenados;
- quem pode consultá-los;
- quais requisitos regulatórios fundamentam esse mecanismo.

### 12.5 Autenticação das APIs técnicas

Para consumo interno, foram mencionadas três possibilidades:

1. validação por Active Directory;
2. JWT combinado com OAuth do Azure;
3. usuário bloqueado/fixo com validação básica, aplicado a países que não podem usar as outras opções por problemas de conectividade.

A terceira opção foi apresentada como menos desejável do ponto de vista de segurança.

### 12.6 Autenticação em APIs expostas externamente

Para operações expostas para consumidores externos, a autenticação básica não é considerada recomendada.

Foram citados mecanismos com identity provider, incluindo:

- Azure;
- Cognito;
- Okta, aparentemente como possível substituto do Cognito;
- OAuth;
- scopes e subscopes.

O fluxo descrito é:

```text
Cliente externo recebe credenciais
        ↓
Cliente obtém token por meio do provedor de identidade
        ↓
Gateway valida identidade e token
        ↓
Gateway ou camada de segurança aplica scopes autorizados
        ↓
API permite somente operações e dados autorizados
```

### 12.7 Autorização de acesso a dados

A autorização não se limita a permitir ou negar acesso à API. Para operações envolvendo apólices, clientes, sinistros ou terceiros, também é verificado se o usuário ou cliente autenticado tem permissão para consultar ou operar aqueles dados.

A apresentação reforçou que uma API Business não deveria permitir que um consumidor externo use numeração sequencial de apólices para consultar informações às quais não possui acesso.

## 14. Estratégia de cache

### 14.1 Dados elegíveis para cache

A estratégia de cache é utilizada para informações de baixa volatilidade, especialmente catálogos, como:

- cores;
- marcas;
- modelos;
- tipos;
- descrições de códigos;
- perfis e permissões, quando aplicável;
- estruturas de referência que não mudam frequentemente.

Não devem ser armazenados em cache dados vivos e mutáveis, como:

- clientes;
- apólices;
- endossos;
- informações operacionais que podem ser modificadas a qualquer momento.

Essa limitação foi reforçada em pergunta adicional ao fim da sessão.

### 14.2 Funcionamento do cache

O cache é preenchido sob demanda. Não foi descrito um processo assíncrono que percorra todas as tabelas de catálogo e carregue tudo antecipadamente.

O comportamento relatado é:

```text
Primeira consulta de determinado dado
        ↓
Consulta busca informação na base
        ↓
Resultado é inserido no cache
        ↓
Próximas consultas equivalentes usam o cache
```

Por exemplo, uma primeira consulta por um código de cor pode buscar a informação no banco e armazenar a associação código-descrição. A próxima consulta pelo mesmo código utiliza o valor em cache.

Uma operação que recupera toda uma tabela de catálogo pode preencher de uma vez todos os valores daquele catálogo.

### 14.3 Atualização do cache

Cada API possui uma configuração, chamada na transcrição de algo semelhante a “zero config”, que define a frequência de reinicialização do cache.

O padrão citado é reset diário à meia-noite, mas isso pode variar por país.

Também existe um serviço para limpar o cache manualmente quando ocorrer atualização de catálogo, como:

- novas marcas ou modelos;
- novos usuários;
- mudanças de permissões;
- alterações em dados de referência.

Após a limpeza, a próxima consulta volta à base de dados e recarrega o conteúdo necessário.

### 14.4 Impacto no desempenho

Foi explicado que o primeiro usuário a consultar determinada informação após a limpeza pode sofrer uma resposta mais lenta, pois aciona a recarga necessária. Os usuários seguintes se beneficiam do cache já preenchido.

## 15. Extensibilidade e proteção do core

### 15.1 Modelo histórico

As APIs possuem três camadas:

1. serviço;
2. negócio;
3. acesso a dados.

A arquitetura é baseada em interfaces Java públicas. Historicamente, isso permitia que países implementassem ou estendessem determinados métodos para alterar comportamentos.

O participante tentou mencionar um conceito de Java relacionado a extensão de métodos, mas não concluiu a terminologia. Portanto, não é possível afirmar se se referia formalmente a herança, sobrescrita, implementação de interfaces ou outro mecanismo específico.

### 15.2 Mudança de direção

A direção atual é evitar que os países alterem diretamente o comportamento das APIs core.

A motivação apresentada é preservar o produto: se um país modifica o comportamento e ocorre uma falha, torna-se difícil distinguir se o incidente pertence ao core ou à customização local.

### 15.3 User exit

Como alternativa, está sendo adotado um modelo chamado **user exit**.

Conceitualmente, o core disponibiliza pontos de saída controlados — descritos como “caixas pretas” — nos quais um país pode conectar uma lógica local sem alterar diretamente o fluxo interno do produto.

O fluxo conceitual é:

```text
Fluxo core
    ↓
Ponto de extensão controlado (user exit)
    ↓
Lógica ou serviço específico do país
    ↓
Retorno ao fluxo core
```

### 15.4 Exemplo citado

Foi apresentado um exemplo hipotético de um país que precisa validar um terceiro em um serviço governamental local antes de realizar determinada operação.

Historicamente, o país poderia modificar diretamente a API de emissão para chamar o serviço externo.

No novo modelo, o core disponibilizaria um ponto de extensão parametrizável. O país poderia configurar a chamada ao serviço local sem alterar o comportamento central da API.

### 15.5 Benefício esperado

A implicação arquitetural é separar:

- comportamento padrão e testável do produto core;
- customização local de cada país;
- dependências externas locais;
- responsabilidades por falhas.

Isso permite que os testes regressivos do core sejam executados sem depender de serviços locais e torna mais claro se uma falha ocorreu no produto ou em uma extensão específica.

## 16. Mensageria, processos assíncronos e comunicação externa

### 16.1 API Business e mensageria

A resposta foi direta: a API Business não foi apresentada como uma camada de mensageria. Seu papel é orquestrar chamadas a APIs técnicas.

A reunião não descreveu um serviço de mensageria específico associado à API Business.

### 16.2 Gestão documental e envio de comunicações

A API RPT pode estar integrada a um framework de gestão documental responsável por gerar e distribuir documentos.

Foi citado o caso de gerar uma carta e enviá-la por e-mail. Nesse cenário, a API não envia o e-mail diretamente: ela delega a operação ao framework ou sistema responsável pela gestão documental e distribuição.

### 16.3 Marketing Cloud

Foi mencionada integração com “Salesforce Marketing Cloud” — ou termo muito próximo disso, conforme a transcrição.

Em alguns países, APIs de Tron podem disparar processos batch que identificam, por exemplo, clientes aniversariantes. O processo grava informações em tabela intermediária e chama uma integração que aciona o sistema externo de marketing para gerar a comunicação ao cliente.

### 16.4 Conclusão sobre assincronismo

A reunião indica que há processos que podem envolver batch, geração documental, comunicação externa e integrações indiretas. Contudo, ela não detalha uma arquitetura geral de mensageria, filas, tópicos, eventos ou brokers.

- se há filas persistentes;
- se há eventos de domínio;
- como ocorre retry;
- como falhas são tratadas;
- quais garantias de entrega existem.

## 17. Desempenho, paginação e paralelismo

### 17.1 Paginação

APIs destinadas a front-ends ou aplicações não devem retornar volumes muito grandes de registros de uma só vez.

Foi usado o exemplo de não retornar dez mil apólices em uma única resposta. A orientação é paginar resultados, devolvendo uma quantidade adequada por página.

### 17.2 Redução de chamadas

A API Business procura reduzir o número de chamadas à API técnica porque, mesmo que a API técnica seja rápida, a comunicação de rede adiciona latência.

Em vez de consultar detalhes para cada apólice individualmente em um loop sequencial, a orientação é consultar dados em lotes quando possível.

### 17.3 Multithreading

A transcrição menciona que APIs podem utilizar múltiplos threads para operações que envolvem grande volume ou diversas chamadas.

Entretanto, a explicação também ressalta que multithreading não é automaticamente a melhor solução. Dependendo do caso, uma consulta em lote a poucas APIs pode ser mais eficiente do que abrir várias chamadas paralelas.

### 17.4 Exemplo de composição em lote

Para uma lista de vinte apólices, em vez de realizar várias chamadas por apólice, o modelo sugerido é:

```text
1. Obter as 20 apólices
2. Consultar em lote os tomadores das 20 apólices
3. Consultar em lote outra informação complementar
4. Consultar em lote um terceiro conjunto de dados
5. Combinar resultados em memória
```

A composição em memória Java é apresentada como muito mais rápida do que multiplicar chamadas sequenciais de rede.

## 18. Organização operacional e relacionamento com os países

A reunião deixou claro que a estrutura corporativa não opera diretamente como uma “produção única” centralizada. A equipe corporativa fornece capacidades, componentes, APIs e apoio aos países, enquanto os países possuem a operação local.

No caso da República Dominicana, por exemplo:

- a área local identificou uma necessidade de integração;
- a liderança local solicitou apoio;
- foram fornecidos requisitos específicos;
- a equipe configurou uma API de canal adequada ao cenário local.

Isso sugere um modelo em que o produto e suas capacidades são compartilhados, mas a adoção, a parametrização e as integrações dependem do contexto de cada país.

### Pergunta: onde encontrar diagramas de sequência de processos assíncronos de emissão?

### Pergunta: as APIs utilizam apenas JSON?

**Resposta:** operações com body, como `POST` e `PUT`, recebem JSON; os serviços também retornam JSON.

**Esclarecimento:** JSON é o padrão descrito na reunião.

---

### Pergunta: onde ficam as validações dos campos?

**Resposta:** validações de formato, obrigatoriedade e tamanho podem ser definidas no Swagger. Regras de negócio e validações de domínio ficam, em regra, dentro do core.

**Esclarecimento:** há separação entre validação sintática/contratual e regra de negócio.

---

### Pergunta: qual a finalidade das APIs RPT, VTC e SPL?

**Resposta:** RPT trata de gestão documental; VTC está associada a tarefas batch e relatórios; SPL trata de funcionalidades relacionadas a fornecedores.

**Esclarecimento:** cada API agrupa um tipo de capacidade, mas a reunião não detalha todo o catálogo de operações.

---

### Pergunta: existem diagramas de sequência dessas APIs?

**Resposta:** não existe um diagrama de sequência geral. As APIs são projetadas para serem pequenas e específicas; Swagger e leitura de código permitem entender suas operações.

**Esclarecimento:** a documentação disponível é mais contratual e técnica do que processual.

---

### Pergunta: como são protegidas as mensagens de erro?

**Resposta:** detalhes técnicos não devem ser enviados ao cliente externo. São usadas mensagens de negócio ou mensagens genéricas, além de códigos HTTP padronizados.

**Esclarecimento:** stack traces, nomes de tabelas e erros de infraestrutura devem permanecer internos.

---

### Pergunta: como o consumidor entende por que uma emissão falhou?

**Resposta:** sempre que possível, a API exposta fornece uma mensagem de negócio útil. Em caso de erro técnico interno, retorna mensagem genérica, como impossibilidade de emitir, e pode fornecer um identificador para suporte interno investigar.

**Esclarecimento:** há equilíbrio entre utilidade para o usuário e proteção de informações técnicas.

---

### Pergunta: quais mecanismos de monitoramento existem?

**Resposta:** existe uma ferramenta de monitoramento com dashboards de erros e desempenho. Também são utilizados testes regressivos automatizados em ambientes prévios.

**Esclarecimento:** monitoramento e regressão são tratados como responsabilidades complementares.

---

### Pergunta: como funciona o cache?

**Resposta:** catálogos e dados pouco mutáveis são carregados sob demanda e mantidos em cache. É possível limpar o cache quando há atualização.

**Esclarecimento:** dados de clientes e apólices não entram em cache por serem mutáveis.

---

### Pergunta: sistemas internos podem acessar diretamente APIs de Tron?

**Resposta:** sim. Há aplicações internas, especialmente cotizadores e portais, que consomem APIs técnicas diretamente.

**Esclarecimento:** isso foi justificado como decisão histórica de implementação, embora a API técnica seja menos simples para consumidores externos.

---

### Pergunta: como é controlado o acesso de clientes externos?

**Resposta:** credenciais, tokens, identity providers, scopes e subscopes determinam quais APIs e dados o consumidor pode acessar.

**Esclarecimento:** a autorização também verifica o direito de acesso aos dados solicitados.

---

### Pergunta: é possível estender APIs de Tron?

**Resposta:** sim, tecnicamente é possível; porém, a direção futura é restringir extensões diretas e usar user exits parametrizados.

**Esclarecimento:** o objetivo é preservar o core e separar claramente customização local de comportamento padrão.

---

### Pergunta: a API Business tem serviços de mensageria?

**Resposta:** não foi apresentada como camada de mensageria. Ela orquestra chamadas a APIs.

**Esclarecimento:** processos de documentação e marketing podem envolver integrações indiretas, mas não foi descrita uma plataforma de mensageria específica.

---

### Pergunta: há coleções Postman e repositórios de código disponíveis?

**Resposta:** foi informado que há documentação e materiais em um “Well Compact” ou nome similar, associado a Carolina Vacedo/Vacedos, além de repositórios em Bitbucket e projetos SoapUI.

## 23. Riscos e desafios

### 23.1 Riscos explicitamente mencionados

- Exposição indevida de detalhes técnicos em mensagens de erro;
- customizações locais comprometendo a estabilidade ou a governança do core;
- dificuldade de identificar a origem de falhas quando o comportamento foi alterado por países;
- impacto de latência de rede em orquestrações com muitas chamadas;
- uso de autenticação básica em cenários em que alternativas modernas não são viáveis;
- cache desatualizado após mudanças em catálogos ou permissões;
- ausência de rastreabilidade consolidada do canal ou parceiro que consumiu uma API técnica.

### 23.2 Desafios derivados do contexto

> **Análise derivada, não declaração literal dos participantes.**

A arquitetura depende fortemente da disciplina de separação de responsabilidades. Se a API Business começar a concentrar regras de negócio ou se as APIs de canal acumularem comportamentos específicos demais, há risco de duplicação de regras e aumento de complexidade.

Também há um desafio de equilíbrio entre granularidade e eficiência. APIs pequenas e específicas facilitam reutilização, mas podem exigir composição e aumentar a quantidade de chamadas. A camada Business precisa decidir adequadamente quando orquestrar chamadas em lote, em paralelo ou de forma sequencial.

## 24. Transformações estruturais identificadas

> Esta seção representa uma leitura analítica do conteúdo apresentado.

### 24.1 De integração técnica para integração orientada a consumidor

A API técnica de Tron foi descrita como complexa e diretamente vinculada ao core. A API Business e as APIs de canal surgem como mecanismos para transformar essa capacidade técnica em interfaces mais adequadas para parceiros e aplicações externas.

```text
Core técnico complexo
        ↓
API técnica detalhada
        ↓
Orquestração e abstração
        ↓
Interface orientada ao consumidor
```

### 24.2 De customização irrestrita para extensão governada

O modelo histórico permitia alterações locais mais diretas. O modelo futuro proposto introduz user exits e parametrização como mecanismos de extensão controlada.

```text
Extensão direta em código local
        ↓
Dificuldade de suporte e responsabilização
        ↓
Pontos controlados de extensão
        ↓
Core protegido e customização isolada
```

### 24.3 De acesso massivo a respostas paginadas e compostas

A orientação para não retornar milhares de registros de uma vez e usar paginação indica uma preocupação com desempenho e experiência de aplicações consumidoras.

### 24.4 De documentação interna detalhada para contratos de API

A documentação parece estar concentrada no contrato Swagger, enquanto detalhes de implementação dependem de leitura de código ou conhecimento interno. Isso favorece integração baseada em contrato, mas pode limitar a autonomia de quem precisa investigar o comportamento técnico profundo.

## 26. Conclusões

A reunião descreveu um ecossistema de APIs cujo objetivo não é substituir o core Tron, mas expor suas capacidades de forma organizada, segura e adaptável a diferentes consumidores.

A lógica de negócio central permanece no core. As APIs técnicas fornecem acesso a essas capacidades; a API Business integra e uniformiza a visão de múltiplos sistemas; e as APIs de canal simplificam integrações específicas por meio de parametrização.

A arquitetura apresentada enfatiza:

- separação de responsabilidades;
- segurança na exposição externa;
- ocultação de detalhes técnicos em erros;
- uso de contratos Swagger;
- validação de formato na borda e regras de negócio no core;
- cache seletivo para catálogos;
- paginação e otimização de chamadas;
- autenticação baseada em identidade e scopes;
- transição para extensibilidade controlada via user exits;
- testes regressivos e monitoramento operacional.

A principal direção estratégica identificada é a evolução de um modelo com maior liberdade de customização local para um modelo de produto mais governado, no qual o core permanece protegido e as necessidades específicas dos países são atendidas por parametrização, APIs de canal e pontos formais de extensão.
