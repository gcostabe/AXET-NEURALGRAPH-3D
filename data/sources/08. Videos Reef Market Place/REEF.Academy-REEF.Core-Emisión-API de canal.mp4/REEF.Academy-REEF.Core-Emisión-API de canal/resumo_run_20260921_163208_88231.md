# Análise estruturada — APIs de canal, API Edge, API Business e Marketplace no ecossistema TRON

> **Nota de qualidade da fonte:** a transcrição contém um volume muito alto de repetições idênticas de “¿Cómo va el trabajo con la mamá?”, provavelmente decorrentes de ruído ou falha de reconhecimento de voz. Essas repetições não trazem conteúdo analítico. A análise abaixo considera apenas os trechos semanticamente compreensíveis da reunião.  
>
> Também há termos com reconhecimento possivelmente impreciso, como “a piez”, “PDETRON”, “P2060”, “P2020”, “SIM/SIMS” e “Pibis”. Quando o contexto permite, eles são tratados como referências prováveis a **API Edge**, objetos/operações do ecossistema TRON/Neutron e **API Business**, mas sem correção silenciosa ou afirmação além do que a reunião sustenta.

## 1. Síntese executiva

A reunião apresentou um modelo corporativo para expor funcionalidades do core TRON por meio de APIs, com foco especial em **APIs de canal** voltadas a processos como emissão de apólices. A proposta busca evitar que cada canal, país ou integração externa precise operar diretamente com a terminologia, a estrutura e a complexidade interna do TRON/Neutron.

O modelo combina três elementos principais:

1. **API Edge**, descrita como uma camada com muitas operações e fortemente ligada à terminologia do core;
2. **API Business**, apresentada como uma camada de negócio que traduz ou simplifica o uso das operações para uma linguagem mais natural;
3. **APIs de canal**, desenhadas especificamente para o contexto de cada país, ramo, produto, cliente ou canal de distribuição.

A principal mensagem é que não existe um Swagger único e universal para emissão. Cada implementação define quais dados devem ser solicitados ao canal, quais serão completados por configuração e quais integrações locais serão necessárias. O objetivo é permitir integrações mais seguras, reutilizáveis e menos dependentes da estrutura interna do core.

A reunião também esclareceu que:

- o **Marketplace** é o ponto de consulta da documentação de APIs já expostas;
- há aproximadamente **600 operações na API TRON/API Edge** e aproximadamente **300 operações na API Business**, segundo números declarados durante a apresentação;
- a autenticação é mediada pelo **API Gateway**, que associa credenciais externas a um usuário TRON configurado internamente;
- a compatibilidade entre versões é tratada como preocupação corporativa, embora situações específicas de cada país possam exigir análise;
- não há, no curto prazo, um plano formal de capacitação ampla para todos os países; o suporte é direcionado quando existe uma necessidade concreta de implementação.

## 2. Contexto e antecedentes

A conversa ocorreu no contexto de uma divulgação técnica conduzida por um integrante do time corporativo de APIs, identificado na transcrição como Pablo. O público aparenta incluir profissionais de diversos países, entre eles República Dominicana, Paraguai, Brasil, México, Chile, Panamá, Peru e possivelmente Costa Rica.

O cenário apresentado indica que existe uma camada de APIs diretamente relacionada ao core, mas que sua utilização pode ser complexa. Essa complexidade decorre, entre outros fatores, da terminologia interna associada ao que a reunião chama de TRON e Neutron. Por essa razão, foi defendido um modelo em que cada implementação cria uma interface mais adequada ao domínio do canal consumidor.

A proposta não é substituir indistintamente as APIs existentes, mas construir uma camada mais compreensível e configurável sobre elas quando o objetivo for integrar canais específicos.

## 3. Problemas identificados

### 3.1 Complexidade da estrutura de dados do core

A apresentação contrasta dois modelos de troca de informação:

- um modelo mais genérico, em que atributos são enviados como pares de código e valor;
- um modelo mais específico ao negócio, em que os campos são expostos diretamente com nomes compreensíveis.

Como exemplo, foram citados campos equivalentes a marca e modelo. No formato associado ao core, o consumidor precisaria enviar algo como um código de atributo e seu valor. No formato de negócio, os dados podem ser apresentados como `brand code` e `model code`.

A consequência apontada é que consumidores das APIs teriam de conhecer estruturas internas, códigos e terminologia do core para realizar integrações que, do ponto de vista do canal, poderiam ser mais simples.

### 3.2 Duplicação de exposição para diferentes consumidores

Foi explicado que um mesmo ramo — a transcrição registra “ramo 308” — não precisa ser implementado em três serviços diferentes para três consumidores distintos. A alternativa apresentada é um serviço único com comportamento adaptado por **pré-configuração**.

A ideia é que cada canal envie apenas as informações que realmente possui. Os dados que não serão enviados pelo canal podem ser preenchidos por configuração, desde que sejam conhecidos e fixos para aquele contexto operacional.

### 3.3 Risco de exposição indevida de dados operacionais

A reunião destacou que informações como o usuário TRON, códigos de canal, códigos de agente ou níveis da estrutura comercial não devem ser fornecidas diretamente por um canal externo como parâmetros livres.

A preocupação explícita é de segurança: se um consumidor externo pudesse informar diretamente um usuário TRON, poderia tentar se passar por outra identidade apenas conhecendo esse identificador.

### 3.4 Dificuldade para descobrir APIs existentes

Participantes relataram dificuldade em identificar se determinada funcionalidade já existe nas APIs corporativas antes de criar uma API interna ou uma nova solução local.

A dificuldade parece estar relacionada a:

- grande volume de operações disponíveis;
- documentação ainda insuficiente para algumas necessidades;
- distância entre os nomes técnicos/estruturais e a necessidade de negócio;
- incerteza sobre qual dado ou tabela interna está por trás de determinada resposta.

A própria apresentação reconhece que a documentação é um ponto a melhorar em nível corporativo.

## 4. Solução apresentada

A solução apresentada pode ser entendida como um modelo de exposição em camadas.

### 4.1 Camada de core: API TRON / API Edge

A API Edge foi descrita como a camada que disponibiliza operações vinculadas ao core TRON e à terminologia Neutron. Ela oferece um conjunto amplo de operações, mas pode ser difícil de consumir diretamente, especialmente para equipes sem familiaridade aprofundada com o modelo interno.

A reunião cita que essa camada possui aproximadamente 600 operações.

### 4.2 Camada de negócio: API Business

A API Business foi apresentada como uma camada que expõe operações em uma linguagem mais natural e orientada ao domínio funcional. Em vez de obrigar o consumidor a trabalhar com estruturas e termos internos do core, ela busca oferecer operações semanticamente mais compreensíveis.

A apresentação informa que há aproximadamente 300 operações nessa camada e que novas operações continuam sendo adicionadas.

### 4.3 Camada específica de integração: APIs de canal

As APIs de canal são o elemento central da sessão. Elas não são apresentadas como um catálogo padronizado já pronto para todos os países, mas como interfaces construídas conforme a necessidade de cada implementação.

Uma API de canal pode:

- receber somente os dados relevantes ao consumidor;
- preencher automaticamente dados fixos por meio de pré-configuração;
- adaptar a estrutura da requisição ao ramo ou produto;
- aplicar informações operacionais relacionadas ao canal autenticado;
- chamar APIs do core por meio de bibliotecas e mapeamentos internos;
- incorporar extensões locais quando o país possuir tabelas, validações ou dados adicionais.

## 5. Modelo lógico de funcionamento

A reunião não apresentou um diagrama completo reproduzível a partir da transcrição, mas permite consolidar o seguinte fluxo lógico.

> **Representação analítica consolidada; não é uma reprodução literal do diagrama exibido.**

```text
Canal externo, portal ou autosserviço
        ↓
Login com credenciais externas
        ↓
API Gateway
        ↓
Associação configurada entre a identidade externa e um usuário TRON
        ↓
API de canal específica da implementação
        ↓
Pré-configuração por canal/usuário
        ↓
API Business e/ou API Edge
        ↓
Core TRON
        ↓
Integrações ou extensões locais do país, quando necessárias
```

### 5.1 Entrada de dados

A API de canal recebe os dados que o consumidor efetivamente conhece e precisa informar. O modelo apresentado evita, quando possível, que o consumidor envie listas genéricas de pares “código–valor”.

### 5.2 Complementação por pré-configuração

A pré-configuração completa informações necessárias para a operação, mas que não devem ou não precisam ser enviadas pelo canal. Foram citados exemplos como dados comerciais e códigos necessários para emissão.

Essa configuração também permite que um mesmo serviço seja usado por consumidores diferentes sem que eles precisem manipular os códigos operacionais uns dos outros.

### 5.3 Mapeamento para o core

Uma biblioteca é utilizada para associar os campos de negócio aos códigos ou estruturas esperadas pelo core. No exemplo citado, o campo `brand code` é associado a um campo referido como `code marca`.

A apresentação afirma que essa biblioteca é capaz de construir, a partir de uma definição mais simples, uma estrutura interna maior relacionada a uma operação que a transcrição chama de “P2020”.

### 5.4 Chamada às APIs internas

Após completar e mapear os dados, a API de canal chama as APIs do ecossistema TRON. A apresentação recomenda que países e equipes evitem atacar diretamente a camada mais complexa quando o modelo API Business + API de canal for aplicável.

## 6. Estrutura dos dados e desnormalização

Um ponto técnico importante da reunião foi a defesa de uma estrutura de dados mais plana e compreensível para o canal consumidor.

Foi mencionado que, em uma estrutura tradicional, poderia existir um array de “dados variáveis” com diversos itens de código e valor. O exemplo usa marca e modelo para ilustrar o problema.

Em vez de exigir uma entrada genérica como:

```text
código: marca
valor: valor da marca

código: modelo
valor: valor do modelo
```

a API de canal pode expor atributos diretamente relacionados ao domínio, como:

```text
brand code
model code
```

A explicação apresentada é que essa “aplanagem” ou desnormalização simplifica a integração e torna a API mais próxima da linguagem de negócio.

### Limite importante

A reunião não detalha:

- o contrato exato dos campos;
- os tipos de dados;
- os esquemas completos de requisição e resposta;
- o mecanismo técnico da biblioteca de transformação;
- a tecnologia usada para implementar essa biblioteca.

Portanto, não é possível concluir se a transformação ocorre por serialização, regras de mapeamento, metadados, banco de configuração, código compilado ou outro mecanismo.

## 9. Autenticação, identidade e segurança

### 9.1 Princípio apresentado

A identidade operacional não deve ser controlada pelo consumidor externo da API. Em vez disso, ela é resolvida pelo API Gateway com base no login realizado.

### 9.2 Fluxo descrito

1. O usuário ou canal realiza login com credenciais externas.
2. O login pode ocorrer, conforme exemplos citados, em Azure AD ou em um diretório ativo.
3. O Gateway consulta uma configuração que associa aquela identidade externa a um usuário TRON.
4. O Gateway injeta ou fornece o usuário TRON à camada interna.
5. A API de canal utiliza esse usuário para localizar a pré-configuração correspondente.
6. A chamada ao core ocorre com as informações operacionais necessárias.

### 9.3 Implicação de segurança

A reunião rejeita explicitamente a ideia de solicitar ao usuário externo que informe o usuário TRON ou códigos sensíveis como parâmetros. Isso reduziria a segurança porque permitiria tentativa de suplantação de identidade.

### 9.4 Dados comerciais e operacionais

A explicação indica que dados como:

- código de canal;
- código de nível comercial;
- código de agente;
- estrutura comercial;
- percentuais de comissão;

podem ser estabelecidos internamente com base no canal autenticado e em sua pré-configuração, em vez de virem livremente na requisição externa.

A transcrição registra referências a “code canal 3” e “code nivel 3”, mas não fornece definição oficial desses códigos ou sua estrutura de governança.

## 10. Extensibilidade e personalizações locais

A reunião deixa claro que o modelo não elimina as particularidades locais. Quando um país possui tabelas próprias, validações adicionais ou necessidades específicas, a solução pode ser estendida.

### 10.1 Caso citado: República Dominicana

Na implementação da República Dominicana, ao inserir informações de terceiros, além dos dados do core, era necessário preencher estruturas adicionais locais.

A transcrição menciona que essas estruturas poderiam estar relacionadas a validações e a verificações associadas a arquivos ou processos de prevenção à lavagem de dinheiro. Contudo, o apresentador afirma não ter certeza sobre o detalhe específico da validação.

Portanto, o fato sustentado é:

- havia uma necessidade local adicional no processo de preenchimento de dados de terceiros;
- foi implementada uma operação própria do país na API Edge;
- a lógica de negócio da biblioteca foi estendida;
- o processo de emissão passou a preencher também uma estrutura local ligada ao terceiro.

Não é possível afirmar com segurança:

- qual era exatamente a tabela local;
- qual regra de negócio ela atendia;
- se a finalidade era, de fato, prevenção à lavagem de dinheiro;
- qual sistema externo ou arquivo estava envolvido.

### 10.2 Implicação arquitetural

Uma leitura analítica possível é que o modelo procura equilibrar padronização corporativa e extensão local: o fluxo principal pode usar APIs e bibliotecas comuns, enquanto necessidades específicas são incluídas em pontos de extensão.

Essa leitura é uma interpretação do desenho apresentado, não uma afirmação literal de uma política arquitetural formal.

## 11. Processo sugerido para uma implementação de emissão

A apresentação propõe uma sequência de implantação.

### 11.1 Definir o que será exposto

O primeiro passo é decidir como o ramo será exposto ao mundo externo, ou seja, quais informações devem ser disponibilizadas para que a emissão seja possível.

### 11.2 Desenhar o serviço

Em seguida, é necessário desenhar a API e definir:

- os campos que serão solicitados;
- os campos que não farão parte da interface externa;
- a pré-configuração necessária para completar a operação.

### 11.3 Analisar clientes e canais

O terceiro passo é analisar quais canais ou consumidores utilizarão a emissão e com quais informações eles efetivamente conseguem operar.

A apresentação reforça que, em geral, o canal fornecerá menos informação do que o conjunto máximo exigido pelo core.

### 11.4 Criar pré-configurações por canal

Para cada canal, devem ser configurados os valores que aquele canal não enviará, mas que são obrigatórios ou invariáveis para sua operação.

### 11.5 Expor a API por meio do Gateway

Por fim, o serviço deve ser publicado com apoio da camada de exposição e autenticação, permitindo que canais sejam habilitados de maneira controlada e segura.

## 15. Swagger e padronização dos contratos

Uma pergunta tratou da disponibilidade de links Swagger para os serviços demonstrados.

Cada país e cada implementação define o seu contrato conforme:

- ramo;
- tipo de produto;
- informações necessárias;
- características do canal;
- regras de preenchimento;
- particularidades locais.

O caso da República Dominicana foi usado para mostrar que diferentes ramos podem exigir estruturas bastante distintas. Um produto de viagem pode precisar de destino, duração e plano; um produto de automóvel pode exigir dados diferentes para tomador, condutor e segurado.

A camada comum, portanto, não é um contrato universal de emissão. O elemento reutilizável é a capacidade de integrar mais rapidamente com o core por meio das camadas, bibliotecas e mecanismos apresentados.

## 16. Governança e suporte corporativo

### 16.1 Papel do time corporativo

O time corporativo de APIs se posiciona como apoio às implementações concretas dos países.

O discurso não indica que os países devam, isoladamente, criar integrações complexas diretamente contra a API Edge. A orientação é trabalhar com o modelo de APIs de negócio e de canal, com apoio corporativo quando houver necessidade real.

### 16.2 Modelo de capacitação

Não há, no curto prazo, uma iniciativa formal de treinamento amplo para todos os países.

A divulgação tem uma finalidade de conscientização: informar que a funcionalidade existe e que os países podem procurar o time quando tiverem uma necessidade concreta.

O apoio pode incluir:

- análise de viabilidade;
- orientação sobre APIs existentes;
- apoio para exposição de serviços;
- ensino do uso das APIs;
- promoção de autonomia para criação de APIs de canal.

### 16.3 Governança de evolução

A reunião afirma que existe uma preocupação corporativa com retrocompatibilidade nas evoluções de APIs e versões de SIM/SIMS.

Entretanto, isso não significa garantia absoluta de ausência de impactos. Se uma implementação local tiver particularidades ou conflitos específicos, será necessário tratá-los no contexto daquela implantação.

## 18. Perguntas e respostas relevantes

### 18.1 Há documentação das propriedades e seus significados?

**Pergunta:** como identificar o significado das propriedades, especialmente para futuras personalizações e desenvolvimentos?

**Resposta:** existe um dicionário de terminologia Neutron que permite relacionar propriedades de objetos a conceitos, colunas e tabelas.

**O que isso esclarece:** há um mecanismo documental para compreender a correspondência entre a estrutura exposta e a estrutura interna do core, embora a reunião não informe onde esse dicionário fica disponível, qual seu formato ou como acessá-lo.

---

### 18.2 É possível usar dados e tabelas locais de um país?

**Pergunta:** como lidar com tabelas criadas localmente que continuam necessárias, por exemplo em processos de emissão batch?

**Resposta:** a camada referida como API Edge pode ser estendida, assim como a biblioteca de mapeamento. A República Dominicana foi citada como caso em que uma extensão local foi criada para preencher dados adicionais de terceiros.

**O que isso esclarece:** o modelo não exige que todo dado local seja removido. Ele prevê extensões quando a necessidade local for justificada.

---

### 18.3 Haverá capacitação para os países?

**Pergunta:** existe plano de treinamento de curto prazo para que países conheçam todas as APIs e aprendam a implementá-las?

**Resposta:** não há uma iniciativa de capacitação ampla de curto prazo. A divulgação serve para tornar a funcionalidade conhecida. Quando existir uma necessidade real, o time corporativo pode apoiar a implantação e ensinar o uso necessário.

**O que isso esclarece:** o modelo de adoção é predominantemente orientado por demanda e caso concreto, não por treinamento massivo antecipado.

---

### 18.4 Há links Swagger prontos para os serviços de emissão?

**Pergunta:** os links Swagger dos serviços mostrados estão disponíveis?

**Resposta:** não existe um Swagger universal. O Swagger apresentado foi montado para a demonstração. Cada país define seu próprio contrato de emissão.

**O que isso esclarece:** a reutilização está na arquitetura e nos componentes de integração, não em um único contrato de requisição aplicável a todos os ramos e países.

---

### 18.5 Existem APIs para sinistros?

**Pergunta:** as APIs de sinistros chegaram a ser desenvolvidas?

**Resposta:** sim. Há operações de sinistros na API TRON/API Edge e uma versão simplificada na API Business para abertura de sinistros.

**O que isso esclarece:** o ecossistema não se limita à emissão; ele também contempla ao menos a abertura de sinistros.

---

### 18.6 Como funciona a autenticação de um intermediário externo?

**Pergunta:** se um intermediário integrar sua própria plataforma para emitir apólices, ele usará usuário TRON e enviará dados como comissão ou identificação comercial?

**Resposta:** o canal externo não deve enviar o usuário TRON. O login externo é tratado pelo Gateway, que associa a identidade autenticada a um usuário TRON configurado. A pré-configuração desse usuário define as informações comerciais e operacionais necessárias.

**O que isso esclarece:** a identidade do consumidor é resolvida no backend; dados críticos não devem ser expostos como parâmetros controláveis pelo integrador externo.

---

### 18.7 Uma atualização de versão impactará APIs já implantadas?

**Pergunta:** a implementação de uma nova versão de SIM/SIMS no Peru impactará a API Business já implantada?

**Resposta:** a expectativa é que não, pois as APIs são evoluídas considerando retrocompatibilidade. Contudo, conflitos específicos decorrentes da implementação local precisam ser analisados caso ocorram. Foi recomendada a atualização da API Business para a versão mais recente.

**O que isso esclarece:** há uma diretriz de compatibilidade, mas a reunião não oferece uma garantia técnica absoluta para todos os cenários.

---

### 18.8 Como evitar duplicar uma API que já existe?

**Pergunta:** como equipes locais podem ter certeza de que uma funcionalidade ainda não existe na API TRON antes de construir algo novo?

**Resposta:** o Marketplace é o principal recurso atual, complementado pelos Swagger e pelo suporte do time corporativo. Uma busca assistida por inteligência artificial está em desenvolvimento para facilitar esse processo.

**O que isso esclarece:** o problema é reconhecido, mas a solução futura baseada em IA ainda não está disponível.

## 19. Limitações reconhecidas

A reunião reconhece, explícita ou implicitamente, diversas limitações.

1. **Não há Swagger universal para emissão.** Cada contrato precisa ser definido conforme o país, ramo e canal.
2. **Não há capacitação ampla de curto prazo.** O apoio é fornecido conforme demanda concreta.
3. **A documentação ainda precisa evoluir.** O Marketplace é útil, mas não elimina todas as dificuldades de descoberta e entendimento.
4. **A busca por inteligência artificial ainda é futura.** Ela é apresentada como algo em desenvolvimento, não como funcionalidade disponível.
5. **A API Edge é complexa.** Seu uso direto exige maior entendimento da terminologia e do modelo interno.
6. **Extensões locais podem ser necessárias.** Países com dados ou validações próprias precisam avaliar adaptações específicas.
7. **A retrocompatibilidade não elimina a necessidade de análise local.** Conflitos entre versões e implementações particulares podem exigir tratamento.
8. **Os detalhes de implementação não foram apresentados.** Não há informação suficiente sobre infraestrutura, redes, segurança operacional, CI/CD, observabilidade ou persistência.

## 20. Riscos e desafios

### 20.1 Riscos explicitamente mencionados

- **Suplantação de identidade:** permitir que o canal externo informe diretamente um usuário TRON seria uma falha de segurança.
- **Duplicidade de desenvolvimento:** equipes podem criar APIs locais para capacidades já existentes se não conseguirem localizar a funcionalidade corporativa.
- **Conflitos de atualização:** apesar da intenção de retrocompatibilidade, uma implementação específica pode apresentar conflitos ao atualizar versões.
- **Complexidade de integração:** atacar diretamente a API Edge pode aumentar a dificuldade, especialmente para equipes que não dominam a terminologia do core.

### 20.2 Desafios derivados do contexto

> Os pontos abaixo são leituras analíticas derivadas da reunião, não afirmações literais dos participantes.

- A personalização por país melhora a adequação ao negócio, mas pode demandar governança para evitar contratos excessivamente divergentes.
- A necessidade de extensões locais sugere que a padronização corporativa precisa conviver com particularidades regulatórias, comerciais ou operacionais de cada país.
- A estratégia de pré-configuração reduz a quantidade de dados exigidos dos canais, mas aumenta a relevância da gestão correta de configurações e identidades.
- A existência de centenas de operações torna a descoberta de APIs um problema de governança de catálogo, documentação e experiência do desenvolvedor.

## 21. Transformações identificadas

### 21.1 Do core técnico para APIs orientadas ao negócio

A direção apresentada é de afastar os consumidores da terminologia e da estrutura interna do core, oferecendo contratos mais próximos da linguagem de negócio.

Isso não significa que o core deixa de existir ou que a API Edge será eliminada. A indicação é de que a API Business e as APIs de canal podem reduzir a exposição direta à complexidade interna.

### 21.2 De integração rígida para integração configurável

O uso de pré-configurações sugere uma mudança de um modelo em que cada consumidor precisaria montar toda a requisição para um modelo em que o canal envia apenas aquilo que realmente domina.

A consequência esperada, segundo a lógica apresentada, é reduzir a necessidade de múltiplos serviços quase idênticos e evitar que parceiros externos manipulem dados internos.

### 21.3 De soluções locais isoladas para ativos corporativos reutilizáveis

Autosserviços, chatbot e APIs corporativas são apresentados como ativos reutilizáveis por diferentes países. A República Dominicana, Paraguai, Brasil, México e Chile foram citados em contextos de adoção ou evolução desses ativos.

### 21.4 De descoberta manual para busca assistida

A intenção de criar uma busca baseada em inteligência artificial no Marketplace aponta para uma transformação ainda em desenvolvimento: permitir que equipes formulem perguntas de negócio e sejam direcionadas às operações existentes.

## 24. Conclusões

A reunião apresentou uma estratégia de integração em que o core TRON permanece como base transacional, enquanto camadas de APIs tornam suas capacidades mais consumíveis por canais, ativos corporativos e integrações externas.

A API Edge representa o acesso amplo e mais próximo do core; a API Business representa uma camada de maior semântica de negócio; e as APIs de canal permitem construir contratos ajustados a necessidades concretas de cada país ou integração.

A pré-configuração, o API Gateway e a associação entre identidade externa e usuário TRON formam o núcleo operacional do modelo. Eles permitem reduzir a quantidade de dados que o canal precisa enviar, proteger informações críticas e aplicar regras comerciais ou operacionais por contexto.

O Marketplace é o principal mecanismo atual de descoberta e documentação. Entretanto, a própria reunião reconhece que ainda há espaço relevante para melhoria na encontrabilidade e interpretação das APIs existentes.

Por fim, a apresentação não promete uma padronização absoluta. O modelo admite que países tenham particularidades e que extensões locais sejam necessárias. A proposta é que essas extensões sejam construídas sobre uma base corporativa reutilizável, com suporte do time de APIs quando houver demanda concreta.
