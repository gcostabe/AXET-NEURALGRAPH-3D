## 7. Campos habilitados por suplemento

## 7.1. Finalidade

A definição de campos habilitados permite determinar quais informações poderão ser modificadas durante a execução de um suplemento.

Ela é opcional. Caso não seja definida, o comportamento padrão permanece disponível. Contudo, quando existe uma definição, ela pode limitar de modo importante a edição de informações.

Esse mecanismo foi destacado como especialmente útil para suplementos indeterminados, pois impede que uma operação genericamente ampla permita mudanças não desejadas.

## 7.2. Regra central de comportamento

A explicação enfatiza uma regra essencial:

- se forem definidos **campos fixos específicos**, os demais campos fixos e todos os dados variáveis deixam de ser habilitados;
- se forem definidos **dados variáveis específicos**, os campos fixos permanecem modificáveis, mas os demais dados variáveis, em qualquer nível, ficam indisponíveis para alteração.

Em outras palavras, a existência de uma configuração não atua como uma permissão adicional. Ela passa a funcionar como uma lista de permissões para o nível configurado.

## 7.3. Níveis de dados configuráveis

Foram citados os seguintes níveis:

| Nível | Descrição apresentada |
|---|---|
| Dados fixos | Informações comuns na tela de emissão, independentemente do ramo |
| Dados variáveis de apólice | Dados específicos do ramo, no nível da apólice |
| Dados variáveis de risco | Informações associadas a cada risco |
| Coberturas | Dados relacionados às coberturas |
| Listas de valores | Dados recorrentes, dependentes de determinado dado variável |

### 7.3.1. Dados fixos

Os dados fixos são comuns às telas de emissão dos diferentes ramos. Para habilitá-los, a configuração utiliza as chaves ou nomes técnicos das colunas na tabela de dados fixos, mencionada como **A 20.030**.

A palestrante esclarece que a tabela contém mais informações do que aquelas disponibilizadas na tela, mas somente os campos mostrados na emissão podem ser habilitados ou restringidos por essa definição.

### 7.3.2. Dados variáveis

Os dados variáveis são definidos de forma específica para cada ramo. Por essa razão, a configuração genérica para todos os ramos é aplicável aos dados fixos, mas não se aplica da mesma forma aos dados variáveis.

Para configurar dados variáveis, é necessário apontar um ramo concreto, porque os dados existentes dependem da definição daquele ramo.

## 7.4. Exemplo: alteração restrita de dados fixos

Foi construído um exemplo de suplemento que deveria permitir apenas:

- alterar a forma de distribuição/envio de documentos;
- alterar o tipo de documento do tomador;
- alterar o código/chave do documento do tomador.

Na configuração, o suplemento é definido para todos os ramos e associado aos atributos técnicos correspondentes aos campos desejados.

O comportamento esperado é:

- os campos explicitamente configurados ficam habilitados;
- os demais dados fixos continuam visíveis, mas não podem ser alterados;
- os dados variáveis de apólice, de risco, de cobertura e listas de valores não podem ser modificados.

A transcrição registra nomes técnicos reconhecidos de forma aproximada, como “coche envío”, “dokun” e “coche dokun”. Esses termos podem representar códigos internos de colunas, mas a transcrição não permite confirmá-los com segurança.

## 7.5. Exemplo: alteração de um único dado variável de risco

Outro exemplo utiliza um suplemento indeterminado que permite modificar apenas o primeiro dado variável de risco, identificado na fala como **UV-Ries 1**.

O comportamento descrito é:

- os dados fixos permanecem modificáveis;
- somente o dado variável de risco explicitamente indicado pode ser alterado;
- todos os demais dados variáveis, independentemente de seu nível ou ocorrência, ficam bloqueados.

## 7.6. Exemplo: lista de valores

A mesma lógica é aplicada às listas de valores. Se uma lista específica for habilitada para um suplemento:

- dados fixos continuam disponíveis para alteração;
- apenas a lista configurada fica disponível entre os dados variáveis;
- demais variáveis e listas, em outros níveis, permanecem bloqueadas.

## 8. Opções habilitadas na emissão

A palestrante alerta que a configuração genérica exige cautela. Desabilitar uma opção de maneira global pode remover uma funcionalidade necessária em um ramo específico.

## 9. Exclusões de suplementos por ramo

## 9.1. Problema endereçado

A definição de um suplemento não restringe automaticamente seu uso ao ramo que eventualmente aparece em sua chave ou configuração. Por padrão, ao criar um suplemento, ele fica disponível para qualquer ramo.

As exclusões por ramo existem para reduzir essa disponibilidade geral, escondendo ou impedindo determinados suplementos em ramos nos quais eles não fazem sentido.

## 9.2. Regra de configuração

Diferentemente de outras definições, esta não admite ramo genérico. A exclusão deve ser cadastrada para um ramo específico.

A configuração considera:

- ramo;
- chave de suplemento;
- extensão;
- tipo de suplemento.

## 9.3. Exemplo: resgate total

Foram citados quatro ramos ilustrativos:

| Identificador usado | Descrição apresentada |
|---|---|
| Ramo A | Automóvel |
| Ramo G/J | Gerais / tratamento diverso, conforme trechos da fala |
| Ramo T | Transporte |
| Ramo V | Vida |

A transcrição alterna entre “ramo J” e “ramo G” em diferentes momentos. Não é possível determinar se isso representa dois ramos distintos, uma mudança de exemplo ou erro de reconhecimento de voz.

O objetivo do exemplo era impedir que o suplemento de **resgate total** fosse utilizado nos ramos que não possuem tratamento de vida.

A lógica apresentada é:

- excluir o suplemento de resgate total nos ramos não relacionados a vida;
- deixar o suplemento disponível no ramo de vida.

A própria apresentadora identifica um erro em um dos valores exibidos no exemplo e esclarece que a referência correta era ao suplemento de resgate. Portanto, o identificador numérico específico não deve ser considerado confiável sem consulta à configuração real.

## 9.4. Implicação funcional

A exclusão afeta a lista de suplementos disponível durante a emissão. Um suplemento excluído não aparece como opção selecionável para o ramo correspondente.

## 10. Causas e motivos

## 10.1. Caráter obrigatório

Ao contrário de campos habilitados, opções e exclusões, as definições de **causas e motivos** foram apresentadas como obrigatórias.

Ao final da emissão de um suplemento, o usuário deve informar:

- a causa;
- o motivo.

O objetivo é registrar por que o suplemento foi realizado e detalhar a razão concreta da operação.

## 10.2. Dependência entre causa e motivo

Os motivos dependem das causas. Primeiro definem-se as causas; depois os motivos associados a elas.

A relação descrita pode ser resumida assim:

```text
Tipo de suplemento
        ↓
Causa aplicável
        ↓
Motivo específico da execução
```

## 10.3. Causas

As causas são associadas ao **tipo de suplemento**, e não à chave e extensão específicas do suplemento.

Um mesmo tipo pode possuir mais de uma causa.

A definição da causa contém:

- a causa;
- uma descrição/nome;
- uma abreviação.

### Exemplos apresentados

| Tipo de suplemento | Causas exemplificadas |
|---|---|
| Anulação de apólice | Decisão da companhia; decisão do segurado; gestão de inadimplência |
| Adicional | Decisão do segurado |
| Diminuição por sinistro | Sinistro |

## 10.4. Motivos

Após as causas, definem-se os motivos. A configuração de motivos considera:

- ramo, podendo ser genérico;
- tipo de suplemento;
- causa previamente definida;
- descrição do motivo;
- indicador de inabilitado.

Não há uma chave de motivo separada no modelo apresentado; o motivo é representado pela sua descrição.

Quando marcado como inabilitado, o motivo não pode ser utilizado nem aparece para seleção durante a emissão.

## 11. Restrições de suplementos por usuário

## 11.1. Finalidade

O sistema utiliza papéis para permitir o acesso de usuários aos processos de emissão. A definição adicional apresentada permite restringir determinados suplementos para usuários específicos, mesmo que esses usuários tenham acesso geral à emissão.

Assim, o controle de papel não é o único mecanismo de autorização: a execução de suplementos pode ser restringida no nível de usuário, ramo e suplemento.

## 11.2. Escopo da regra

A restrição pode ser configurada:

- para um ramo específico;
- genericamente para todos os ramos.

Os elementos mencionados são:

- ramo;
- chave e extensão do suplemento;
- tipo de suplemento;
- usuário.

O usuário deve ser informado por sua chave interna no Riff Core, isto é, o identificador utilizado ao entrar no sistema.

## 11.3. Exemplo apresentado

O cenário utiliza três usuários e três suplementos:

| Elemento | Identificação funcional |
|---|---|
| Usuário 1 | Usuário com algumas restrições específicas |
| Usuário 2 | Usuário com restrições por ramo e uma restrição global |
| Usuário 3 | Usuário sem restrições no exemplo |
| Suplemento geral | Suplemento indeterminado |
| Suplemento de renovação | Operação de renovação |
| Suplemento de anulação | Operação de anulação |

As regras explicadas incluem:

- no ramo A, o usuário 1 não pode executar o suplemento geral;
- no ramo G, o usuário 1 também não pode executar o suplemento geral;
- no ramo G, o usuário 2 não pode executar o suplemento geral;
- no ramo G, o usuário 2 também não pode executar a renovação;
- em todos os ramos, o usuário 2 não pode executar anulações;
- o usuário 3 não possui restrições no exemplo.

## 11.4. Comportamento por ramo

### Ramo A

| Usuário | Comportamento descrito |
|---|---|
| Usuário 1 | Não pode executar o suplemento geral; pode executar os demais |
| Usuário 2 | Pode executar geral e renovação; não pode anular por restrição global |
| Usuário 3 | Pode executar todos |

### Ramo G

| Usuário | Comportamento descrito |
|---|---|
| Usuário 1 | Não pode executar o suplemento geral; pode executar os demais |
| Usuário 2 | Não pode executar suplemento geral, renovação nem anulação |
| Usuário 3 | Pode executar todos |

### Ramo T e ramo de vida

| Usuário | Comportamento descrito |
|---|---|
| Usuário 1 | Sem restrição específica nesses ramos; pode executar todos |
| Usuário 2 | Pode executar geral e renovação; não pode anular, pela restrição global |
| Usuário 3 | Pode executar todos |

## 11.5. Inconsistência identificada no encerramento do exemplo

No resumo verbal final, a palestrante afirma que o usuário 2 “pode executar o suplemento general para las pólizas del ramo G” e também a renovação nesse ramo.

Essa afirmação contradiz a explicação detalhada imediatamente anterior, segundo a qual o usuário 2 não poderia executar, no ramo G:

- o suplemento geral;
- a renovação;
- a anulação.

A leitura mais consistente com as regras detalhadas é que o usuário 2 **não pode executar nenhum dos três suplementos no ramo G**. Como a própria palestrante se corrige várias vezes durante esse exemplo, a frase de resumo final deve ser tratada como inconsistente e não como regra confirmada.

## 12. Modelo operacional de configuração

A reunião permite reconstruir o seguinte fluxo operacional para definição de suplementos:

```text
1. Definir o suplemento
   ├── Chave
   ├── Extensão
   ├── Tipo
   └── Propriedades gerais de comportamento
        ↓
2. Definir controles opcionais, se necessários
   ├── Campos modificáveis
   ├── Botões e opções de emissão
   └── Exclusões por ramo
        ↓
3. Definir controles obrigatórios
   ├── Causas por tipo de suplemento
   └── Motivos por ramo, tipo e causa
        ↓
4. Aplicar restrições de usuário, quando necessário
        ↓
5. Executar o suplemento na emissão
   ├── Sistema disponibiliza apenas campos permitidos
   ├── Sistema controla as opções permitidas
   ├── Sistema filtra suplementos disponíveis ao ramo
   ├── Usuário informa causa e motivo
   └── Sistema respeita as permissões específicas do usuário
```

### Leitura analítica

O modelo descrito sugere uma configuração em camadas. Primeiro define-se a capacidade funcional geral; em seguida, são aplicadas restrições de dados, interface, ramo, justificativa e usuário.

Isso tende a permitir reutilização de suplementos sem abrir indiscriminadamente todas as possibilidades de alteração para todos os ramos e usuários.

## 18. Riscos e desafios

## 18.1. Riscos explicitamente mencionados ou exemplificados

### Configuração genérica indevida

A palestrante alerta que uma definição genérica pode desabilitar uma opção que é necessária em um ramo específico.

### Exposição indevida de suplementos

Como suplementos ficam disponíveis para todos os ramos por padrão, há risco de um suplemento aparecer em um ramo no qual ele não deveria ser usado, caso as exclusões não sejam corretamente configuradas.

### Alterações excessivas em suplementos indeterminados

Sem restrições de campos, um suplemento indeterminado pode permitir modificações muito amplas nas informações da apólice.

### Atribuição inadequada de permissões

Usuários com papel de emissão podem ter acesso ao processo em geral, mas ainda precisam de controles específicos para impedir operações de suplemento não autorizadas.

## 18.2. Desafios derivados do contexto — análise

A seguir estão interpretações analíticas, não afirmações literais da reunião.

### Complexidade de configuração

A combinação entre ramo, suplemento, extensão, tipo, dados variáveis, menus, causas, motivos e usuários pode gerar uma matriz de regras extensa. Isso sugere a necessidade de governança rigorosa de configuração e de validações antes de colocar regras em uso.

### Dependência de códigos técnicos

Diversas configurações dependem de identificadores técnicos de tabelas, colunas, programas, menus e opções. Esse aspecto pode aumentar a dependência entre conhecimento funcional e conhecimento técnico.

### Risco de inconsistência documental

Os próprios exemplos contêm autocorreções e uma contradição no resumo final de permissões. Isso indica que documentação e testes de configuração são particularmente importantes para evitar interpretações incorretas.

## 19.3. Da definição puramente técnica para uma decisão compartilhada com o negócio

Embora tabelas, códigos e menus tenham forte caráter técnico, a palestrante enfatiza que o negócio deve conhecer as opções. A implicação é que a definição de comportamento não é vista apenas como uma atividade de tecnologia: ela traduz decisões de operação e negócio.

## 23. Conclusões principais

A sessão conclui a parte de suplementos que ainda estava pendente, deixando para uma etapa futura apenas o tema de interesses de vida.

As conclusões mais relevantes são:

1. **O suplemento possui uma definição geral**, composta por chave, extensão, tipo e propriedades de comportamento.

2. **Os campos que podem ser modificados podem ser controlados**, especialmente para evitar que suplementos indeterminados alterem informações além do necessário.

3. **Os botões e opções da emissão podem ser habilitados ou bloqueados por suplemento e ramo**, com atenção especial às regras genéricas.

4. **Suplementos são inicialmente disponibilizados de forma ampla aos ramos**, sendo necessário usar exclusões para impedir usos inadequados.

5. **Causas e motivos são obrigatórios**, criando uma justificativa estruturada para a execução do suplemento.

6. **Usuários podem ser impedidos de executar suplementos específicos**, mesmo tendo acesso geral ao processo de emissão.

7. **A documentação técnica passa a ser um recurso de consulta importante**, conectando as decisões funcionais às tabelas e estruturas de dados envolvidas.

8. **A configuração exige atenção**, pois regras genéricas, identificadores técnicos e combinações de ramo, suplemento e usuário podem produzir efeitos amplos ou inesperados.

9. **Há inconsistências em alguns exemplos da apresentação**, especialmente na síntese final das permissões do usuário 2. Esses pontos devem ser validados na configuração real antes de serem usados como referência operacional.
